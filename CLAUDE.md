# CLAUDE.md

The Mac mini Claude Code runs on and controls, machine and account in one repository: shell scripts, one `Brewfile`, one `mise.toml`, the `home/` tree that is linked into `$HOME`, and the Go tools that are each a folder at the root — `hachiko/` so far. There is no release pipeline and nothing to publish: a tool's wrapper in `home/.local/bin` builds it in place on the next run after its sources change, so an edit is live within minutes of landing, and a tree that does not compile leaves the last binary that did in place. macOS and Apple Silicon only, refused up front rather than half-done. Every script opens with a comment explaining why it exists and what would break if it ran elsewhere in the order, so read the script rather than looking for a second copy of it here. README has the layout and the reasoning behind all of it — read it before changing structure.

Two files here are named CLAUDE.md. This one is guidance for working in the repo. `home/.claude/CLAUDE.md` is the global instruction file being version-controlled — content, not guidance. Do not merge them.

## Entry points

`bootstrap.sh` is the one a Mac with nothing on it has: no git to clone with, so it installs Homebrew — which brings the Xcode command line tools through `softwareupdate` rather than the dialog — clones the repo to `~/.mac-mini` and runs both phases. It takes no arguments, because there is one Mac and one shape for it. It never runs as root: there is no account to create, and Homebrew refuses root outright.

`machine.sh` refuses root and calls `bootstrap-system.sh`, `remote-login.sh`, `unattended.sh`, `tailscale.sh`, `docker.sh`, `harden-ssh.sh` in that order, then `xcode.sh` last and only where there is a terminal — Xcode is an 11GB download behind an Apple ID and a 2FA code, so a run with nobody watching lists it as left to do instead. None of it needs an account anywhere.

`claude.sh` is the second phase and the one that does: `install.sh`, then `claude/login.sh`, then `claude/signing-key.sh`. `install.sh` first because `login.sh` logs in to a Claude Code that `install.sh` installs, and `signing-key.sh` needs the `user.email` from the `.gitconfig` `install.sh` links; `login.sh` reruns `install.sh` once there is a token, for the project docs it could not clone without one. `claude/signing-key.sh` calls `claude/op-token.sh` for the 1Password service-account token — the script to rerun with `--replace` after rotating it — then `claude/ssh-agent.sh` for the agent that holds the private half and then `claude/register-signing-key.sh`, which takes the public half from that agent — or from 1Password when the agent is not up yet — and puts it on the GitHub account.

Public, which is what makes CI free, and it holds no secret: the signing key and the signing certificates are 1Password references, and the tokens are files `.gitignore` never sees.

## Edits here publish themselves

The boswell daemon commits anything dirty in this repo five seconds after the last write, through the `$HOME` and `~/.claude` symlinks too since git sees the realpaths, and pushes within the hour, when the oldest unpushed commit is an hour old. Nothing about it is yours to trigger: never offer to commit or push here, and never run `boswell once` to hurry it along. It watches the project docs the same way, pushing those within a minute; see README.

Five seconds is short, so a half-finished edit can be committed before the next write finishes it, and what lands is main with no review step. Make an edit whole in one write where it matters.

Commit and push to main yourself when something must land now, no branch and no PR. Standing permission, and an exception to the global rules on branching and asking before a push.

A sync that cannot push opens a GitHub issue titled `Auto-sync failed`, on whichever repository failed. One already open is what stops the next attempt filing a second, so close it once the push lands — an open one means the next outage goes unreported.

## Rules

- Editing the main checkout is fine here, an exception to the global worktree rule: boswell publishes main, and a worktree would only delay that.
- Everything checks before it changes. This Mac is re-run in place and is reached over the very sshd and tailnet a step here would touch, so a step that installs a second tailscale, rewrites a working sshd, or reboots a machine somebody is working on is a regression even when it is idempotent.
- Nothing is written for one account: the Mac's is `timche` and CI's is `runner`. Paths go through `$HOME`, a mise template or a `~` the reading program expands itself, and the account record is `dscl`'s rather than `getent`'s, which macOS does not have. `test/assert-machine.sh` fails on a literal `/Users/<name>` in any script, plist or `mise.toml`, and `test/assert.sh` fails on a `/Users/<name>` or `/home/<name>` anywhere under `home/` or in `mise.toml`.
- `.claude` stays under `home/`; at the repo root it would load as this repo's own project configuration. Its skills still load here a second time, as directory-scoped `home:*` skills, since Claude Code discovers `.claude/skills` in subdirectories too; that only affects sessions in this repo.
- `home/.claude/CLAUDE.md` is loaded whole into every session, and adherence drops past about 200 lines of ordinary markdown. `test/assert-markdown.sh` enforces that budget in words, about 2,400, since a paragraph here is one line however long, and the no-hard-wrap rule beside it. `test/assert.sh` runs that script and so does a Linux job of its own, because the macOS suite skips a markdown-only push; nothing in it may use a command only macOS has.
- `/bin/bash` on a Mac is 3.2, which is what every script here runs under. No associative arrays, and no reading an empty array under `set -u` — it is an unbound variable there.
- launchd expands neither `~` nor `$HOME` in a plist — a `$HOME` in `StandardOutPath` is an `EX_CONFIG` failure at load with nothing saying which key was wrong — but it does hand a gui-domain agent a `HOME`, the account's rather than the installer's. So a plist holds no absolute path: `/bin/sh -c` is what expands one, and the wrapper derives its socket, its log and its token file from the same `$HOME`. worktree-gc's is the one exception, rendered from a mise template because launchd reads `WatchPaths` itself.
- launchd also starts an agent in `/`, so anything a job runs that reads its configuration from the working directory has to be told which directory instead. `mise` is the one that bites: it decides which tools are active from the directory it is asked about, and from `/` nothing this repo declares is, so `mise which go` reports a go that is installed as missing. Every `mise` call in a wrapper or a script names its directory — `-C <repo>`, or a `cd` into it — and never relies on where it was started.
- A plist is a symlink into the checkout, so a pull moves the agent. launchd resolves the link at bootstrap and reads the file only then, so a plist that changed needs `launchctl bootout` and a fresh `bootstrap`, while a wrapper that changed needs `kickstart -k`. Neither is visible in a link that still points where it did, so the installers keep a copy or a hash of what was loaded and compare against that. The sshd drop-in stays a copy: it is root-owned in `/etc`, and a link into a checkout the account can write would hand that account sshd's configuration.
- The private half of the signing key never touches the disk. It goes from `op` down a pipe into `ssh-add` and exists in the agent's memory only. Nothing may write it, print it, or pass it as an argument — and the same goes for the service-account token that reads it. Neither is the public half written: git asks the agent which key to sign with, and `~/.ssh/allowed_signers` is the only file derived from it.
- Prompts belong in a script that has checked for a terminal. Under the documented curl install stdin is the pipe feeding `bootstrap.sh`, which is why it hands each phase `/dev/tty` when there is one; a step that would prompt without a terminal has to say what it skipped instead, or a provision with nobody watching hangs.
- A compiled tool here is Go, one folder per tool at the repo root, standard library first and `CGO_ENABLED=0`, built against the go version the root `mise.toml` declares. A POSIX sh wrapper in `home/.local/bin/<tool>` is the only thing linked into `$HOME`: it finds the checkout through its own resolved path, hashes the tool's sources, rebuilds with mise's go into `~/Library/Caches/<tool>` when that hash has moved, moves the result into place in one step, and keeps the last binary that built when one does not — a half-written edit is on the Mac within seconds of being written, and a LaunchAgent may not stop watching for it. Only the rebuild depends on mise; the binary it execs depends on nothing, which is the point on a Mac where mise or Homebrew can be the thing that broke. Each tool's behaviour is `go test` in its own folder, run by CI, and the assert scripts check only the wiring a Go test cannot see.
- mise is a version manager for language runtimes and nothing else: `node`, `bun` and `python` in `home/.config/mise/config.toml`, which is every project's, and a runtime a repository needs for itself in that repository's root `mise.toml` — which is why this one declares `go` there for its own tools, while another project's `go` or `rust` stays in that project's. Claude Code comes from Anthropic's installer into `~/.local/bin` and updates itself on the default channel, because pinning it means turning its updater off and then owning what the updater was doing; mise comes from its own installer into the same place for the reason its install page gives, and herdr from its own because `herdr update` replaces the binary it runs from. Those three are the same exception — the authors ship the installer — and `~/.local/bin` sits ahead of Homebrew's prefix in `.zshenv` and `.bashrc` so a `brew install mise` or `brew install herdr` cannot shadow them. portless, ccstatusline and chrome-devtools-mcp are npm packages in that same tool list, installed by mise's npm backend and run on mise's node, where a Homebrew formula would bring a second node.
- Every other tool is Homebrew's, one line in the `Brewfile` at the repo root — boswell included, through `tap "timche/tap"`, which is the one thing mise's bootstrap could not do: it fetches a tap's own `api/formula/<name>.json`, a plain tap publishes none, and it refuses to proxy to the brew CLI. `bootstrap-system.sh` and `install.sh` both apply it with `brew bundle --no-upgrade`, so a re-run installs what is missing and moves no version. A script that wants a package checks for it and reports what is missing; it does not install it. `xcodes` and `aria2` are the exception and stay in `xcode.sh`, which runs only where there is a terminal. `brew bundle check --no-upgrade` in `test/assert-machine.sh` is what keeps the file and the Mac in step, and asserts that no other script installs anything.

## Testing

`./install.sh` then `test/assert.sh`, on the Mac, is the quick check after a change to the account half; `./machine.sh` then `test/assert-machine.sh` for the other one. Both run against a Mac that is already built, so the fresh-Mac path is CI's alone. A change to a compiled tool is `go test ./...` and `go vet ./...` in that tool's folder — `mise exec -- go test -C hachiko ./...` from the repo root — beside `test/assert.sh`, which only checks that the wrapper, the links and the agent are in place.

CI is `.github/workflows/test.yml` on a hosted `macos-latest` runner, and nowhere else: there is no macOS container, and the suite changes the machine it runs on. It runs `bootstrap.sh` against a clone of the branch, then `machine.sh` and `xcode.sh` twice each and `claude.sh` once with the `install.sh` it starts with run again after it, asserting after each, then `go vet` and `go test` for the compiled tools, then the three launchd-backed tests, then `harden-ssh.sh`. `.github/workflows/secrets.yml` is the Betterleaks scan of the full history and `.github/workflows/markdown.yml` the markdown rules, both on `ubuntu-latest`. What none of them can reach is in README under Testing.
