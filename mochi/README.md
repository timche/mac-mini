# mochi

`mochi` is Tim's own Claude Tag for Discord. He replies to a message in a server mochi is in and mentions it with an instruction; on this Mac a Claude Code session starts in that server's herdr workspace with the lead workflow, his instruction and the conversation around it, and he carries on in herdr. It is a tool of its own rather than a hachiko command, because hachiko is scoped to looking after this Mac: a Go module in `mochi/` with its own wrapper in `~/.local/bin/mochi`, built the way [Layout](../README.md#layout) describes, its own LaunchAgent `io.github.timche.mochi` and its own log `~/Library/Logs/mochi.log`. The one link between the two is the heartbeat below.

Everything Discord goes through [`discord/`](../README.md#layout), the repository's own client, on the standard library alone: `discord/rest` for the REST API v10 and `discord/gateway` for the gateway, v10 with JSON and no compression, over a client-only RFC 6455 websocket on `crypto/tls`. mochi's `go.mod` requires that module and replaces it with `../discord`, so nothing is fetched and there is no `go.sum`; the wrapper hashes `discord/` with mochi's own sources, runs both modules' tests as the gate, and builds with `GOTOOLCHAIN=local`, so no Go toolchain is downloaded from inside the LaunchAgent either. `test/assert.sh` builds a copy with only what launchd hands the agent and the network refused (`GOPROXY=off`), which proves the checkout is enough, and breaks a test in `discord/` on purpose to prove its tests gate the binary too.

The gateway answers Hello with heartbeats at Discord's interval, the first at a random point of it; a beat due while the last went unacknowledged is a connection that died without saying so, closed and resumed. It identifies with the Guild Messages and Message Content intents, keeps the sequence, and resumes at the `resume_gateway_url` READY gave after a dropped connection, a close Discord allows a resume after, a Reconnect (op 7) or an Invalid Session (op 9) that says it is resumable; an Invalid Session that is not, and closes 4007 and 4009, identify anew, the first after a random one to five seconds. Each event mochi uses — READY, MESSAGE_CREATE and INTERACTION_CREATE — reaches a typed handler in a goroutine of its own. Close 4004, a token Discord turns away, and the other closes no reconnect gets past (4010 to 4014: shard, API version, intents) end the session for good. REST keeps Discord's rate limits: a route's bucket from the `X-RateLimit-*` headers, waited out when it is spent; a 429 waited out for its `retry_after` or `Retry-After`, every route held back when it is global, and given up on after five; a 502 sent again three times. A thread rename or post edit is made with no wait at all, so a spent bucket or a 429 there is the rename limit the caller schedules around rather than ten minutes inside the call. No error text carries the token or an interaction's.

Who and where is `home/.config/mochi/config.json`, linked to `~/.config/mochi/config.json`: the one Discord user whose mention does anything, and a `server` entry per Discord server mapping its guild id to a herdr workspace label and the repository a tab starts in. Repeek is `1220378778665095291` → `repeek` → `~/projects/repeek`. None of it is a secret — a user id is on Tim's own profile and a guild id is in the URL of every message in the server — so it is in the repository rather than 1Password; the bot token, which is, is a reference in `mochi.env.op` beside the wrapper. Every id is a snowflake as a string, copied from Discord with Developer Mode on. The keys: `user`, the one account whose mention starts or feeds a session; `server`, a list with one entry per Discord server mochi is in, each with `guild`, the server's id, `workspace`, the herdr workspace the session's tab goes in, found by its label and made when there is none, `repo`, the checkout the tab starts in so the session has that project's instructions loaded, where `~/` is this account's home; and `split`, the `model` and `effort` of the classifier below, both claude's own words, `sonnet` and `medium` when left out. What is a project's own rather than this Mac's is in the project's repository, in `.mochi/` at its root, so a session changes it through the repository like any other change and it applies once merged into the main checkout: `.mochi/config.json` holds `forum`, a forum channel's id, so a session started from a channel gets a post there rather than a thread on Tim's message, `announce`, the channel `mochi announce` posts to, and `links`, what a post may link to — a domain, each with its subdomains, or an entry with a scheme in it, which allows that one exact address, such as `chrome://extensions` — every key optional and none other allowed, each id a snowflake as a string, each domain a host name alone and each address a scheme, a host and at most a path, one JSON object with each key once (encoding/json matches keys without regard to case, so `Forum` is `forum` again) and nothing after it; the forum and the announce channel are read from Discord before use and refused, with the reason, when either is not in the server mapped to the repository. mochi reads it from the server's mapped checkout at each use — an opening, a forum post, a `mochi post`, `announce` or `edit` — as a regular file of at most 16 KB that stays inside the repository once links are followed and outside git's own files, opened without blocking so a fifo cannot hang it, and a link that leads nowhere counting as broken rather than missing; with none, each of the three is off, and one that is broken is logged and counts as none for that use, with `mochi post`, `announce` and `edit` saying what is wrong with it when they refuse for it. A mapped repository with no `.mochi/config.json` is logged once, so a forum that is missing for that reason shows in the log. A mention is of mochi's user, `<@id>` or `<@!id>`, and never of a role, mochi's own managed role included, the one Discord's autocomplete offers beside it: a role mention stays in the instruction as text. A message from Tim that names mochi without mentioning its user is ignored with one line in the log. A mention in a server with no entry is ignored, and so is every author but that user, bots included: what anybody else wrote reaches a session only as fenced data. The file is read strictly — an unknown key, or an id that is not a snowflake, stops mochi rather than leaving it obeying nobody.

What a mention gathers depends on where it is, because the discussion a moderator's suggestion gets is mostly plain messages rather than replies, and no fixed window of the latest messages holds it. A reply in a channel gets the replied-to message, its reply chain upward, about fifty messages either side of it (one `around` call, which Discord caps at a hundred), and any later message in the channel that replies to it, deduplicated and in time order. A mention inside a thread or forum post mochi did not open gets the thread from its starter, up to a hundred messages, with the starter added and the gap said when the thread is longer. A mention that replies to nothing, outside a thread, gets the last fifty messages of the channel. Every message carries its author's display name, its time and its link, and the replied-to one is marked. Tim's own mention is the instruction and is not repeated in the context, except inside a thread, where it is part of what the thread is about. Nothing gathered is dropped, but the context comes in two labelled sections, each in time order, and the orders say the first is what Tim's instruction is about: FOCUS — the replied-to message, its reply chain and the later replies to it; in a thread, its starter and Tim's mention with what it replies to; for a mention that replies to nothing, the last five messages before it — and then SURROUNDING CHANNEL, marked as possibly unrelated, with everything else. A split session's TASK line stays above both. A prompt over 200 KB loses the oldest surrounding messages first and never the focus, and says so. A follow-up and `mochi history` have no sections.

Every attachment in what was gathered is downloaded into `~/Library/Caches/mochi/sessions/<thread>/`, outside any repository, and listed by path beside its message, because Claude reads an image from a path and Discord's attachment URLs expire. 25 MB a file and 100 MB a session, and a file skipped for either is listed as skipped and why. The folder goes when the session's record does.

The session is a new tab in the mapped workspace — found by its label in `herdr workspace list`, made in the repository when there is none — with `--cwd` set to the repository, `--no-focus`, and `MOCHI_THREAD=<thread id>` in its environment; then `herdr agent start mochi-<thread> --kind claude` with no model or effort, which leaves both at Tim's defaults, and `herdr agent prompt` with the session's whole opening, pasted as it is, so the session has no file to read for it. Claude Code shows a long paste as a "[Pasted text]" placeholder but hands the model all of it; a slash command inside one never runs, and herdr passes no argument with a line break in it to a starting `claude`, so the opening names the skills instead and the model loads them, the lead skill being one a brief may ask for by name. A follow-up is pasted the same way. Each begins the way mochi's prompts do — "Invoke the lead skill and the mochi skill before anything else." for an opening, how Tim followed up for a follow-up — which is how the prompt hook tells them from his own typing. A repository can keep instructions for mochi's sessions alone in `.mochi/instructions.md`, which ordinary sessions never load: mochi reads it from the mapped checkout for every opening, a new session's, a split's or a restart's, as a regular file that stays inside the repository once links are followed, at most 16 KB of it with a note when it goes on, and puts it after Tim's instruction as a block of its own, PROJECT INSTRUCTIONS, outside the Discord fence since it is the repository's own text, with its backticks kept and nothing in it able to open or close another block; a follow-up does not repeat it. After that first line the opening carries the standing orders every session mochi starts shares, `claude-plugins/mochi/briefing.md` whole, as a block of its own, MOCHI'S STANDING ORDERS, ahead of Tim's instruction: how to read the fenced blocks and how a follow-up arrives, `mochi history` and `mochi post` with their flags, who reads what, the post shapes, the project's `.mochi/` settings, and keeping the tab's name. mochi reads it at every opening, a new session's, a split's or a restart's, from the checkout its wrapper runs from (`MOCHI_BRIEFING`), as a regular file of at most 32 KB, and a briefing that is missing, empty, too large or not a file starts no session: the log says why and Tim gets a ❌. Then comes what is that session's alone: where the session posts, then Tim's words and everybody else's in two blocks fenced the way hachiko's on-call brief is — a nonce only that prompt knows, backticks and marker look-alikes taken out — and a split session's TASK line inside the fence; a follow-up points back at the orders and the skill. The `mochi` skill holds what every post follows, whichever session makes it: plain language, no internals or names of the tools behind the work, the allowed links, attachments from the checkout or its scratch folder, the secret scan, `mochi announce`, and `mochi edit` and `mochi delete`. No on-call standing orders: this is ordinary work in a project, under the lead workflow.

The skill, the briefing and the four session hooks are a Claude Code plugin, `mochi`, in a marketplace of this checkout's own, `claude-plugins/` (`mac-mini`), rather than global skills and settings, so a session in a repository mochi does not serve has none of them. `settings.json` declares the marketplace as a `directory` source at `~/.mac-mini/claude-plugins`, which Claude Code expands itself, so no account is written into it; a relative-path plugin in a directory marketplace loads from the checkout in place, with no install record and no cache copy, so an edit to it reaches the next session. The same file sets `mochi@mac-mini` to `false`, and the plugin's manifest says `defaultEnabled: false` as well. `claude/mochi-plugin.sh`, run by `install.sh`, sets it to `true` in `.claude/settings.local.json` of each repository `~/.config/mochi/config.json` maps a server to — the local scope, which wins over the user's and the project's and is one person's alone — merged into what is there with `jq` and keeping the file's mode, a file `jq` cannot read and a symlink left alone, a repository not checked out yet reported, and nothing written where `git check-ignore` says the file is not ignored, with what to do instead.

On Discord: a thread opened on Tim's message whose first post mentions Tim — "Session started for <@Tim>'s message: <link>", the link a raw one Discord shows as a pill and a forum on its card, then the replied-to message and Tim's words as block quotes under their authors' names, line breaks kept, attachments as a count like "(2 images)", anything that would ping a crowd or a role made inert, then "**Summary:**" and the classifier's one or two plain sentences on what the messages ask for, for that session's task, escaped like any title and left out when the classifier gave none or when it holds a link or a path, by the same check `mochi post` makes, and the replied-to message shortened with "…", then the summary, to keep the post under Discord's 2,000 characters — since he keeps Discord's notifications to mentions and this is what subscribes him to the thread; he is also made a member of it, so he follows it even if the mention is missed, and neither happens in a thread he is already in. No word mochi posts names a tool behind the work, since moderators read it; the tab and the workspace are in the log for Tim — and 👀 on his message, a mention or a follow-up, for as long as mochi is handling it, taken back once the reply, the question, the ❌ with its reason, or the session's prompt is out, and 👍 in its place, which stays, once what he asked has reached a session: herdr took the prompt (after an esc when the session was on a question), every session a split or his answer to a question started has its opening, or a stop went through; a failure leaves nothing but the ❌ reply. That is all of mochi's on a message, in threads and posts of its own or of somebody else's. The state is in the name of the thread or post mochi made, in front of its title: `⏳ <title>` a session working, `❓ <title>` waiting on Tim (a question to answer, or a result to review), `✅ <title>` done with nothing left for him, `❌ <title>` failed. Discord allows a thread two renames in ten minutes, so the name wanted is kept and only the latest is sent: a rename over the limit, or one Discord answers with 429, is made once when the window has passed, never the states in between; a thread mochi did not create, such as a forum post Tim mentioned it in, is never renamed and keeps its author's title. The session moves the state itself with `mochi post --review` (❓) and `--done` (✅), and a follow-up of Tim's puts it back to ⏳ until the session's next such post. Tim stops a session with a mention whose whole instruction is "stop" or "cancel": mochi sends it an esc when it is working or on a question, prompts nothing, never asks the classifier, shows ⏸ until his next follow-up and says "Stopped. Mention mochi to continue."; the turn the esc ended pings nobody, and "stop showing the old elo" is an instruction like any other. Each session's state and its name are kept in `~/Library/Caches/mochi/marks.json`, under a lock since a session's `mochi post` writes it too, so a restart renames from the right state. A session that has stopped on Tim says so itself: the mochi plugin runs `mochi session-event` from a `Stop` hook and from a `PreToolUse` hook on `AskUserQuestion`, and say when Tim has answered in the session itself from a `PostToolUse` hook on `AskUserQuestion` and a `UserPromptSubmit` hook; each in a session with `MOCHI_THREAD` set writes one small file into `~/Library/Caches/mochi/events/` — thread, kind, and how much work was still running — and outside one does nothing; it runs the cached binary, reads no config, needs no token, prints nothing and always exits 0, so the turn and the tool go on exactly as without it. The listener reads that folder every second. A question, or a turn that ended, waits three seconds first, so a follow-up queued behind the turn that starts the moment it ends cancels it, and then shows ❓ and gets one post in its thread — "The session is waiting on <@Tim>." — the one place mochi pings anybody, allowed to ping him alone; not for a session that said it is done, nor for a turn that ended with subagents or shells still running, and not again until his next word reaches the session, from Discord or typed in the session itself. That word puts ⏳ back unless the session has set a state of its own since the ping, and anything the session reported from before it, or from before a follow-up last started it, is out of date and pings nobody. A ping that fails is retried after 30 seconds, doubling to an hour, and a thread Discord no longer has is left alone. Whether he has been pinged is kept in `waits.json`, so a restart neither pings twice nor forgets, and a restart clears any half-written event a hook was killed in the middle of. A session that is done and has cleaned up, with nothing left open, posts `--done --close`, which leaves a `close` event of its own; mochi closes its tab a minute later, but only when Tim's last word to it came from Discord. A prompt submitted in the session counts as his own typing unless it is one of the prompts mochi pastes, which the hook recognises by how they begin, and any word from him inside the minute keeps the tab open. The tab is closed only while nobody can be using it: it still carries the label mochi gave it, holds the one pane, is not the tab in front, and its agent is neither working nor on a question; otherwise the log says why and the request is dropped rather than tried again. The record stays, so a later follow-up starts a new session. The orders give a session two audiences: the thread is the team's, for progress about the product as users see it — findings, options and trade-offs in product terms, questions the team can weigh in on, results with screenshots — and the session is Tim's, for anything internal: code, APIs, rate limits, infrastructure, tools, plans. A decision with both sides is framed for the product in the thread and kept technical in the session; a post with no flag is an update about the product that needs no answer. The thread and the tab are named for what the session is about: the classifier's title for the task, or when it gave none the start of the message Tim replied to, then his own words — a name for him to find it by, which a session sees only inside the fence. A mention inside a thread somebody else opened makes that thread the session's, since a thread cannot hold a thread. Anything that fails is ❌ and one line saying why, in the thread, or as a reply to his message when there is no thread yet. Every line mochi writes itself is a sentence, a capital first and a stop at the end, and names Tim only by a mention where it means to ping him. Every post mochi makes has `allowed_mentions` empty, so nothing it quotes pings anybody.

One mention can start several sessions: "research a, b and c separately" is three. Claude decides that, rather than a rule about the wording. Before a new session, mochi runs one headless `claude -p` with `--output-format json --json-schema` and `--tools "" --strict-mcp-config --setting-sources "" --no-session-persistence`, in an empty temporary folder, with the prompt on stdin, the same scrubbed environment as herdr's, and a minute to answer. It sees Tim's instruction and the message he replied to, fenced, for resolving "a, b and c", and answers with a decision — one session, one per item, or ask — a title for the work as a whole, and every item it sees, each a title and a self-contained instruction. "many" is for items he asks to be done separately and for plainly unrelated pieces of work; "one" for a single item or one piece of work about several, such as comparing them or one plan; "ask" when his words cover several items without saying which, such as "take a look at the three suggestions". The model and effort are `split` in the config file, sonnet at medium by default; `mochi split-eval --model <m> --effort <e> < cases.jsonl` runs JSON-lined cases (`{"instruction":…,"replied":…,"want":N}`, with `"decision":"ask"` for a case that should be asked about) through the same prompt, schema and flags and prints each case's decision, count, titles, time and pass, then a summary, which is how the model is chosen. One task, or any failure — a timeout, JSON that does not parse, an empty list, no `claude` — is one session with Tim's own words, as if nothing had been asked. More than five for "many" is a ❌ and nothing started. On "ask", mochi replies to his mention "Separate sessions or one?" with two buttons, one naming the items and one for a single session — only the second when there are more than five — and he can also reply to the question with the number, "all", "separately", "one" or "1". Only his press counts; anybody else's gets "Only the person who asked can choose", visible to them alone. The press is acknowledged at once, the question is edited to show the answer with its buttons disabled, and the sessions start as if he had asked for that from the start. A question waits in `~/Library/Caches/mochi/pending.json`, so a restart still takes the answer, for a day; then it is edited to say it expired and he mentions mochi again. Buttons arrive over the gateway like messages, needing no intent and no permission beyond posting the question. Several tasks each get a public thread of their own in the channel, named from the title, and their own tab and session with the shared context and their own instruction; mochi replies to his message with a link to each, and reacts ⏳ while any of them works, ❓ when none does and one waits on him, ✅ once all are done, or ❌ when any did not start; each new thread's first post carries its own session's state. A mention inside a thread splits into the thread's parent channel; inside a forum post, which has no channel to open threads in, it is one session, and the thread says so. A follow-up is never classified.

A mention inside a session's thread is a follow-up, relayed to the same agent as a new prompt with everything posted in the thread since his previous mention, fenced: the moderators' answers and his own messages, with mochi's own posts — the session's, the pings, the replies — and Discord's notices, such as a thread renamed, left out, as `mochi history` leaves them out too; a reply to one of mochi's posts keeps its link to it, and when nobody else wrote, the relay is his message alone. Nothing in the thread reaches the session unless he mentions mochi. When the agent is gone — a session he closed — a new one starts with the whole thread as context, and the thread says so. Tim answers wherever he is, so a follow-up to a session waiting on a question, which herdr will not prompt, is his answer to it: mochi cancels the question with an esc, reads `herdr agent get` until herdr stops calling the agent blocked, as hachiko's on-call does, and then prompts it with a brief that opens by saying he answered in Discord instead of the question; a question still up after five seconds of that is a ❌ and nothing prompted. `~/Library/Caches/mochi/state.json` maps each thread to its agent, its source and his last mention; a record untouched for a week whose agent is gone is dropped with its attachments.

A session has two commands of its own. `mochi post [--review | --done] [--pr <url>] [--file <path>]... <text>` posts into its thread, split between lines past Discord's 2,000 characters, with up to ten files, each within what the server takes for one file — 10 MB, 50 MB at boost tier 2, 100 MB at tier 3, read from the guild — and a file over it, or files over it together, refused with a reason, so the session can say in the post that it is too large to attach. Any kind of file goes up, but only from inside the checkout the session runs in, a checkout of its server's repository, or Claude Code's scratch folder for that checkout or the mapped repository (`~/.cache/claude-tmp/claude-<uid>/<path with every other character a dash>`, where `.zshenv` points `CLAUDE_CODE_TMPDIR`, taken from HOME rather than from the variable), by its real path once links are followed and never from a `.git`, nor a file named as secrets are kept (`.env*`, keys and certificates, `id_*`, `.npmrc`, `.netrc`, `.pgpass`, `credentials*`, keystores, `.git-credentials`), nor one hard-linked under another name, nor one git ignores in the checkout unless it is an image, a video or a zip. Before anything is sent the post's text, and every attachment but images and videos, go through betterleaks, the scanner of the account's own pre-commit hook, into the archives they hold, with the checkout's own `.betterleaks.toml` or `.gitleaks.toml` when it has one and no configuration from the session's environment: a finding refuses the post with its rule and where it was, never the secret, for the session to tell Tim, and a scan that cannot run — betterleaks missing, failing or past a minute — refuses it as well. It is a guard against a session's mistakes, such as naming the wrong file, rather than a boundary against a session that means harm, which runs as the account and can reach the files by other ways. What a project wants attached to a review is for the project's own instructions to say. `--review` is for a post that needs an answer from Tim or the team — a result ready for review, or a question about the product — and sets ❓; `--done` is for a task complete with nothing left for him, such as after he said to merge and it merged, and sets ✅; a post with neither changes no state. The thread's readers are moderators, often not technical and without GitHub access, so a post stands on its own in Discord: plain language about what they will see as users, proof as images or video. Text carrying a link, a Discord invite or a file path is refused with the reason, bar an `https://` link whose host is one of the `links` in the server's repository's `.mochi/config.json` or a subdomain of one, with no credentials or port: a store listing is how the team finds the product. A `links` entry with a scheme in it is one exact address instead, such as `chrome://extensions`, which Discord leaves as plain text for a tester to paste: a post may name it in any case and in backticks, and anything added to it — a path, a query or a fragment — is a link again. Anything else that names such a domain — `http://`, a bare `chromewebstore.google.com/…`, `www.`, a look-alike such as `chromewebstore.google.com.evil.com` — is refused as before. A pull request goes through `--pr`, which takes only `https://github.com/<owner>/<repo>/pull/<number>` for the session's own repository, read from the mapped checkout's origin remote, and adds `#<number> (<url>)` as a paragraph of its own, after a blank line. A post with a pull request line has its link previews suppressed, the allowed links' with it; one without keeps Discord's preview of its allowed links. Before `op run` the session's server is not known yet, so the text is held to every server's domains there and to its own server's once it is. The orders tell the session to post with `--review` when it hands Tim a result and `--done` when it is finished, `--pr` on those whenever there is a pull request, and nothing else unprompted. Such a post has a fixed shape — a bold one-line summary, then **What changed** in at most three plain bullets, **Screenshots** numbered in the order the files are attached (**Videos** when the proof is videos, **Screenshots and videos** for both, which `mochi post` checks against the files), **Still to check** only when something is left, and **Questions** as a numbered list so people can answer by number — with headings and list styles fixed, and stays brief, since Tim reads the details in the session and the pull request. A pull request a session posts with `--pr` is watched from then on, in `~/Library/Caches/mochi/prs.json`: every two minutes, and only while one is watched, the listener reads it with `gh api` on the account's own `gh` login. Merged is the session done — ✅ in the name, "Merged #<n>." in its thread, archived three days later like any done post, the tab left as it is — and closed without merging is "Closed #<n> without merging." with the state left alone; either ends the watch. Either is said only when a look has found the pull request open first: one already merged or closed when the watch began was posted after the fact, and the session has said so itself, so it gets the ✅ and nothing in the thread. A pull request is watched once per session, however often it is posted, and a finished one stays recorded as finished until the session is forgotten, so posting it again after the merge starts no second watch and no second notice. Check runs that finished failed on the head commit are told to the session once per push, as one of mochi's own prompts, "CI failed on #<n>: <checks>. Fix it and push.", which puts it back to ⏳; nothing of them goes to Discord or pings Tim, and a session on a question is told once it is answered. With no text argument, `mochi post` reads the text from stdin, so a post of several lines needs no shell quoting; the outer process reads it before `op run` and passes it on as an argument. `mochi history [--before <id> | --after <id> | --around <id>] [--limit N]` prints up to a hundred more messages of the channel or thread it started from, in the same fenced form, with their attachments downloaded, and says how to page further; the prompt tells the session to page back whenever the start of the topic is not in view. Both read the thread from `MOCHI_THREAD` and refuse one mochi has no record of, and history reads only the source in that record, never one passed to it, so a session cannot browse the rest of the server.

`mochi announce [--pr <url>] [--file <path>]... [<text>]` is for any session, one mochi did not start included, and needs no `MOCHI_THREAD`: when Tim asks a session to share its work with the team, it posts to the `announce` channel in the `.mochi/config.json` of the server's repository, the server being the one whose repository the session's checkout is of — the working directory's toplevel, a worktree's own included, read for its origin remote and matched to the server whose mapped repository has the same one, and refused where none has. It is held to everything `mochi post` is: text as an argument or on stdin, the same links, paths and allowed domains, `--pr` for that repository alone, files from the checkout or Claude Code's scratch folder for it under the same rules, the server's upload limits, the betterleaks scan, and no mentions at all, Tim included. It moves no state, opens no thread, and prints the posted message's link. What goes wrong it refuses before `op run` where it can — no checkout, an unmapped one, a repository with no announce channel, a refused link or pull request — so a refusal costs no 1Password read. The `mochi` skill, loaded when Tim or the project's own instructions ask a session to share or announce something, has the orders: who reads it, what to write and not, and posting at once since his asking is the go-ahead.

Since a session posts without anybody reading it first, it can take back what it got wrong. `mochi edit [--drop-files] [--pr <url>] <message link> [<text>]` replaces a message's text, from the argument or stdin, and `mochi delete <message link>` takes it down; both work in any session. The link is a message's, `https://discord.com/channels/<guild>/<channel>/<message>` (or `ptb.`/`canary.`), in a server the config maps, and the message has to be mochi's own, in that server's announce channel or, from a session mochi started, in that session's own thread or forum post (`MOCHI_THREAD`, with a record in the state); a session mochi did not start reaches the announce channel alone, and a thread's or post's first message, whose id is the channel's, is edited but never deleted, since deleting it leaves the post with nothing on top; anything else is refused with the reason, and a link to an unmapped server, or no message link at all, before `op run`. The new text is held to a post's rules — links, paths, allowed domains, `--pr` for the server's repository, the proof heading against the attachments it keeps, Discord's 2,000 characters since an edit cannot be split, and betterleaks with the working checkout's configuration — and goes with no mentions, so an edit pings nobody, the first post that mentions Tim included. Its previews are suppressed only with a pull request line, as a post's. `--drop-files` sends an empty attachment list, which removes them all, for when an attachment is what should not be there. Both skills tell the session to fix a post that should not be there at once and say so.

The token is the `bot token` field of the `mochi-discord` item in the `dev` vault, referenced from `home/.local/bin/mochi.env.op` beside the wrapper. Every command that needs it re-enters the binary under `op run --env-file`, so it is in one process's environment and never in an argument, a file or the log, and it is taken out of any error text before that is logged. The listener resolves it once per start, and `post` and `history` once per run. A start that never got a token leaves a marker in the cache, and the next start waits out half an hour from it before asking 1Password again, as does a start Discord refused: `ThrottleInterval` alone would be an `op run` every five minutes for as long as the item does not resolve. A gateway that will not connect is tried again in five seconds, doubling to five minutes with a fifth of jitter either way and never sooner than five seconds after the last identify of any mochi process, which is Discord's limit; a close with 1000 straight after an identify is tried again at once. Ten failed attempts, or half an hour of them, and the listener exits, as it does when a connection that dropped stays down for half an hour: only a fresh start under `op run` picks up a token rotated in 1Password, and nothing beats while it is down, so the watch below has already said so. A token Discord turns away, close 4004, is not tried again at all.

While the gateway is connected — Discord acknowledging its heartbeats — mochi writes `~/Library/Caches/mochi/heartbeat` every half minute, and hachiko's watch reads its age the way it reads sync's, from the plist where there is no heartbeat yet: ten minutes without one is a ⚠️ naming `launchctl kickstart -k gui/<uid>/io.github.timche.mochi` and the log. When the wrapper has built a new binary behind it, mochi closes its Discord connection and becomes the new binary in the same process, between mentions and never inside one: `exec` with the arguments and environment it already has, so the token it was started with carries over and no second `op run` is spent. Only when that fails does it exit, for `KeepAlive` to start it again behind the plist's five-minute throttle, which also stands between a binary that crashes on start and a loop of `op run`s. Nothing else runs mochi's wrapper on a timer, so the listener runs `~/.local/bin/mochi version` itself every five minutes, with no secret in its environment, which is what builds an edit. A message sent while it is reconnecting or restarting is not replayed to it, a fresh gateway session not receiving what it missed, so a mention that got no 👀 is one to send again.

A server whose repository's `.mochi/config.json` has a `forum` gets a post in that forum for each session started from a channel, rather than a thread on Tim's message, since new messages bury a thread. The post is named as a thread would be, `⏳ <title>`, the emoji its state and nothing else, and tagged with the classifier's kind of work, `Feature`, `Bug`, `Improvement` or `Research`, found on the forum by name and skipped when the forum lacks it. A state change renames the post; a change of type edits name and tag together, which counts against the same two-in-ten-minutes limit as a rename, and a forum that refuses the tag leaves the name following the state alone. A post that still carries a state tag from before loses it with its next change. Its first message is the announcement with its quotes, Tim is made a member, and his mention gets one reply, "Created [<title>](<post>)."; a split is a post per task and one reply listing them, and the question of how to split stays a reply in the channel. A follow-up inside the post relays as one in a thread does, and `mochi history --post` reads the post where plain `mochi history` reads the channel the session came from. A session refiles its post with `mochi post --type <kind>`, when Tim says it is another kind of work or the work shows it. A post three days in `Done` is archived, never deleted, and comes back to the list when somebody writes in it. A mention inside a thread or a post mochi did not make, a forum post of somebody else's included, stays as it was: that thread is the session's, with no post. Sessions in threads opened before a server had a forum go on as threads.

Setting it up: a Discord application of its own called mochi, separate from the hachiko-discord admin bot, with Public Bot off and the Message Content intent on, invited to each server with View Channels, Read Message History, Send Messages, Create Public Threads, Send Messages in Threads, Add Reactions, Embed Links and Attach Files, which in a forum also covers making posts and editing the name, tags and archiving of mochi's own; no Manage Channels or Manage Threads; its token in the `bot token` field of the `mochi-discord` item in the `dev` vault; and an entry in the config file for the server. `install.sh` links the rest and loads the agent.

## Environment knobs

`MOCHI_CONFIG`, `MOCHI_CACHE_DIR` (the build cache, the state, the heartbeat and each session's attachments), `MOCHI_ENV_FILE`.
