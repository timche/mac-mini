# hachiko

`hachiko` watches the two failures a Mac with no screen cannot notice, every five minutes from the `io.github.timche.hachiko` LaunchAgent. Named for Hachikō, the Akita who waited at Shibuya station every day. The other thing a Mac with nobody at it needs looking after is in [The worktree sweep](#the-worktree-sweep): `hachiko gc`, on a ten-minute agent of its own, sweeping what a removed worktree and a finished session left behind. `hachiko sync` is the third, a long-running agent that commits and pushes what gets written in the project docs and in this repository's `home/.claude`; [Auto-sync](#auto-sync) has it. `hachiko update` is the fourth, and the one thing on this Mac that moves a version: the five-minute check starts one a night, in [Updates](#updates). One binary, one command and one package each. `hachiko status` is the odd one out, in [One screen of it](#one-screen-of-it): nothing runs it on a timer, it is read by a person or a session in a terminal, and it only reads.

The first is a process that lost something it retries on and is logging the mistake into a file nothing bounds, tens of gigabytes an hour; with nobody sitting at the Mac, the first symptom is a build failing for want of space. The second is a process spending a core on work nobody is waiting for, which is what a worker left behind by a session that ended looks like.

Standard library only, so the binary depends on nothing — not mise, not Homebrew, not a runtime — a Mac whose tooling has broken being exactly a Mac worth watching; [Layout](../README.md#layout) has how the wrapper builds it in place, and `go test ./...` in `hachiko/` is its behaviour, the clock, the disk, the walk, the process sample, `lsof` and herdr all being injected.

What it reads: free space on the Data volume from `statfs`, and every regular file over a gigabyte under `/private/tmp` and `$HOME`, staying on one volume and pruning `.git` and `node_modules`. A file that has gained two gigabytes since the last sample is growing fast and `lsof` names the process writing it, but that alone is no alert: what those files are gaining, against the free space they are eating into, has to put the volume within six hours of full (`HACHIKO_FILL_HOURS`), the exception being under 20 GB free, where the growth is the emergency rather than the evidence for one. Sizes are the allocated ones, a sparse disk image being apparently hundreds of gigabytes it does not occupy.

What it does not read is the whole of `~/Library` except `Logs` and `Caches`, and `~/Desktop`, `~/Documents`, `~/Downloads`, `~/Movies`, `~/Music`, `~/Pictures` and `~/Public`: under launchd an unsigned binary is its own TCC-responsible process, and a folder behind a consent prompt makes `open()` wait for a dialog on a screen this Mac does not have, so the sweep never returns and the machine's only monitor is the thing that is stuck. For the same reason a directory that has not answered in three seconds is abandoned and retried an hour later, and the walk gives up after a minute; `test/assert.sh` runs a sweep through `launchctl submit` to prove it.

CPU is the difference in cumulative CPU time between two samples over the wall clock between them, from one `ps -A` read in the C locale, the start date being half of a process's identity and the reused pid the other half. Never ps's own `%cpu`, a decaying average over a process's whole life that understates a worker which has just gone wrong. One is reported after half a core across every interval for an hour, a span of time rather than a count of runs, and `~/.config/hachiko/cpu-allow` is a glob per line for what is expected to burn a core here.

A hot process of this account's whose parent is launchd and whose working directory is inside `~/projects` or a worktree root is called out as left behind by the session that started it. One not this account's names the owner and `sudo /usr/local/libexec/claude-root restart-daemon <name>` where the [root helper](../README.md#the-root-helper) allows that daemon, and otherwise the `sudo kill` it would take, the allowlist being read out of the installed helper by string equality so that a process cannot talk its way into a command.

The thresholds: under 100 GB free, under 20 GB free, a gigabyte to be worth watching, two gigabytes of growth between samples, six hours from full, half a core for an hour. Each is an environment variable (`HACHIKO_LOW_GB` and the rest), which lets the tests trip the same arithmetic with megabytes and minutes rather than filling a disk to prove it.

One message per incident per state change: a file still growing is the same incident until it stops, low space stays one alert until free space is back over 100 GB, and a disk and a CPU incident in the same run are one message and one session.

Under 20 GB free, hachiko truncates the fastest growing file and only that one, a check working its way down the list reaching a file that is somebody's; only under `/private/tmp`, the Claude Code scratch root or `~/Library/Logs`, and only where the name ends `.log`, `.out`, `.err` or `.output` or contains `.log.`. Never an `rm` and never a `kill`: the writer keeps its descriptor and the space comes back at once.

Every sweep also caps this machine's own logs, an agent that runs for ever writing for ever: six files by exact path and never by pattern — `herdr.log`, `hachiko.log`, `hachiko-gc.log`, `hachiko-sync.log`, `hachiko-listen.log` and `mochi.log` — where over 10 MB (`HACHIKO_LOG_CAP_KB`) one previous generation is kept as `<name>.0`, so each is bounded at twice the threshold. Each is copied and then emptied in place rather than renamed, which is the thing newsyslog gets wrong, a rename-and-recreate leaving a writer that holds the descriptor appending to the archive.

Every message has one shape, and `hachiko/internal/wording` is the whole of it: a lead line of one marker and one short plain sentence, which is all a lock screen shows and all a forum post's name holds, then the findings, then the one thing Tim can do, then the incident id as subtext, a blank line between each because Discord renders consecutive lines as one block. Six markers and no others — 🔴 critical with nobody acting, 🟢 clear again, ⚠️ degraded or a deadline coming, ℹ️ nothing wrong, 💾 the disk, 🔥 a process on the CPU — and a name that has to read as prose is escaped, a worker called `[Fix it](https://wherever)` otherwise arriving as a link Tim is invited to click. `go test -run TestMessages -v ./...` prints every message end to end.

Alerts go to a private Discord forum through a bot, the one way anything hachiko has to say leaves the Mac, and the same token reads a reply back out of the thread it opened; see [Answering from Discord](#answering-from-discord). The token is the `bot token` field of the `hachiko-discord` item in the `dev` vault, referenced from `home/.local/bin/hachiko.env.op` and resolved by `op run --env-file` only when there is something to send. A send that fails leaves the incident unraised, so the next check tries again.

What hachiko cannot notice is itself not running, so every sweep checks in with [shibuya](../shibuya/README.md), a Worker rather than anything on this Mac, and a quarter of an hour without one is shibuya's message to send. The worktree sweep, sync, the Discord listener and [mochi](../mochi/README.md) each write a file as they go, and the age of that file is the whole of what the watch knows about one: one ⚠️ naming the agent's own log and the `launchctl kickstart -k gui/<uid>/<label>` that is Tim's to run, and a 🟢 when it comes back, at an hour for the sweep (`HACHIKO_GC_STALE`) and ten minutes for the other three (`HACHIKO_SYNC_STALE`, `HACHIKO_LISTEN_STALE`, `HACHIKO_MOCHI_STALE`). Nothing is said where the plist is not there, and where it is with no stamp beside it the clock runs from its modification time.

`~/Library/Logs/hachiko.log` is the log, one line per thing that happened and nothing on a quiet check. `hachiko --dry-run` reports what a check sees and changes nothing, `hachiko --test-alert` proves the way out to Discord, `hachiko --help` has the rest.

## One screen of it

`hachiko status` is the command nothing on a timer runs: one screen for a person or a session in a terminal, saying whether the machinery above is healthy without reading four logs and a `launchctl print` each. Five sections — the agents, free space, what the watch has open, every repository sync keeps upstream, and the logs it caps — in colour only where stdout is a terminal, and then one colour meaning one thing.

Each agent is two readings, since they answer different questions: `launchctl print gui/<uid>/<label>` says whether launchd has the agent at all, and the stamp says whether it is doing its job. Their thresholds, labels and logs come from the same table the watch decides liveness by, so a screen cannot say an agent is fine while the watch is alerting about it; the watch's own agent is the one with no threshold, and the screen says so and names shibuya.

The incidents are the watch's own words out of its state file, but the repositories are measured again, because what sync wrote down is what it has told Tim and what this screen answers is what is true now; late is the watch's own rule, `push_delay` plus `HACHIKO_SYNC_LATE`, and the git it runs is `--no-optional-locks`, a plain `git status` taking `index.lock` in the very repositories sync is committing in. It only reads: no state is written, the watch's lock is never taken — a sweep holds that one across a herdr call and an `op run` — and `op` is never called, a screen opened twice a day not being something that may spend the service account's day.

## The on-call session

An alert that says a file is growing is a page in the middle of the night that still needs somebody to read a process listing. So hachiko opens a Claude Code session to do the reading: `hachiko oncall <name> <brief-file>` puts a tab in the herdr workspace for this repository, with this checkout as its directory, and starts an agent called `oncall-<name>` in it, Opus at medium effort. herdr rather than a `claude -p` of its own, because Tim attaches to the same server from anywhere and an agent waiting on `AskUserQuestion` shows in his sidebar as `blocked`. Never focused, and one session per incident name, a second alert while the first is being worked being an update to that session.

That update does not always land, herdr refusing a prompt to an agent already waiting on a question, so hachiko cancels the question first: `herdr agent send-keys oncall-<kind> esc`, then `herdr agent get` to see that the agent really did leave `blocked`, and then the prompt. The esc is read back rather than assumed, `send-keys` answering for the keys reaching the pane and not for what the agent did with them, and only when the question survives it does the old path stand: the message names the tab, says the update was not delivered, and carries the whole of the detail.

The findings reach the session between two markers carrying a nonce the prompt alone knows: a path, a command line, a log line quoted back by `lsof` were all chosen by whatever filled the disk, so that block is the one part an attacker writes.

The alert goes out session first, then one short line from hachiko — what fired, and that an agent is looking into it in a named tab. The session investigates read-only and its first duty is to send its own message with `hachiko notify <incident> <file>`, the only way anything but hachiko reaches the channel: what is happening, the cause as far as it knows it, and either the one fix it is about to carry out or the options it recommends. That command takes no lock and writes no state, a sweep holding its own lock for longer than the five minutes the session is told to report within, so the report leaves a marker the next sweep picks up. Afterwards it sends `hachiko notify --outcome <incident> <file>` and writes a note under `$PROJECT_DOCS_DIR/mac-mini/incidents/`; that flag is on that one message and no other, which is how hachiko tells what resolves an incident from what a session sends while waiting.

The fallback is why hachiko speaks first and keeps its own details, the session depending on herdr, a Claude login and usage being left: if it cannot be started the first message carries the full raw details, if one started and has not reported ten minutes later hachiko sends them itself, and under 20 GB free or after a truncate it carries the whole of it immediately.

Three kinds of incident reach a session, and the third is nothing like the other two: a disk filling and a core burning are measured every five minutes and fixed by stopping something, where a step [the nightly update](#updates) could not do is fixed by a version. So an `update` session reads before it fixes anything — the failure it was handed, `~/Library/Logs/hachiko.log`, the step's own code under `hachiko/internal/update` — and what it may run for its one attempt is the step again or `hachiko update`, with `hachiko update --dry-run` for the readings alone.

## Nobody answers

A question in front of a sleeping man is not a resolution, so the wait is a timeline — a reminder at an hour carrying this check's numbers and the tab it is waiting in, a warning at two hours forty-five that in fifteen minutes the agent will act on its own, quoting the option the session itself named, and at three hours the question cancelled and the session told to decide. Three hours is Tim's number: long enough that he is asleep rather than busy, short enough that a disk losing 90 GB an hour has not taken it. Every step re-measures its numbers on the check it goes out on and sends once.

Which option the warning quotes is the session's own: any message of its that leaves something for Tim to answer carries a line reading `If no answer: <the single option you would take>`, which `hachiko notify` reads out of the message rather than taking as a flag — he reads it too, so stating it to him and stating it to hachiko are one act.

hachiko reads where the agent is from `herdr agent get oncall-<kind>`, and `blocked` is the whole of how it knows nobody has answered yet, the clock starting when a check first sees it. What ends a wait has to say what happened, which an agent merely leaving `blocked` does not, so the three endings are a `hachiko notify --outcome`, a session Tim closed, and the handover followed by the same minutes of silence the session was given to report in. An agent that is `working` gets nothing on top of a fresh turn for those minutes and no longer, a turn hung on a tool call otherwise reading as `working` for as long as the Mac is up; a wait that ends with no outcome reported posts one line saying so.

The session fixes one thing before it asks anybody. On a disk filling or a core burning that is emptying or deleting files under `/private/tmp`, the Claude Code scratch directory or `~/Library/Logs`, and inside a project's own log or tmp folder only files whose name says they are a log — or the [root helper](../README.md#the-root-helper)'s `restart-daemon`, exactly as the brief gives it. Stopping a process is not among them whatever it is costing, a kill taking whatever it was halfway through with it; on a failed update step it is the step run again, a tool rolled back, or the fix in this checkout as one commit pushed to `main`.

One attempt per incident, an attempt being one change plus the reading that says whether it worked: if that reading says it did not, the session puts its change back where it can and hands the incident to Tim with two to four options. A second attempt is where a fix on a machine nobody is looking at starts making the incident worse, so the message before the change is `hachiko notify --attempt <incident> <file>` and every prompt after it says the attempt is spent. The handover allows one thing more, stopping the process causing the incident, SIGTERM then SIGKILL ten seconds later, always the least destructive thing that resolves it — and it is in the opening prompt, so the option can be named while the whole incident is still in front of it.

The never list is the same for every kind and whatever has been handed over: any sudo but the root helper's `restart-daemon` as the brief gives it and its `reinstall-portless`; deleting or emptying anything outside those three roots and a project's own log files, `~/Library/Caches` included, since hachiko's state directory is in it; a force-push, a branch deleted, or a push to any repository but this one and any branch but `main`; an edit under `~/.claude` or `home/.claude`, which is the on-call session's own permissions; restarting herdr, the Mac or a launchd job other than through the root helper; a live Claude session's processes, unless one is itself causing the incident, in which case it is that pid and never a name; and anything that touches 1Password. Modifying source outside that one fix, a repository, a database or a docker volume, and a merge or a deploy, need him too — and on an update incident, his approval code.

These sessions run under `bypassPermissions` and act before anybody has read what they decided to do, so what holds them to that list is the orders and the partner's review below, not a hook. Every session also runs [`claude-hooks guard`](../claude-hooks/README.md), which denies `pkill`, `killall`, `fuser -k` and a `kill` whose pids come from `pgrep`, `lsof`, `ps`, `netstat` or `ss`, each session running its own copy of the same dev servers, and anything that takes the Mac's one foreground outside `focus-lock`.

Every autonomous decision also gets a second pair of eyes, the one attempt included: the session spawns `oncall-partner`, a Fable agent with Read, Grep, Glob and Bash and a prompt that forbids anything but inspection, and acts only if it agrees — a disagreement on the attempt meaning nothing is carried out, and after a handover the less destructive proposal. An answer from Tim needs no partner, he being the authority it stands in for.

The handover reaches no update incident, there being nothing to project about a step that failed and nothing retrying it once the attempt is spent; its clock stops at the line at two hours forty-five, and what resolves it is his answer or the step working on a later night. Two things cut the three hours short on the other kinds: a projection, each check, of how long until free space reaches 20 GB at the faster of what the files it can see are gaining and what the volume is actually losing, needing two checks in a row because an extrapolation from one interval is where every way of being wrong lives; and a quarter of the free space there was when the question went up being gone. An early handover is its own step and not the deadline's: a session that judged waiting safe and asked again still has its three hours coming.

Short of a handover, a question that has gone stale is cancelled and asked again, and an incident that has stopped by itself is handed to the session to verify and close — both on two checks in a row, the three-hour clock running from the first question throughout.

## Answering from Discord

Reading a reply is the half that is optional, and off until the config file names the account it is taken from. Attaching to herdr from a phone is three minutes of work and reading a message is none, so the question is answerable in the thread the alert is in — one reply, or one digit.

What this needs is `~/.config/hachiko/discord`, which ships empty: a `channel` and a `user`, both Discord snowflakes and neither a secret, which is why they are a file in the checkout. The channel is what every message goes to, so a Mac with none configured has nowhere to send an alert at all; the account is what reading a reply needs on top of it, a channel with nobody named behind it being a listener that obeys anybody who can see it. The two secrets are `HACHIKO_DISCORD_BOT_TOKEN` and `HACHIKO_APPROVAL_TOTP`, `op://` references in `home/.local/bin/hachiko.env.op`.

One incident, one thread: the first message of an incident is the message that opens the post, carrying its name and its tags with it, and every message after that goes inside, so a reminder three hours later is under the alert it is about. Whether the configured channel is a forum comes from Discord rather than from the config file — `GET /channels/<id>` and a `type` of 15, one extra call per incident and nothing to get wrong in a file — and on a text channel it is two calls instead, the message and a thread started from it; a channel whose type could not be read is treated as a text channel. The thread id is in the state against the incident, which is how `hachiko notify` finds it without taking the lock, and once nothing is pending it moves to a list of closed threads for a week, a wait being able to end before the session's outcome arrives.

The forum's two tags are found by name on the channel Discord describes rather than by an id written down here, an id in the source tagging whatever a forum rebuilt from scratch happens to have in that slot. A post is opened tagged `Open`; `hachiko notify --outcome` takes it off, puts `Resolved` on and archives the post, so what is left open in the forum is what is still running, and the retag comes after the message, Discord unarchiving a thread anything is posted into.

`hachiko listen` is the half that reads, on its own LaunchAgent, `io.github.timche.hachiko-listen`, with `KeepAlive` because the poll is the job and a process sitting in one has no business holding the lock the sweep needs. It re-enters itself under `op run` so the token is resolved once per start and not once per poll, and unconfigured it exits at once, the plist's five-minute `ThrottleInterval` being what that costs.

While it is polling it writes a heartbeat into `~/Library/Caches/hachiko/listen/heartbeat` every half minute, which the five-minute check reads the way it reads the sweep's stamp — and the two ways it stops polling are not the same thing. With nothing in the config file nobody asked for replies at all, so it removes that heartbeat and the check reads the feature as off rather than as a listener that died; with only the token unresolved, somebody does mean replies to work, so the heartbeat is left to go stale and the ⚠️ points at `~/Library/Logs/hachiko-listen.log`.

Every five seconds it asks each open thread for the messages after the highest id it has seen — an id and not a time, so a listener that was down for an hour reads what it missed — and only messages whose author is the configured user count, an instruction to an agent with authority over this Mac coming from the one person who owns it. A thread that will not answer — no permission on it, or Tim deleted it — is backed off, doubling from one poll to five minutes, and said once rather than every five seconds. A reply reaches the session cancel-then-prompt, his words fenced and the marker labelled as his rather than as incident data, a bare number read as the option he picked; the agent leaves `blocked` with nothing having recorded a nudge, which the next sweep reads as him having answered.

The never list still needs him, and a Discord account somebody has taken over is not him, so an action on that list needs a code: the session registers it with `hachiko approval-request <incident> <file>`, posts in the thread what it is asking to be allowed to do, and he replies `approve` with six digits from his authenticator. The code is checked here — RFC 6238, SHA-1, thirty seconds, one step either side — against a secret the session is never given, a code is refused the second time, and three wrong ones cancel the request.

A post about an incident that is over goes three days after it was resolved (`HACHIKO_POST_KEEP`), which the watch does once an hour. It is the one thing hachiko does that cannot be undone, so what may go is read off Discord rather than off hachiko's own state: the post is in that forum, carries the `Resolved` tag, is archived, and its archive timestamp is older than that. [shibuya](../shibuya/README.md)'s posts go the same way.

Setting it up: a Discord application with a bot, the Message Content intent turned on, invited to the private server with permission to read messages, send them, send them in threads, create public threads, manage threads, add reactions and read message history; a forum channel with an `Open` tag and a `Resolved` one; a `bot token` field and an `approval` one-time-password field on the `hachiko-discord` item in the `dev` vault; and the channel and user ids in the config file, with `updates` beside them for [the nightly update](#updates)'s summary. Manage Threads is easy to miss and is the one that tags and closes a post, and the `approval` reference is the field's own value rather than `?attribute=otp`, hachiko verifying codes itself and so needing the secret.

## The worktree sweep

Cleaning up after a removed worktree is a garbage collector, `hachiko gc`, rather than a hook on the removal, because no removal reliably hands us one: herdr removes worktrees, so does Claude Code, so does `git worktree remove` by hand, git has no post-remove hook, and Claude Code's `WorktreeRemove` does not fire for a git worktree ([anthropics/claude-code#94212](https://github.com/anthropics/claude-code/issues/94212), open) — and registering it would be the wrong trade even if it did, configuring those hooks *replacing* Claude Code's own `git worktree` behaviour.

So the trigger is time. Three of its six sweeps are about a worktree that is gone, and none runs unless it is: a compose project whose `com.docker.compose.project.working_dir` label points inside a worktree root that no longer exists, removed with `docker compose -p <name> down -v --remove-orphans`; the named volumes that project left behind; and a process whose current directory is a removed worktree, SIGTERM and then SIGKILL ten seconds later. Inside a worktree root — `~/.herdr/worktrees/<repo>/<branch>` or `<repo>/.claude/worktrees/<name>` — and nowhere else, which is not the same as a folder that does not exist: a daemon shared with another machine reports projects whose working directory was never on this disk, and `down -v` on one of those deletes a database over a path that only looks missing. It never touches pid 1, its own process tree or a process another account owns, holds a `mkdir` lock at `~/Library/Caches/hachiko-gc.lock` rather than the watch's, and `--dry-run` prints what it would do.

The volumes are the one thing no label can decide, a volume carrying only `com.docker.compose.project`: `repeek-main_postgres-data` is the main checkout's database and looks exactly like a worktree's. So the sweep records every compose project it sees with a container inside a worktree root, and which worktree, in `~/Library/Caches/hachiko-gc/state.json`, and a named volume goes only when its project is in that record and the folder is gone.

The other two are about a session that is over rather than a folder that is gone. Claude Code gives every session a scratch folder, `${CLAUDE_CODE_TMPDIR:-~/.cache/claude-tmp}/claude-<uid>/<project-slug>/<session-id>/`, and removes none of them, so the sweep removes one whose name is a session id, that no running session claims by the pid in `~/.claude/sessions/<pid>.json`, and that nothing was written under for a week, the grace being for `claude --resume`. The next is `git worktree prune` under `~/projects` (`HACHIKO_GC_PROJECTS`): git's own prune drops the metadata of a worktree whose folder git cannot find and nothing more, so a session still working keeps its entry.

The sixth is the one pass about nothing having been left behind: docker's build cache and the images nothing refers to grow whether or not a session ever ended. So `docker builder prune --force --filter until=168h` and `docker image prune --force --filter until=168h`, once a day (`HACHIKO_GC_PRUNE_EVERY`), with the age as docker's own `until` filter takes it (`HACHIKO_GC_PRUNE_AGE`) — a week, because a layer from this morning is one today's build is about to want. Never volumes, never containers, never networks, which is why it is two commands rather than one `docker system prune`, and no `-a`.

Routine cleanup is a log line and nothing else; what reaches the Discord channel is only what the sweep could not do — a compose down that exited non-zero, a process still there after SIGKILL, a prune that failed — one message per distinct failure while it persists, with a 🟢 when it clears. Docker being down is not a failure and says nothing at all.

A LaunchAgent runs it, `io.github.timche.hachiko-gc`, with `RunAtLoad` and `StartInterval` 600, and no `WatchPaths`, a worktree being two levels below anything a watch on `~/.herdr/worktrees` would see. The log is `~/Library/Logs/hachiko-gc.log`, and what the sweep cannot report is not running at all, so it writes the time it finished into `~/Library/Caches/hachiko-gc/last-run` and the five-minute check reads that stamp's age, over an hour (`HACHIKO_GC_STALE`) being one ⚠️ with the `launchctl kickstart` that starts it again.

## Auto-sync

[`hachiko sync`](#hachiko) commits, pulls and pushes `~/projects/docs` with nobody asking it to, so a note taken in one session is readable from another device a minute later. Every repository `~/.config/hachiko/sync` lists is watched by the one process, the config read once at startup, so another repository is one `repo =` line and a restart; `mode = dry-run` reports what each pass would do and changes nothing.

The second entry is this repository, and it is there for one folder: `paths = home/.claude`. The rest of it is committed by the session that changes it, as `CLAUDE.md` says, but the global `CLAUDE.md`, the settings, the skills, the agents and the hooks are written through the `~/.claude` symlink outside any change anybody set out to make, so nothing commits them. A `paths =` line, repeatable and relative to the repository's root, is what makes a daemon on a tree a session also writes to safe: every command a pass runs carries those paths, which for `git commit` is git's own `--only`, so a change staged elsewhere stays staged and out of the commit. Inside those paths the opposite holds, and deliberately — a file staged in part is committed whole, half of one on the remote being a file nobody wrote.

Three rules come with a limited repository, a `repo =` with no `paths =` being the whole repository, which is the docs. It does not pull and may not be told to: `git pull --rebase --autostash` stashes and reapplies the whole working tree, which is precisely the work this exists to leave alone, so `fetch_interval` does nothing and a rejected push is a failure posted to Discord. It syncs on one branch, the one its own `refs/remotes/origin/HEAD` names, a commit on a branch somebody checked out here carrying work in progress onto it. And a push publishes the branch rather than a commit, so sync marks its own commits with a `Synced-by: hachiko sync` trailer and pushes only when there is one waiting, counting the push delay from the oldest; a session's commits never start a push, but they do go up underneath sync's.

Two minutes of quiet rather than the docs' five seconds before `home/.claude` becomes a commit, and then the same minute's push delay. The Mac reads those files through the symlink the moment they are written, so what goes to GitHub is the history rather than the live copy.

It runs as a LaunchAgent labelled `io.github.timche.hachiko-sync`:

```sh
launchctl print gui/$(id -u)/io.github.timche.hachiko-sync         # loaded, and what launchd makes of it
tail -f ~/Library/Logs/hachiko-sync.log                            # why something did not land
launchctl kickstart -k gui/$(id -u)/io.github.timche.hachiko-sync  # after editing the config
hachiko sync --once                                                # one pass in the foreground: sync now
```

The plist is a symlink into this checkout naming no path of its own, and `install.sh` bootstraps it once `~/projects/docs` is a clone; sync exits non-zero on purpose when the wrapper has replaced its binary, so `KeepAlive` puts the new one in. Each repository is asked once, before any pass, where it really is and — for a limited one — which branch its `origin/HEAD` names; one that cannot answer is left out with a ⚠️ of its own and the daemon runs the rest.

The subject is written by a model: `subject_model = haiku` in the config, through the Claude Code already logged in on this Mac, so a commit says what changed rather than which files did. It is handed the staged diff capped at 16 KB and the last ten subjects as the house style, an alias and never a pinned model id; the call is isolated, a diff being somebody's text rather than instructions, and anything but one usable line is `Update a.md, b.md`.

Five seconds after the last write to a watched tree, a burst of edits lands as one local commit, before the rebase, so a pull runs over a checkpoint rather than a dirty tree. The push waits for `push_delay`, counted from the committer time of the oldest commit in `@{upstream}..HEAD`: a minute for the docs, long enough that a burst of notes goes up as one push and short enough that nobody reads a stale page for long. It polls `git status` every second rather than watching the tree, a recursive watcher needing cgo and being unable to exclude `.git`, and leaves a tree alone while `HEAD` is detached or a `MERGE_HEAD` exists.

A failure goes to the Discord channel every other hachiko message goes to, one ⚠️ while it persists and a 🟢 when it clears. A push rejected is rebased once and pushed again, and a rebase that conflicts is aborted and pauses pulling until the local `HEAD` or the upstream ref moves.

What watches it is the five-minute check, reading a heartbeat sync writes every half minute — the oldest of its repositories' own ticks, so a loop wedged on something no timeout caught stops it advancing. With sync alive it also reads each repository: a commit more than half an hour past its own `push_delay` (`HACHIKO_SYNC_LATE`), or a tree dirty for over ten minutes (`HACHIKO_SYNC_DIRTY`), is one message, each reading carrying the repository's own pathspec because what is not sync's to commit is not sync's to be behind on. A heartbeat over ten minutes old (`HACHIKO_SYNC_STALE`) is sync itself having stopped.

## Updates

Nobody is at this Mac, so it keeps itself up to date: `hachiko update` moves its tooling forward once a night and deals with what each upgrade leaves behind. It is the one thing here that moves a version, `install.sh` deliberately applying the `Brewfile` with `--no-upgrade` and installing mise's tools `--locked`; mise holds a release back for its default day, long enough for a hijacked release to be pulled and short enough that the Mac is never a night behind.

The five-minute [hachiko](#hachiko) agent starts it rather than a LaunchAgent of its own, since an agent that fires once a day skips the day on a Mac that was asleep at four in the morning: the schedule is a stamp in a state directory of its own, past 04:00 local (`HACHIKO_UPDATE_HOUR`) with the last finished run before 04:00 today. What the check starts is a process of its own, an upgrade taking tens of minutes where the check has five and [shibuya](../shibuya/README.md) reporting a Mac offline a quarter of an hour after its last check-in; a lock keeps the next check from starting a second one, taken over after two hours or at once where the pid it records is gone.

The steps, in order, each of them reported:

- **mise**, with `mise self-update`, since mise comes from its own installer and nothing else on this Mac can move it.
- **The tools mise manages**, with `mise up` for the global config and again with `--local` for this repository's own `mise.toml`, each naming its directory because mise decides what is active from the directory it is asked about and a LaunchAgent starts in `/`. What moved is read off `mise outdated` either side.
- **The lockfiles that rewrote**, committed and pushed to `main`, `~/.config/mise/mise.lock` and `~/.config/mise/locks` being symlinks into this checkout and a lockfile left on the Mac meaning a rebuilt Mac installing whatever `latest` meant on the day. Every git command is limited to those paths, and nothing is committed unless `main` is checked out.
- **portless's proxy daemon**, through [the root helper](../README.md#the-root-helper), when node or portless moved: the daemon is root running a path with a version in it, so a `mise up` leaves root running a file that is gone, and every `.localhost` and `.timche.dev` URL with it.
- **Homebrew**, with `brew update`, `brew upgrade` for formulae and casks, and `brew cleanup`, what moved read off `brew list --versions` either side since a cask that will not upgrade stops `brew upgrade` partway. The cleanup is the one failure worth expecting, `sudo brew services start` having taken root ownership of the keg tailscaled runs out of, and the message names the `sudo rm -rf` for it.
- **tailscaled**, restarted through the root helper when its formula moved, launchd reading a plist at bootstrap and the plist naming the `opt` symlink. Then `tailscale status --json` is read back for up to a minute, and a backend that is not `Running` is an incident: this Mac is reached over the tailnet.
- **herdr**, with `herdr update`, for the reason mise is its own: the update replaces the binary it runs from. The server is left alone, restarting it ending every session on this Mac, and takes the new binary when it next starts.
- **oh-my-zsh**, with `git -C ~/.oh-my-zsh pull --ff-only`, a clone that cannot fast-forward having somebody's commits in it. It moves between two commits rather than two releases, so what it moved is the short sha either side of the pull.
- **Apple's updates that restart nothing**, a Safari or a command-line-tools update among them, installed through [the root helper](../README.md#the-root-helper): which they are is worked out as root from softwareupdate's own listing rather than handed to it, and what went in is read back off a second listing, `softwareupdate --install` exiting zero for a label it could not find. Each is one **Moved** line. The helper is a root-owned copy only Tim installs, so until he has run `root-helper.sh` the action is one it refuses — which is said under **Needs you** every night until he has, rather than raised as a step that failed.
- **macOS and whatever is left**, which it only reports: macOS's own automatic install is off because it restarts the Mac over running sessions, and `softwareupdate --install` of a macOS update wants a volume owner's password even when root asks on Apple silicon, which this Mac has no MDM to supply in its place. Read after the install above, so what it names is what is still waiting.

One summary goes to the `updates` text channel, in three sections and that order: **Needs you**, **Moved**, **Failed**. What is waiting on Tim is read from what this Mac is rather than from what the night did — a macOS update nobody has installed, and a herdr server still running the binary it started from, which only he can restart — so it is in every summary until it is dealt with, and a night where nothing moved but something is waiting still posts one. That is also the night the lead line carries ⚠️ and a count of what needs him, rather than ℹ️. Each move says how far it went where its versions are dotted numbers — `major`, `minor` or `patch`, biggest jump first — and then what moving it took with it, one of Apple's updates carrying only the version it is now at, softwareupdate saying nothing about what was there before, the proxy daemon and the tailscaled restart being news about the version that made them necessary rather than lines of their own. A quiet night says nothing at all; without that channel it stays in `~/Library/Logs/hachiko.log`, which has every run either way.

A step that failed is an incident in the forum every other alert goes to, with [an on-call session](#the-on-call-session) on it, and the update posts nothing about one: it records what it is failing on and the next five-minute check raises it. All of one run's new failures go in one incident, kind `update`, being one night's news and one session's reading, and one that keeps failing is raised once and no more. The line saying a step works again is the update's own.

The hand-off is two files, each with one writer, the two holding a lock each and an update holding its across however long brew takes: `~/Library/Caches/hachiko-update/failing.json` is the update's, which steps are failing and since when with what the command said and the one line for Tim, and `~/Library/Caches/hachiko/update-raised.json` is the check's answer, which incident each was raised as. A Discord that was down all day loses nothing, neither file being a queue.

`hachiko update --security <thing>…` is the out-of-cycle run, here rather than beside whatever named the advisory because of the rule above: only those things, with `--minimum-release-age 0d` on the mise steps, the day a release is held back for being the wrong way round for a version that fixes something already published. A target is matched against five shapes — `mise:<tool>`, `brew:<formula>`, `pip:<python>:<package>`, `mise-self`, `herdr` — and refused otherwise, both where it is built and again where it runs, those names arriving from an advisory feed and ending up in a command line.

Such a run is answerable for two steps and no others, which keeps it out of the night's hand-off, and it writes no last-run stamp, one written at noon meaning no nightly run that night. It takes the night's lock, and its summary reads "Security update".

`hachiko update --dry-run` is the explicit "what would move", taking the readings without changing anything, and `hachiko update` is the explicit "update now", for a session waiting on a fix upstream rather than on four in the morning.
