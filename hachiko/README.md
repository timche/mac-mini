# hachiko

`hachiko` watches the two failures a Mac with no screen cannot notice, every five minutes from the `io.github.timche.hachiko` LaunchAgent. Named for Hachikō, the Akita who waited at Shibuya station every day. The other thing a Mac with nobody at it needs looking after is in [Worktree isolation](#the-worktree-sweep): `hachiko gc`, on a ten-minute agent of its own, sweeping what a removed worktree and a finished session left behind. `hachiko sync` is the third, a long-running agent that commits and pushes what gets written in the project docs and in this repository's `home/.claude`; [Auto-sync](#auto-sync) has it. `hachiko update` is the fourth, and the one thing on this Mac that moves a version: the five-minute check starts one a night, in [Updates](#updates). One binary, one command and one package each. `hachiko status` is the odd one out, in [One screen of it](#one-screen-of-it): nothing runs it on a timer, it is read by a person or a session in a terminal, and it only reads.

The first is a process that lost something it retries on and is logging the mistake into a file nothing bounds — a worker whose Redis went away writes the same connection error a few hundred thousand times a second, which is tens of gigabytes an hour into a path somebody chose because it was convenient. On a machine somebody is sitting at, the fans say so; on this one the first symptom is a build failing for want of space, hours later, with the disk already full. The second is a process still spending a core on work nobody is waiting for, which is what a worker left behind by a session that ended looks like.

It is one of the repository's compiled tools, a Go module in `hachiko/` built in place by the wrapper in `~/.local/bin/hachiko`; [Layout](../README.md#layout) has how that works and why there is nothing to install. Standard library only, so the binary the agent runs depends on nothing — not mise, not Homebrew, not a runtime — which matters because a Mac whose tooling has broken is exactly a Mac worth watching. `go test ./...` in `hachiko/` is its behaviour: the clock, the free-space reading, the file walk, the process sample, `lsof`, herdr and the sender are all injected, so every rule below is checked without filling a disk, waiting an hour or opening a session.

What it reads: free space on the Data volume from `statfs`, which is what `df` reads without the parsing, and every regular file over a gigabyte under `/private/tmp` and `$HOME`, staying on one volume and pruning `.git` and `node_modules` — walked sixteen directories at a time; the walk and the process sample together take about a second. A file that has gained two gigabytes since the last sample is growing fast, and `lsof` names the process writing it. Growing fast is not on its own an alert: what the files found growing are gaining between the two samples, against the free space they are eating into, has to put the volume within six hours of full (`HACHIKO_FILL_HOURS`) before anybody is woken for it, and otherwise the log says what is growing and how long the space would last. Free space already under 20 GB is the exception, where the growth is the emergency rather than the evidence for one and every path below behaves as if there were no horizon. Sizes are the allocated ones, from the block count rather than the apparent length, because a VM's sparse disk image is apparently hundreds of gigabytes it is not occupying.

What it does not read is the whole of `~/Library` except `Logs` and `Caches`, and `~/Desktop`, `~/Documents`, `~/Downloads`, `~/Movies`, `~/Music`, `~/Pictures` and `~/Public`. Under launchd an unsigned binary is its own TCC-responsible process with none of the grants a herdr pane has, and what it meets in those folders is not a refusal: a folder behind Full Disk Access answers "operation not permitted" at once, but one behind a consent prompt makes `open()` wait for a dialog on a screen this Mac does not have — so the sweep never returns, never releases its lock, and the machine's only monitor is the thing that is stuck. `~/Library` goes wholesale because it is every other app's data and macOS guards it under Device Control and Data Access; `Logs` and `Caches` are walked as roots of their own, being the machine's own output rather than anybody's. None of this can be discovered at runtime, because the same binary run from a session walks all of it fine — which is why `test/assert.sh` runs one sweep through `launchctl submit` and asserts it finishes, raises no dialog, and leaves no unanswered request in `tccd`'s log.

Behind that list is a deadline, because the next folder macOS decides to guard should not cost the Mac its monitor either: a directory that has not answered in three seconds is abandoned, named once in the log and remembered in the state file so later runs skip it without waiting, and the walk as a whole gives up after a minute so the CPU check and the alerts still run. Both of the calls that touch a directory are inside that deadline — reading it, and asking which volume it is on, which is an `lstat` that hangs just as readily on a mount whose server has gone away, and `~/OrbStack` is NFS.

A skip is not permanent, because a read goes slow under disk pressure and disk pressure is exactly what a runaway writer causes: a directory that stopped answering is tried again an hour later, which costs one more three-second wait if it is still gone, and if it answers it is put back in the walk and said so once. Otherwise one slow read during the incident this exists for would have blinded the watch to `/private/tmp` for good.

CPU is the difference in cumulative CPU time between two samples over the wall clock between them, from one `ps -A` for the whole machine, taken in the C locale because the start date it prints is half of a process's identity. Never ps's own `%cpu`, which on macOS is a decaying average over the process's whole life: it understates a worker that has just gone wrong and overstates one that has finished. A process is reported when it has held half a core or more across every interval for an hour, which is twelve intervals of five minutes and so thirteen samples; a sample that comes in low starts the hour again, and because the window is a span of time rather than a count of runs, an interval the agent missed costs nothing. Identity is the pid and its start time together, since a pid is reused and the history behind one belongs to whoever held it. `~/.config/hachiko/cpu-allow` is a glob per line for the things expected to burn a core here — the OrbStack VM, a UTM guest, Spotlight, Time Machine, a macOS update, the window server — and hachiko never reports its own process tree.

Who owns a hot process is read out of the same `ps` sample, `uid` for anything that decides by it and `user` for the message, since macOS keeps its daemon accounts in Directory Services rather than in `/etc/passwd` and `ps` is the only thing here that can resolve one. A process of this account's whose parent is launchd and whose working directory is inside `~/projects` or a worktree root is called out as left behind by the session that started it, which is the shape of a worker whose session is gone; everything else with a parent of launchd is called a system process owned by whoever owns it, because every daemon launchd starts has ppid 1 and calling one orphaned describes how macOS starts daemons rather than anything being wrong with it. A hot process that is not this account's also gets a line of its own in the first message and in the brief, naming the owner and the one command that would deal with it: `sudo /usr/local/libexec/claude-root restart-daemon <name>` when the daemon is one the [root helper](../README.md#the-root-helper) allows, which costs no password, and otherwise the `sudo kill` it would take and the fact that launchd starts most daemons again. The allowlist is read out of the installed helper rather than copied here, by string equality against the name `ps` reported, so a daemon Tim adds to it is named in the next alert and a process cannot talk its way into a command. The helper's command is the one sudo the session's limits allow, and one of the few fixes it may carry out before anybody has answered, since the helper restarts nothing off its list; a `sudo kill` stays on the never list, so that line is Tim's to decide on and the session's only to recommend.

The thresholds: under 100 GB free, under 20 GB free, a gigabyte to be worth watching, two gigabytes of growth between samples, six hours from full for that growth to be worth an alert, half a core for an hour. Each is an environment variable (`HACHIKO_LOW_GB` and the rest), which is what lets the tests trip the same arithmetic with megabytes and minutes rather than filling a disk to prove it.

One message per incident per state change. A file still growing is the same incident until it stops, low space stays one alert until free space is back over 100 GB, and 20 GB is an escalation that is allowed to say so once. A hot process is one incident for as long as it stays hot, and a disk and a CPU incident in the same run are one message and one session.

Under 20 GB free, hachiko truncates the fastest growing file, and only that one: the biggest offender or nothing, since a check working its way down the list would reach a file that is somebody's. Only under `/private/tmp`, the Claude Code scratch root or `~/Library/Logs`, and only when the name ends `.log`, `.out`, `.err` or `.output` or contains `.log.`. Never an `rm` and never a `kill`: the writer keeps its descriptor and its offset, so a log it appends to goes on working and the space comes back at once, where an unlinked file frees nothing until the writer exits and a killed worker takes a session's work with it. What to do about the writer is a decision for a person.

Every sweep also caps this machine's own logs, which is the other half of a disk nobody is watching: an agent that runs for ever writes for ever, and what the thresholds above catch is the emergency rather than the drift. Six files, by exact path and never by pattern, all under `~/Library/Logs`: over 10 MB (`HACHIKO_LOG_CAP_KB`) one previous generation is kept as `<name>.0`, replacing the one before it, so each log is bounded at twice the threshold. One line in the log per cap, nothing to Discord — this is hygiene rather than news — and one `lstat` per file on a sweep with nothing to cap, which is nearly all of them.

Each of them is copied and then emptied in place rather than renamed, which is the thing newsyslog gets wrong: against a writer holding the descriptor, a rename-and-recreate leaves the writer appending to the archive and the empty file at the path never grows enough to be rotated again, so rotation there is worse than doing nothing. And every one of these has such a writer — `herdr.log`, `hachiko-sync.log`, `hachiko-listen.log` and `mochi.log` for the life of the Mac, `hachiko.log` and `hachiko-gc.log` for the length of a sweep, each opened with `>>` by the shell in its plist, so the writer's next line lands at nothing rather than leaving a sparse hole, and it never knows. Between the last byte copied and the truncate the writer may append a line, and that line is lost — accepted, because the window is microseconds, these are logs read only when something is wrong, and the alternative is stopping the writer, which for herdr is every session on this Mac.

A copy fills `<name>.0.tmp` and only becomes the generation on the way out, with an exclusive create and a rename, because the thing that makes a log worth capping — a disk with nothing left — is also what makes a copy fail halfway. Writing the generation directly meant a failed copy had already destroyed the one good copy of the log and left half of it in its place, at the worst possible moment to lose it; now a failure leaves the generation before it exactly where it was and takes its own half-written file with it. A copy left behind by a sweep that was killed between the two is this sweep's to take back, the name being hachiko's own, and anything at that path that is not a plain file is what the exclusive create refuses to go round. The generation keeps the log's own permissions, so it is readable by whoever could read the log and no wider.

A cap that cannot happen is said once and not again until that log caps: the full disk, or the link somebody left, is still there five minutes later, and the watch runs twelve times an hour for ever. The state remembers which logs are owing a complaint, and forgets one the moment the log is capped or is nothing to complain about.

Nothing follows a link at any of the three paths. These are account-owned paths and hachiko runs as the account, so there is no privilege to be had through one of them — that was the whole reason this is hachiko's and not the [root helper](../README.md#the-root-helper)'s — but a write through a link somebody swapped in is still a write nobody asked for: all three are `lstat`ed and a link at any of them is refused and said so, the copy is one `O_RDWR|O_NOFOLLOW` descriptor so the file read is the file emptied, and both files it writes are opened `O_NOFOLLOW` too.

Every message has one shape, and `hachiko/internal/wording` is the whole of it: a lead line — one marker, a space, and one short plain sentence, which is all a lock screen shows and all a forum post's name holds — then `**Label:** value` lines for the findings there were and a `- ` bullet each where there are several, then the one thing Tim can do, then the incident id and the machine as Discord subtext, which is the one line in it he never acts on. One blank line between each of those and the next, because Discord renders consecutive lines as one block of text and a message of four findings is read on a phone; inside one of them nothing is spaced, so a label keeps its own bullets and a bullet keeps its continuation line. Six markers and no others: 🔴 critical with nobody acting, 🟢 clear again, ⚠️ degraded or a deadline coming, ℹ️ nothing wrong, 💾 the disk, 🔥 a process on the CPU. Sizes read "4.3 GB", rates "about 52 GB an hour", durations "1 hour 5 minutes", times "at 17:20" or "yesterday at 17:20", a process "dasd (pid 147)"; a path or a command line is in an inline code span whose fence is a backtick longer than the longest run inside it, so a file named with one cannot style the rest of the message. A name that has to read as prose rather than as code — the lead's, a process's, the account that owns it — is escaped instead, character by character, because a worker called `[Fix it](https://wherever)` would otherwise arrive as a link Tim is invited to click and one called `**You can run:**` as a line of hachiko's own. Not in the post's title, which Discord renders as plain text: the title is the lead line with that escaping taken back out. The standing orders hold the session to the same shape, so a thread reads as one voice rather than as a watch and an agent taking turns — and `shibuya/src/message.ts` is that file's counterpart on the other side, since the two post into the same channel. `go test -run TestMessages -v ./...` in `hachiko/` prints every message there is to read end to end.

Alerts go to a private Discord forum through a bot, which is the one way anything hachiko has to say leaves the Mac, and the same token is what reads a reply back out of the thread it opened; see [Answering from Discord](#answering-from-discord). Its token is the `bot token` field of the `hachiko-discord` item in the `dev` vault, referenced from `home/.local/bin/hachiko.env.op` beside the wrapper and resolved by `op run --env-file` only when there is something to send, since every run counts against the service account's daily limit. The token reaches one process and one request header: `op run` re-enters the binary with `--send`, which reads the message on stdin and posts it with `net/http`, so it is in no command line `ps` shows the machine and in no file — and net/http's own error text is redacted before it reaches the log. A send that fails leaves the incident unraised, so the next check tries again rather than going quiet about it; a channel nobody has configured is one of those failures rather than a message quietly dropped.

What hachiko cannot notice is itself not running, so every sweep checks in with [shibuya](../shibuya/README.md), which is a Worker rather than anything on this Mac: the reading when the sweep read what it meant to, and a failure when it ran and came back knowing less than it should. A quarter of an hour without one is shibuya's message to send.

The other agents it can notice, and does, in one table-driven check: the worktree sweep, sync, the Discord listener and [mochi](../mochi/README.md) each write a file as they go, and the age of that file is the whole of what the watch knows about one. Each reports its own failures, and what nothing can report about itself is not running at all. None of them is an incident and none opens an on-call session — the one answer is the `launchctl kickstart -k gui/<uid>/<label>` the message carries, and it is Tim's — so it is one ⚠️ naming the agent's own log, and a 🟢 in the same thread when it comes back. The thresholds are an hour for the sweep, which is six of its own intervals (`HACHIKO_GC_STALE`), and ten minutes for the other three (`HACHIKO_SYNC_STALE`, `HACHIKO_LISTEN_STALE`, `HACHIKO_MOCHI_STALE`), which is longer than a whole retry ladder against an unreachable remote and longer than the five minutes the listener's agent and mochi's throttle a restart by.

Nothing is said at all where the agent is not there to be running, which is the only way to tell a Mac that was never meant to run one from a Mac where it has stopped: a fresh Mac has no stamp because nothing has ever run, and alerting on that would fire on every machine this repository provisions until `install.sh` reached the agent. For the sweep, for sync and for mochi, which ships configured, that is the plist, and where the plist is there and no stamp is, the clock runs from the plist's own modification time — so an agent that was installed and never ran is caught rather than excused. The listener is the one with no such fallback: it writes a heartbeat only once a channel and a user are configured, and answering from Discord ships off, so a missing heartbeat is the feature being off rather than a listener that died. A listener with nothing configured removes its own heartbeat on the way into that idle state, which is what keeps an alert already open on it from standing for the life of the Mac with nothing left to answer it.

Once the feature is on, every way out of the listener that is not the poll is a listener which has stopped, and each of them leaves the watch something to find too old: one whose token stopped resolving keeps the heartbeat it has, and one that has never once polled at all — no `op` to resolve the token with, no env file naming it, a vault that will not answer — writes one where there is none, so the ⚠️ fires ten minutes later rather than never. Only where there is none, which is the whole of it: launchd starts that agent again every five minutes for as long as it keeps exiting, and a heartbeat rewritten on each of those starts would be the one alert here that can never fire.

The beat itself is a pass that found Discord answering, and not a pass that happened. A token Discord rejects, or a permission taken off the bot, is a listener that polls for ever and reads nothing, with every reply Tim sends reaching nobody — and the only thing on this Mac that could notice is the heartbeat it stops writing. A thread whose last read failed counts as one it cannot reach, and so does a thread inside its backoff: with up to five minutes between tries, almost every pass of a failing listener is a pass that asked nothing, and reading those as healthy is what would let a rejected token keep its heartbeat. Nothing open is not trouble, which is also the limit of what this can see — there is no thread to read, nothing is asked of Discord, and a token it would reject is not found out until an incident gives the listener something to read.

The exception is an agent that goes while the watch has an alert open on it, which gets one ℹ️ in that same thread saying it is no longer installed, and then nothing further. Silence under a ⚠️ is the one thing this watch never leaves, and an agent being removed answers "it has stopped" as much as its coming back does — without that line the last word in the thread is a warning about something that has since ceased to exist.

`~/Library/Logs/hachiko.log` is the log, one line per thing that happened and nothing at all on a quiet check. `hachiko --dry-run` reports what a check sees and changes nothing, `hachiko --test-alert` proves the way out to Discord, and `hachiko --help` has the rest.

## One screen of it

`hachiko status` is the command nothing on a timer runs: one screen for a person or a session in a terminal, saying whether the machinery above is healthy without reading four logs and running a `launchctl print` each. Five sections, a few lines apiece — the agents, free space, what the watch has open, every repository sync keeps upstream, and the logs it caps. Plain text in columns, and colour only where stdout is a terminal, and then one colour meaning one thing: this is degraded. A pipe gets none, because the first thing done with the output is to grep it or paste it into a message.

Each agent is two readings rather than one, since they answer different questions: `launchctl print gui/<uid>/<label>` says whether launchd has the agent at all and the pid when it is running something this minute — an agent on an interval has none between runs, which is not the same as not being there — and the stamp says whether it is doing its job. The stamps, their thresholds, the labels and the logs come from the same table the watch decides liveness by, so a screen cannot say an agent is fine while the watch is alerting about it. The watch's own agent is on the list and is the one with no threshold, because nothing on this Mac can tell whether the thing doing the checking is running; the screen says so and names [shibuya](../shibuya/README.md). launchd's output is parsed defensively — a whole key matched, the first match taken, anything unparsed read as an agent running nothing — since that block is nested, undocumented and launchd's to change.

The incidents are the watch's own words, out of its state file: what it has open and since when, which tab the on-call session is in, and the three things it says once and then remembers having said — an agent that has stopped, a repository sync is getting nowhere with, and a log it could not cap. An alert nobody was ever told about is not an open alert and is left out. The repositories are measured again instead, by two read-only git commands apiece and a read of sync's own record of a conflict, because what sync wrote down is what it has told Tim and what this screen answers is what is true now. A limited repository's row names the paths it is limited to, since every other cell in it is measured inside those and nowhere else in the checkout. Late is the watch's own rule, the repository's `push_delay` plus `HACHIKO_SYNC_LATE`, for the same reason the thresholds are one table.

Both of those commands, and the watch's own two, run `git --no-optional-locks`, because read-only is not the same as lock-free: a plain `git status` refreshes the index and takes `index.lock` to do it, and the repositories being read are the ones `hachiko sync` is committing in every few seconds. A screen somebody opened to see whether sync is working, or a check asking whether it has fallen behind, may not be the reason a commit fails.

It only reads. No state is written, the watch's lock is never taken — a sweep holds that one across a herdr call and an `op run`, so a screen that waited for it would hang for minutes — nothing is sent anywhere, and `op` is never called, since a screen somebody opens twice a day may not spend the service account's day. It exits non-zero only where it could not run at all: a reading it could not take is a line in its own section, because this reports problems rather than being one more thing that has them.

## The on-call session

An alert that says a file is growing is a page in the middle of the night that still needs somebody to read a process listing. So hachiko opens a Claude Code session to do the reading: `hachiko oncall <name> <brief-file>` puts a tab in the herdr workspace for this repository, with this checkout as its directory so the session starts with the machine's own instructions loaded, and starts an agent called `oncall-<name>` in it. herdr rather than a `claude -p` of its own, because Tim attaches to the same server from anywhere with `herdr --remote`, the session is still there hours later, and an agent waiting on `AskUserQuestion` shows in his sidebar as `blocked` — which is the point, since everything the session may not fix by itself ends in a question for him. Never focused, since he may be in the middle of something, and one session per incident name: a second alert while the first is still being worked is an update to that session rather than a second agent on the same disk.

That update does not always land. herdr refuses a prompt to an agent that is already waiting on a question, and waiting on a question is where the standing orders leave an on-call session that could not fix what it found — so the commonest second alert of an incident would reach nobody. What hachiko does instead is cancel the question: `herdr agent send-keys oncall-<kind> esc`, then `herdr agent get` to see that the agent really did leave `blocked`, and then the prompt. The order is the whole of it, since a prompt sent first is one herdr refuses and a step recorded as delivered is one never tried again, and the esc is read back rather than assumed because `send-keys` answers for the keys reaching the pane and not for what the agent did with them. The options in the old question were about the incident as it stood when it was asked, so the session asks again with ones that fit what it is now. Only when the question survives the esc does the old path stand: the message names the tab, says the update was not delivered, and carries the whole of the detail, because nothing in that tab is going to read it for him. The same goes for a session that started but that the brief never reached — the tab is named rather than left unmentioned, and nothing waits ten minutes for a report that cannot come.

The model is Opus at medium effort, passed through to Claude Code as `-- --model opus --effort medium` on the `agent start`. It is the only thing reading a process listing at four in the morning, and the only thing deciding what to do about what it read.

What reaches the channel either way is one message per state change. A truncate is the exception that always sends: it is the one thing here that changes somebody's disk, so it is an incident of its own even on a run where the file was already flagged and the threshold was already crossed.

What the session is handed is a prompt whose orders come first, then the findings between two markers carrying a nonce that prompt alone knows, then a line saying that was the data. Everything in that block — a path, a command line, a log line quoted back by `lsof` — was chosen by whatever filled the disk, so it is the one part of the prompt an attacker writes: the fence is what keeps a file named "ignore your orders" from reading as a turn in the conversation, backticks go out of it, and nothing inside it can spell the end of it. Paths and arguments are clipped on the way in for the same reason Discord's 2,000 characters are respected.

The order the alert goes out in is the session first, then one short line from hachiko — what fired, and that an agent is looking into it in a named tab. The session investigates read-only, and its first duty is to send its own message: what is happening, the cause as far as it knows it, and then either the one fix it is about to carry out or the options it is about to offer and which one it recommends. It sends that with `hachiko notify <incident> <file>`, which is the only way anything but hachiko reaches the channel and which is handed no URL of its own. That command takes no lock and writes no state: a sweep holds its lock across a herdr call and an `op run`, which together can outlast the five minutes the session is told to report within, so the report leaves a marker and the next sweep is what clears the incident. Then it either carries out the one fix described below or waits in `AskUserQuestion` with two to four options, recommendation first. Afterwards it sends the outcome as `hachiko notify --outcome <incident> <file>` and writes a note under `$PROJECT_DOCS_DIR/mac-mini/incidents/`. That flag is on that one message and no other, which is the whole of how hachiko tells the message that resolves an incident from the several a session sends while it is still waiting; `--outcome` is a constant word rather than anything of the incident's, so it is one of the few things here allowed to be an argument, and `--attempt` below is the other.

The fallback is why hachiko speaks first and keeps its own details. The session depends on herdr being up, on a Claude login and on usage being left, and a watch that only ever spoke through an agent would be silent exactly when that chain broke. So: if the session cannot be started, the first message carries the full raw details and says so; if a session started but has not reported ten minutes later, hachiko sends the details itself and says the agent did not report; and under 20 GB free, or after a truncate, the first message carries the whole of it immediately rather than waiting for anybody to finish reading.

Three kinds of incident reach a session, and the third is nothing like the other two. A disk filling and a core burning are measured every five minutes and fixed by stopping something; a step [the nightly update](#updates) could not do is measured by nothing at all and fixed by a version. So an `update` session reads before it fixes anything: the failure it was handed, `~/Library/Logs/hachiko.log` for the run it came from, the step's own code under `hachiko/internal/update` in this checkout and what the tool itself says about its own state. Then it makes the one attempt below, and what it may run for it is the step again or `hachiko update` — `hachiko update --dry-run` for the readings alone — a run from inside a herdr pane working because the step that updates herdr drops herdr's own variables for that one command. The markers it may write and the orders it is given are shaped for it, the autonomy below among them.

## Nobody answers

A question in front of a sleeping man is not a resolution. Whatever the session could not fix itself, it asks about and then waits — and if Tim is asleep or in the middle of something, the options go stale, the writer goes on writing, and the incident is never closed by anybody. So the wait is a timeline rather than an open end, and at the end of it the session decides.

hachiko reads where the agent is from `herdr agent get oncall-<kind>`, one call per kind per check. `blocked` is the whole of how it knows nobody has answered yet, and the clock starts when a check first sees that rather than when the brief went out: the wait being measured is his, and until the agent has asked him something there is nothing for him to answer.

What ends a wait is something that says what happened, and an agent that has left `blocked` is not one of them. Tim picking an option, hachiko's own `esc`, and a session that gave up on its turn are one reading from herdr, and ending the wait on it closed an incident on the strength of hachiko's own cancel and then told nobody. So the three endings are a `hachiko notify --outcome`, which is the message that says the incident is resolved; a session Tim closed, which there is nothing left to hand anything to; and the handover followed by the same minutes of silence the session was given to report its findings in. Only that flag ends it the first way, because a session sends more than two messages — its analysis, the same question posted into the Discord thread, an update when the situation moves — and reading any second report as the outcome ended the wait on the strength of a message saying the question was still open.

A session that was briefed and has not got as far as a question keeps its wait for an hour, and the clock starts whenever that first `blocked` sighting comes. The ten-minute deadline above is for its first message and not for its question — the question comes after the reading — and a wait dropped at that deadline threw the whole timeline away for a session that asked two minutes later.

So answering in herdr is not by itself an answer as far as hachiko is concerned. Picking an option there and leaving the session to it reads exactly like the two things that are not an answer, and the timeline goes on until the session says what came of it with `--outcome`. That is the right way round: what he picked still has to be carried out, and nothing but the session knows whether it was.

In between, an agent that is `working` is working on his answer or on what hachiko handed it, and nothing goes out on top of that while the turn is fresh: no reminder, no warning, no handover over the work hachiko asked for. That pause is the minutes a session is given to report in and no more, because a turn hung on a tool call reads as `working` for as long as the Mac is up and a wait that deferred to it without limit would have no reminder, no warning and no handover at all — the silence the whole timeline exists to prevent, reached through the one state that looks reassuring. The early handover is the exception the pause does not hold, since a disk that will be full before he wakes does not wait for a tool call either.

An agent with no question up and nothing in flight keeps the timeline running, with each step sent as a prompt alone: there is no question of its own to cancel, and an `esc` to an agent that is not on one takes away whatever it has started. An unblock hachiko did not cause gets the same few minutes first, in case it is him answering with the agent between turns; one hachiko caused itself gets none, that being the reading none of this trusts.

Every way a wait ends with no outcome reported posts one line saying so, and so does a handover that reaches nobody — once per incident, however long it goes on failing. Without those, the last word in the channel about an incident nothing resolved is the warning that the agent would decide in a quarter of an hour, and nothing after it.

A marker merges with the one before it rather than replacing it, so a later message that happens not to repeat the `If no answer:` line keeps what the last one said — overwriting lost the option the warning has to quote. And that line is read as a line of its own, the last of them: a session quotes log lines into its report, and anything looser handed Tim an option chosen by whatever filled the disk.

At an hour, a short reminder with this check's numbers — free space, what the file is now and how fast, what the process is spending — and the tab it is still waiting in. At two hours forty-five, a warning that in fifteen minutes the agent will act on its own, quoting the option the session itself named. At three hours, the question is cancelled and the session is told to decide. Each step sends once and only once it has actually sent: a Discord that was down for the one check an hour came up on tries again on the next rather than losing the step, and a step that fires marks the earlier ones done, so a check coming back after an outage does not send an hour's reminder about a question already past its deadline. Nothing of hachiko's own goes to the channel at the handover itself — the session's own message is what says what it did and why, and two messages about one decision would be one too many.

The `esc` that cancels the question is read back until the agent has actually left `blocked`, for about five seconds. send-keys answers for the keys arriving in the pane and not for what Claude Code did with them, and the real herdr was measured answering `blocked` on the first read after the `esc` and `done` 152 to 160 ms later: one read, taken straight afterwards, is what concluded that the question was still up and sent no prompt at all. When the `esc` lands and the prompt that was to replace it does not, hachiko remembers owing that prompt and the next check sends it on its own — a second `esc` would cancel whatever the session has started since, and there is no question left to cancel. The standing orders say the other half of it to the session: a question cancelled while it waits is hachiko's doing and not Tim declining, and hachiko's prompt follows.

Three attempts in a row that do not land are the end of it until the agent is seen off its question. An `esc` that keeps failing is a question taken away every five minutes with nothing put in its place, and an agent sitting on one herdr will not cancel is the one state nothing can be delivered in at all — so the messages to Tim go on, the line the failed handover posted is what names it for him, and nothing of the agent's is touched again until there is no question there.

Three hours is Tim's number: long enough that he is asleep rather than busy, short enough that a disk losing 90 GB an hour has not taken it. Reminders and the handover carry numbers re-measured on the check they go out on rather than the ones the question was asked with, because an answer to a three-hour-old question is about a machine that has moved.

Which option the warning quotes is the session's own. Any message of its that leaves something for Tim to answer has to carry a line reading `If no answer: <the single option you would take>`, and `hachiko notify` reads that line out of the message rather than taking it as a flag of its own. It is a line Tim reads too, so stating it to him and stating it to hachiko are one act — and nothing the session writes about an incident goes in a command line, where every process on the machine reads it and a path chosen by whatever filled the disk would be an argument. The marker the report leaves is where it is kept until the next sweep picks it up.

A question in front of a sleeping man resolves nothing, so the session fixes one thing before it asks anybody. Which fix depends on the kind. On a disk filling or a core burning it is emptying or deleting files under `/private/tmp`, the Claude Code scratch directory or `~/Library/Logs`, and inside a project's own log or tmp folder only files whose name says they are a log — `*.log`, `*.out`, `*.err`, `*.output` or `*.log.N`, which is the same rule the truncate above obeys and for the same reason: a project's tmp folder holds a build somebody is waiting on as readily as a log, and "its log folder" is a licence to empty the log files in it rather than the folder — or running the [root helper](../README.md#the-root-helper)'s `restart-daemon` for the busy daemon, exactly as the brief gives it and never spelled by the session, because a daemon loop is the incident the helper exists for and forbidding it left dasd spinning through two nights with the fix one passwordless command away. Stopping a process is not among them, whatever it is costing: a kill takes whatever the process was halfway through with it, and nothing in a reading of the disk prices that, so it waits for Tim or for the handover. On a failed update step it is the step run again or `hachiko update`, a tool reinstalled or rolled back through mise or brew, or the configuration or code fix in this checkout — made in a worktree, tests green, as one commit pushed to `main`, which is what every session here does and so needs nothing of him.

One attempt per incident, and an attempt is one change plus the reading that says whether it worked: the step run again, or the numbers taken again. If that reading says it did not work, the session puts its own change back where it can — `git revert` of its commit, the version it replaced reinstalled — and hands the incident to Tim with what it tried, what it saw and two to four options with its next idea first. The second attempt is where a fix on a machine nobody is looking at starts making the incident worse, so there is not one: the message that goes out before the change is `hachiko notify --attempt <incident> <file>`, which records the attempt in the wait, and every prompt that reaches the session after it — a question cancelled and asked again, the handover, his reply out of Discord — says that the attempt is spent. Only Tim picking something gives the session anything further to carry out. A fresh incident of the same kind gets its own attempt, because a disk that filled again after the log was emptied is a new fault with a new reading behind it.

What it may do at the three-hour handover is then one thing more: stopping the process or processes causing the incident, SIGTERM and then SIGKILL only if it is still there ten seconds later. Always the least destructive thing that actually resolves it, and if the only effective fix is on the never list, nothing destructive happens at all: it says which fix it is, why it stopped, and goes on waiting. All of it is in the opening prompt rather than only in the prompt that hands it over, so the session knows from the first minute what it would be allowed to do and can name the option while the whole incident is still in front of it.

The never list is the same for every kind and whatever has been handed over: any sudo but the root helper's `restart-daemon` as the brief gives it and its `reinstall-portless`; deleting or emptying anything outside those three roots and a project's own log files, `~/Library/Caches` included, since hachiko's own state directory and the binary the wrapper builds are in it; a force-push, a branch deleted, or a push to any repository but this one and any branch but `main`; an edit under `~/.claude` or `home/.claude`, which is every session's configuration and the on-call session's own permissions with it; restarting herdr, the Mac or a launchd job other than through the root helper; a live Claude session's processes, unless that process is itself what is causing the incident, in which case it is that pid and never a name every session answers to; and anything that touches 1Password. Deleting or modifying source outside that one fix, a repository, a database or a docker volume, and a merge or a deploy, need him too — and on an update incident, his approval code. That code reaches what is his rather than what is on the never list: the hook refuses a never-list action however it has been approved, so one of those is a command he runs himself, and the session's part is to say exactly what it is.

That list is a hook rather than a paragraph, because these sessions run under `bypassPermissions` and now act before anybody has read what they decided to do. `hachiko oncall` creates the tab with `--env HACHIKO_ONCALL_SESSION=<kind>`, so the marker is in the environment of Claude Code, of every subagent it spawns and of every hook run for either — all of them one process tree — and `home/.claude/hooks/oncall-guard.py` is a `PreToolUse` hook on `Bash`, `Edit` and `Write` that exits before reading its own stdin in every session without that marker. For a marked one it reads the command, refuses anything on the list with exit code 2 and the reason on stderr, which is the refusal that stops the call before the permission rules — which in one of these sessions allow everything — are read at all, and which the agent reads as the denial reason. The daemons it will allow under sudo are read out of the installed helper, like the brief's own line, so a daemon Tim adds to it is one the guard allows the same night. A guard against this session's own mistakes and not a sandbox: the account already has root by other routes and writes the hook itself, so what it has to catch is the plausible wrong move at four in the morning rather than a determined one, and where a rule cannot be read off the command — whether the brief really gave that daemon, whether the one attempt is already spent — the orders and the partner hold it instead.

Every session, marked or not, also runs `home/.claude/hooks/kill-by-pid.py`, a `PreToolUse` hook on `Bash` that denies `pkill`, `killall`, `fuser -k` and a `kill` whose pids come from `pgrep`, `lsof`, `ps`, `netstat` or `ss`, since every session runs its own copy of the same dev servers and a name, pattern or port reaches all of them. It reads the command the way the shell splits it, so a mention in quotes goes through, and lets through anything it cannot parse rather than cost every session its shell.

Every autonomous decision gets a second pair of eyes before it happens, the one attempt included. The session spawns `oncall-partner`, a Fable agent with Read, Grep, Glob and Bash and a prompt that forbids anything but inspection, hands it the incident and the action it proposes, and acts only if it agrees. On the attempt a disagreement means nothing is carried out and the incident goes to Tim with both views; after a handover it means the less destructive of the two proposals where both are inside the limits, and otherwise nothing destructive at all. The message after acting says the partner reviewed it and what it found, and quotes the limit the action was allowed under, so what was permitted is in the record rather than in somebody's reasoning. An answer from Tim needs no partner — he is the authority the partner stands in for.

The handover reaches no update incident. There is nothing to project about a step that failed and nothing a crossed free-space mark says about one, and once the session's own attempt is spent nothing on this Mac retries the step again — retrying is moving a version with nobody watching, which is the one thing here that happens only on the schedule Tim set. So its clock is the reminder at an hour and then one line at two hours forty-five saying that nobody has answered and that nothing retries it, quoting the option the session named, which for one of these says what is left rather than what it would do: usually that tomorrow night's run tries the step again. Nothing is handed over at three hours and nothing further is sent, the question stays in front of him, and what resolves it is his answer in the thread or in herdr — or the step working on a later night, which is the update's own 🟢 into that post and the end of the wait. A session he closes and a herdr nothing can reach end it the way they do for any other incident.

Two things cut the three hours short, because a disk that will be full before he wakes is not something to wait out. hachiko projects, each check, how long until free space reaches 20 GB at the faster of the two rates there are to go by — what the files it can see are gaining, and what the volume is actually losing, which catches a writer the walk never found — and hands over early when that comes before the handover would or inside the hour, whichever is sooner. Two checks in a row have to say so, because that is an extrapolation from one interval and one interval is where every way of being wrong lives: one burst of writing that stops by itself, a volume somebody freed and refilled, a sample taken late. Five more minutes is nothing against three hours, and a single subtraction is not enough to hand a session the authority to stop a process. A span the check had to invent rather than measure is no projection at all — a Mac that slept, or a clock somebody set, divides a real growth by a made-up second and says the disk is about to go — so the projection is skipped outright on one of those. The other trigger needs no rate and no second opinion, being a measurement rather than a projection: a quarter of the free space there was when the question went up is gone. The numbers are hachiko's, since it is the only thing sampling the disk every five minutes while the agent sits on its question; the judgement is the session's. It may agree that waiting costs more than acting and act, or decide the writer is about to stop by itself and ask again with fresh options — and it says which it chose either way. An early handover is its own step and not the deadline's: a session that judged waiting safe and asked again still has three hours coming, which is what the clock was for.

Short of a handover, a question that has gone stale is cancelled and asked again rather than left standing: a file that has doubled since it was asked, a free-space threshold crossed in either direction, or a writer that was not there before. Only against writers that were actually recorded, since a file between writes when the question went up has none and the next one found would otherwise look new on nearly every incident. The three-hour clock keeps running from the first question through all of it, and so does a new alert for the same kind: he has been unanswered since then either way, and a writer that worsens every hour would otherwise push the deadline out for ever. The steps do reset with a new incident, because the handover is a decision about an incident and each one gets its own.

An incident that has stopped by itself is the one piece of news that comes before everything on the clock and outlives a handover already made. A check that finds nothing growing fast enough to reach the end of the volume with free space over every threshold, or nothing over the CPU share, hands the session that reading the way it hands it a change: verify it against the machine rather than taking the reading for it, and if it really has resolved, report the outcome and close. Two checks in a row have to say so, the same rule the projection above obeys and for the same reason: one interval is a writer between bursts or a daemon between runs as readily as an incident that is over, and what this hands the session is a reason to close one. Said once per incident, because every check after the first says the same thing about the same quiet Mac, and never off a reading that is missing rather than clear — a walk that ran out of its seconds saw part of the disk, a directory it was told to skip may be holding the very file the question was asked about, and a check with no process sample saw no processes. Without any of it a daemon that stops spinning by itself leaves a session waiting on a question about a process that is no longer there, and nobody is told until somebody asks.

The last way this ends badly is a session Tim closed. An agent herdr has never heard of is gone rather than an error, and at the deadline hachiko says so itself: no agent left to decide, nothing was done, and the numbers as they stand.

herdr not answering at all is neither an answer nor a closed session, so one check that cannot reach it leaves the wait exactly as it was — a server being restarted or a configuration being reloaded is not something to wake anybody about, and the next check asks again. An unbroken run of them is the other thing entirely: there is no session to remind, nothing to hand a decision to and no way to tell whether anybody answered, so after the same minutes a session gets to report in, one line says the session cannot be reached and nothing is being worked, and the wait stops being counted. Any answer at all ends the run, so an outage that came back and went again is two outages, each measured from itself.

## Answering from Discord

Reading a reply is the half that is optional, and off until the config file names the account it is taken from. Attaching to herdr from a phone is three minutes of work and reading a message is none, so the question is answerable in the thread the alert is already in — one reply, or one digit.

What this needs is `~/.config/hachiko/discord`, which ships empty: a `channel` and a `user`, both Discord snowflakes and neither a secret, which is why they are a file in the checkout rather than a 1Password reference. Anything in there that is not a snowflake is read as nothing, since both end up in a request path. The channel is what every message goes to, so a Mac with none configured has nowhere to send an alert at all; the account is what reading a reply needs on top of it, since a channel with nobody named behind it would be a listener that obeys anybody who can see it.

The two secrets are `HACHIKO_DISCORD_BOT_TOKEN` and `HACHIKO_APPROVAL_TOTP`, `op://` references in `home/.local/bin/hachiko.env.op` beside the wrapper, which is the one env file hachiko has: `op run` is given it whenever there is something to send or a listener to start, and it refuses a reference it cannot resolve, so both fields have to exist on the item before either command works. The token reaches one process's environment and one `Authorization` header, and every error text that leaves the bot has it taken out first.

A bot that will not post — a token Tim revoked, an application somebody deleted, a channel the bot was removed from — is a send that failed, and there is nowhere else for the message to go. The error goes to the log and the incident is left unraised, so the next check sends it again rather than the watch going quiet about a disk filling because of a permission. A thread that could not be opened is the other way round and not a failed message at all — the message is already posted, so the rest of that incident goes to the channel rather than being sent a second time.

One incident, one thread. The channel is a forum one, so that thread is a post and the first message of an incident is the message that opens it: one `POST /channels/<forum>/threads` carrying the post's name, its tags and the message together, and the post's id — which is the starter message's id as well — is what comes back. On a text channel it is two calls instead, the message and a thread started from it. Which of the two it is comes from Discord rather than from the config file, `GET /channels/<id>` and a `type` of 15, one extra call per incident and nothing to get wrong in a file; a channel whose type could not be read is treated as a text channel, and a forum that then refuses a plain message is a send that failed, which the next check tries again. Either way every message after the first — the session's analysis, the reminder, the warning, the outcome — goes inside, so a reminder three hours later is under the alert it is about. The thread id is in the state against the incident, which is how `hachiko notify` finds it without taking the lock, and once nothing is pending or waiting on that incident it moves to a list of closed threads, so the listener stops polling it, and stays there for a week: a wait can end before the session reports, when its question went away with the session, and the outcome it sends hours later still goes under the alert rather than opening a second post.

The forum's two tags are what makes it readable at a glance, and they are found by name on the channel Discord describes rather than by an id written down here: the ids are the forum's own, and one in the source would tag whatever a forum rebuilt from scratch happens to have in that slot. A post is opened tagged `Open`; the message that says the incident is over — `hachiko notify --outcome`, whose flag travels to the `--send` child as an argument with the thread and the channel, being one word and nothing of the incident's — takes `Open` off, puts `Resolved` on and archives the post, which closes it without locking it, so what is left open in the forum is what is still running. A tag the forum does not have is skipped rather than an error: the alert is the point, and the forum is Tim's to set up. The retag comes after the message and never before it, because Discord unarchives a thread anything is posted into; and it is reported rather than returned, since the message has already gone out and a label that would not go on may not reach the session as a report that did not send. The archive is nothing to the listener: Discord still answers a bot reading an archived post's messages, and by then the incident is closed, which has already taken its thread out of the list being polled.

`hachiko listen` is the half that reads. Its own LaunchAgent, `io.github.timche.hachiko-listen`, with `KeepAlive` because the poll is the job: a reply is worth seconds rather than five minutes, and a process sitting in a poll has no business holding the lock the sweep needs. It writes nothing the sweep owns — the threads it polls come from the state read-only, and what it remembers about them is files of its own. It re-enters itself under `op run` so the token is resolved once per start and not once per poll, which is what keeps a five-second loop off the service account's daily limit. Unconfigured, it exits at once and the plist's five-minute `ThrottleInterval` is what it costs: one start and one exit every five minutes, no network, no `op`, and a line in the log only when that state changes. It writes down what it last said so that turning the feature on or off gets a line and nothing else does — a line per start would be a line every five minutes for the life of the Mac about something that is not wrong.

While it is polling it writes a heartbeat into `~/Library/Caches/hachiko/listen/heartbeat` every half minute, beside what it already keeps there and in no file the sweep owns, and the five-minute check reads its age the way it reads the sweep's stamp and sync's. Only while it is polling, and the two ways it stops polling are not the same thing. With nothing in the config file nobody asked for replies at all, so it removes that heartbeat on its way into the idle state and the check reads the feature as off rather than as a listener that died ten minutes ago — which also gives an alert already open on it something that clears it. With a channel and a user set and only the token unresolved, somebody does mean replies to work: that is a listener which has stopped, so the heartbeat is left exactly where it is to go stale and be reported, and the ⚠️ points at `~/Library/Logs/hachiko-listen.log`, where the line it wrote on the way in says the token is what failed.

It also exits when the wrapper has built a new binary behind it, the way `hachiko sync` does, since neither has an interval of its own and nothing would otherwise run an edit to the listener until the Mac restarted. The exit falls between passes and never inside one: a pass that has taken a reply off Discord has already marked it seen, so one abandoned halfway through would drop the reply it was handing to the session. `KeepAlive` is unconditional here rather than `SuccessfulExit`, because both of the ways this listener exits on purpose are clean ones. `ThrottleInterval` counts from one start to the next rather than from the exit, so a listener that has been up longer than five minutes — which a configured one always has — is restarted at once; only a replacement inside the first five minutes waits out the remainder, which is the gap the heartbeat's ten minutes has to cover.

Every five seconds it asks each open thread for the messages after the highest id it has seen — an id and not a time, so a listener that was down for an hour reads what it missed. They come back sorted by snowflake, which is a timestamp, rather than reversed on an assumption about which order Discord sent them in: it documents newest first for a plain fetch and oldest first for an `after`, and guessing wrong hands the agent a conversation backwards and remembers the oldest id as the newest. Only messages whose author is the configured user count: everybody else in the channel is somebody who can see it, the bot's own messages are hachiko talking to itself, and an instruction to an agent with authority over this Mac comes from the one person who owns it. Every message is marked seen whether or not it could be acted on, or one Discord will not let the bot react to would be handled for ever.

A thread that will not answer — no permission on it, or Tim deleted it — is backed off, doubling from one poll to five minutes, and said once rather than every five seconds. One line when it stops answering, one when it starts again, and nothing in between: the same rule the rest of this log is written to, and twelve identical lines a minute would bury the ones that matter.

A reply reaches the session the same way everything else does, cancel-then-prompt, with his words fenced and the marker labelled as his rather than as incident data: the fence keeps an instruction out of a log line and keeps one in here, and the agent has to be able to tell the two apart. A bare number is read as the option he picked and said so in the prompt. It is the answer the standing orders were waiting for, so the clock stops on its own — the agent leaves `blocked` with nothing having recorded a nudge, which the next sweep reads as him having answered, because he has. An agent that is not on a question is prompted without an esc and the reply queues behind what it is doing. He gets a tick on his own message, or a line in the thread if the bot cannot react.

The never list still needs him, and a Discord account somebody has taken over is not him. So an action on that list needs a code as well: the session registers the one action with `hachiko approval-request <incident> <file>`, posts in the thread what it is asking to be allowed to do, and he replies `approve` with the six digits from his authenticator. The code is checked here — RFC 6238, SHA-1, thirty seconds, one step either side — against a secret the session is never given, and the approval it is told about names the action it registered rather than whatever it has decided since. One request, one approval, and the step a code belonged to is remembered and refused the second time, because a code is good for thirty seconds and would otherwise be good for all of them. Three wrong codes and the request itself is cancelled: six digits over three steps is about one chance in a thousand a try, which is hours rather than years for an account somebody has taken over, and that is no protection at all when what it reaches is deleting a repository. The session then has to register the action again, which it cannot do without saying in the thread what it is asking for, where Tim can see it. The count is against that action, so asking to be allowed something else starts from nothing. A code with nothing open to approve and a wrong code are answered with the same four words, since a hint is a hint to whoever is trying codes.

A post about an incident that is over goes three days after it was resolved (`HACHIKO_POST_KEEP`), which the watch does once an hour — housekeeping rather than watching, and it costs an `op run`. It is the one thing hachiko does that cannot be undone, so what may go is narrow and every part of it is read off Discord rather than off hachiko's own state: the post is in that forum, it carries the `Resolved` tag, it is archived — which is what closed means on a forum — and its archive timestamp is older than that. So an open incident is never touched, nor a post somebody reopened by writing in it, nor anything in a forum with no `Resolved` tag. Only the closed listing is read, since an open post cannot be resolved, and it is paged through to the end. A post Discord refuses to delete is one line and left alone: it would refuse again in the same way, and a retry loop would spend the sweep on one post. [shibuya](../shibuya/README.md)'s posts go the same way, being in the same forum with the same tags.

Setting it up: a Discord application with a bot, the Message Content intent turned on, invited to the private server with permission to read messages, send them, send them in threads, create public threads, manage threads, add reactions and read message history; a forum channel with an `Open` tag and a `Resolved` one; a `bot token` field and an `approval` one-time-password field on the `hachiko-discord` item in the `dev` vault; and the channel and user ids in the config file. `updates` beside them is a plain text channel for [the nightly update](#updates)'s summary, which is not an incident and has nothing to answer; without it that summary stays in hachiko's log. Manage Threads is the one that is easy to miss and the one that tags and closes a post — a post's tags are not something its own author may change without it. The `approval` reference is the field's own value rather than `?attribute=otp`, which is the current code — hachiko verifies codes itself, so it needs the secret, and it reads either the `otpauth://` URI or a bare base32 string, since which of them `op` hands back for a one-time-password field is 1Password's business rather than this one's.

## The worktree sweep

Cleaning up after a removed worktree is a garbage collector, `hachiko gc`, rather than a hook on the removal, because no removal reliably hands us one: herdr removes worktrees, so does Claude Code, so does `git worktree remove` by hand, git has no post-remove hook at all, and Claude Code's `WorktreeRemove` does not fire for a git worktree ([anthropics/claude-code#94212](https://github.com/anthropics/claude-code/issues/94212), open). Registering `WorktreeCreate` and `WorktreeRemove` would be the wrong trade even if it did: the docs say configuring them *replaces* Claude Code's own `git worktree` behaviour rather than adding to it, so a hook that cleaned up would also own creating the worktree.

So the trigger is time. Three of its six sweeps are about a worktree that is gone, and none runs unless it is: a compose project whose `com.docker.compose.project.working_dir` label points inside a worktree root that no longer exists, with `com.docker.compose.project.config_files` as the second opinion, removed with `docker compose -p <name> down -v --remove-orphans`; the named volumes that project left behind; and a process whose current directory is a removed worktree, SIGTERM and then SIGKILL ten seconds later. The label rather than `docker compose ls`, which reports the config files alone and so misses a project started with `-f` or from a file named something else. Inside a worktree root — `~/.herdr/worktrees/<repo>/<branch>` or `<repo>/.claude/worktrees/<name>` — and nowhere else, which is not the same as a folder that does not exist: a daemon shared with another machine reports projects whose working directory was never on this disk, and `down -v` on one of those deletes a database over a path that only looks missing. It never touches pid 1 or its own process tree, never signals a process another account owns, holds a `mkdir` lock of its own at `~/Library/Caches/hachiko-gc.lock` — not the watch's, so a sweep and a check never wait on each other — takes over a lock older than the interval or one whose holder has gone, and answers `--dry-run` by printing what it would do.

The volumes are the one thing no label can decide, because a volume carries only `com.docker.compose.project` and nothing about the folder: `repeek-main_postgres-data` is the main checkout's database, which looks exactly like a worktree's. So the sweep writes down every compose project it sees with a container inside a worktree root, and which worktree, in `~/Library/Caches/hachiko-gc/state.json`; a named volume no container is using goes only when its project is in that record and the recorded folder is gone. A project never seen running in a worktree is never touched however its volumes are named, an anonymous volume is never touched at all, and a record is forgotten once its worktree is gone and nothing of the project is left.

The other two are about a session that is over rather than a folder that is gone. Claude Code gives every session a scratch folder, `${CLAUDE_CODE_TMPDIR:-~/.cache/claude-tmp}/claude-<uid>/<project-slug>/<session-id>/`, and removes none of them, so the sweep removes one whose name is a session id, that no running session claims, and that nothing was written under for a week. Live is what `~/.claude/sessions/<pid>.json` says, by the pid in its name rather than by the record being there, since the record outlives the process. The week of grace is for `claude --resume`, which reuses the folder, and herdr resumes every session it had after a restart. A project folder goes with `rmdir` once the last session folder in it has, so anything else left in it keeps it, and anything not named like a session id is left alone — `bash-edit-diff` and `tasks` beside the session folders, `cc-socks` and `tart` a level above them.

The last is `git worktree prune` in every repository directly under `~/projects`, which is `HACHIKO_GC_PROJECTS` where a check needs it somewhere else. git's own prune rather than a rule of this script's: it drops the metadata of a worktree whose folder git cannot find and nothing more, so a session still working keeps its entry, and it reports what it pruned on stderr with `-v`, which is where each line of the log comes from. A `.git` directory rather than a `.git` file, since the file is what a worktree has.

The sixth is the one pass that is about nothing having been left behind, and the reason it is here rather than anywhere else: docker's build cache and the images nothing refers to grow whether or not a session ever ended, and neither of them goes when a worktree does. So `docker builder prune --force --filter until=168h` and `docker image prune --force --filter until=168h`, once a day (`HACHIKO_GC_PRUNE_EVERY`), with the age as docker's own `until` filter takes it (`HACHIKO_GC_PRUNE_AGE`, passed as written since the format is docker's to decide) — a week, because a layer from this morning is one today's build is about to want. Never volumes, never containers, never networks, which is why it is two commands rather than one `docker system prune`: a volume here is somebody's database and goes only by the rule above. And no `-a`, so an image a project still names by tag stays however long it has been since anybody built with it, the next build having only to pull it again.

Once a day rather than every ten minutes because the first prune of a day reclaims what the ones after it would have, and a prune walks every layer and cache record the daemon has: six an hour would be a hundred and forty subprocesses to be told nothing a hundred and thirty-nine times. When it last ran is in the sweep's own state, written to that file before either command runs rather than left to the save at the end of the sweep: these two are the longest-running thing the sweep does, and a sweep killed or timed out between them is exactly the one that never reaches that save and would prune again ten minutes later. One line in the log with the space each half got back, nothing at all where both got nothing, and the next prune is as soon as there is a daemon again where docker was down — being down spends no day. A prune that exits non-zero is a failure like the rest, with one difference: the nine sweeps an hour that did not prune are not sweeps where it has started working, so what is open stays open until a prune actually runs.

Routine cleanup is a log line and nothing else; what reaches the Discord channel is only what the sweep could not do — a compose down or a volume removal that exited non-zero, a process still there after SIGKILL, a folder that would not go, a worktree prune or a docker prune that failed. One message per distinct failure while it persists rather than one every ten minutes, with a 🟢 line in the same thread when it clears — sent as that incident's outcome, so the post is retagged `Resolved` and closed, and goes with the rest three days later — and the dedupe lives in the state file beside the record of the projects. Docker being absent or its daemon down is not a failure and says nothing at all: a Mac with OrbStack stopped has no containers to sweep.

A LaunchAgent runs it, `io.github.timche.hachiko-gc`, with `RunAtLoad` for what the machine lost while it was off and `StartInterval` 600, which is the whole of the trigger. There is no `WatchPaths`: it is not recursive, so a worktree at `~/.herdr/worktrees/<repo>/<branch>` is two levels below anything a watch on that root would see, and Claude Code's worktree roots are per repository, which no single path watches — a removal is caught by the next sweep rather than by a write. So the plist is a symlink into this checkout like the agents beside it, with `/bin/sh -c` exporting the PATH and opening the log before it `exec`s the wrapper, and `install.sh` loads or reloads it as it does the others. The log is `~/Library/Logs/hachiko-gc.log`, and a sweep that finds nothing writes nothing to it.

What the sweep cannot report is not running at all, so it writes the time it finished into `~/Library/Caches/hachiko-gc/last-run` and the five-minute check reads that stamp's age — over an hour, `HACHIKO_GC_STALE`, and one ⚠️ says so with the `launchctl kickstart` that starts it again. It is one of the three agents the watch checks the liveness of the same way; [hachiko](#hachiko) has how that reads and why nothing is said on a Mac with no gc plist.

## Auto-sync

[`hachiko sync`](#hachiko) gets everything written in the project docs upstream on its own: it commits, pulls and pushes `~/projects/docs` with nobody asking it to, which is what makes a note taken in one session readable from another device a minute later. Every repository `~/.config/hachiko/sync` lists is watched by the one process. The config is read once at startup, so another repository is one `repo =` line and a restart; `mode = dry-run` in it reports what each pass would do and changes nothing, which is how a change to sync itself is watched before it is trusted.

The second entry is this repository, and it is there for one folder: `paths = home/.claude`. The rest of it is committed and pushed by the session that changes it, as `CLAUDE.md` says, but the global `CLAUDE.md`, the settings, the skills, the agents and the hooks are written through the `~/.claude` symlink by Tim, by his tools and by Claude Code itself, outside any change anybody set out to make — so nothing commits them, and they sit in the tree being read by every session and published by nobody. A `paths =` line, repeatable and relative to the repository's root, is what makes a daemon on a tree a session also writes to safe: every command a pass runs against the tree carries those paths, which for `git commit` is git's own `--only`, so a change a session has staged elsewhere stays staged and out of the commit, one it has not staged stays where it was, and the subject names the synced files alone. Inside those paths the opposite holds, and deliberately: `--only` commits the working tree as it stands, so a file under `home/.claude` that somebody staged in part is committed whole. Those files are sync's, and half of one on the remote would be a file nobody wrote. A `repo =` with no `paths =` is the whole repository, which is the docs.

Three rules come with a limited repository. It does not pull and may not be told to: `git pull --rebase --autostash` stashes and reapplies the whole working tree, which is precisely the work outside those paths that this exists to leave alone, and git has no pull a pathspec can narrow — so `fetch_interval` does nothing, nothing ever rewrites the tree, and a rejected push is a failure posted to Discord rather than something to rebase. It syncs on one branch, the one its own `refs/remotes/origin/HEAD` names, read once at startup: a commit on a branch somebody checked out here would carry files that are nobody's work in progress onto it and the push would publish that branch, with nothing to bring them back. And a push publishes the branch rather than a commit, so sync marks its own commits with a `Synced-by: hachiko sync` trailer and pushes only when there is one of them waiting, counting the push delay from the oldest. A session's commits are never what starts a push — one it is still shaping would be published, and one it then amends or squashes is one it can no longer push without forcing — but they do go up underneath sync's when it has something of its own to send, which is how a session's work reaches the origin without it having pushed. A repository synced whole, which is the docs, pushes every unpushed commit on the branch as it always has. A tree sync may not commit in — mid-rebase, mid-merge, or on another branch — is left alone with one line in the log saying why, said once rather than once a second.

Two minutes of quiet rather than the docs' five seconds before `home/.claude` becomes a commit, and then the same minute's push delay. The Mac reads those files through the symlink the moment they are written, so what goes to GitHub is the history rather than the live copy: a session's run of edits across `CLAUDE.md` and `settings.json` lands as one commit, and a `settings.json` caught half-written is that much less likely.

It runs as a LaunchAgent labelled `io.github.timche.hachiko-sync`:

```sh
launchctl print gui/$(id -u)/io.github.timche.hachiko-sync         # loaded, and what launchd makes of it
tail -f ~/Library/Logs/hachiko-sync.log                            # why something did not land
launchctl kickstart -k gui/$(id -u)/io.github.timche.hachiko-sync  # after editing the config
hachiko sync --once                                                # one pass in the foreground: sync now
```

The agent is a symlink into this checkout like everything else, which launchd accepts: it resolves the link when the job is bootstrapped and reads the file behind it. It has nothing to render because it names no path of its own — launchd expands neither `~` nor `$HOME` inside a plist, and a `$HOME` in `StandardOutPath` is an `EX_CONFIG` failure at load with nothing anywhere saying which key was wrong, but launchd does hand a gui-domain agent a `HOME`. So `ProgramArguments` is `/bin/sh -c`, and the shell exports the PATH and opens the log before `exec`ing the wrapper: the PATH because launchd hands a job almost none and every pass shells out to git, and `exec` because the status `KeepAlive` reads has to be the daemon's rather than the shell's. Nothing else is exported, these commits being signed from the key file `~/.gitconfig` names. There is no `WatchPaths`, the one key that would have to arrive absolute, because it polls `git status` itself rather than being woken by a write. `test/sync-agent.sh` proves all of it against launchd itself, under a label of its own and with a stand-in for the wrapper, because an assert that only reads the file passes on a plist launchd would refuse.

Each repository is asked once, before any pass, where it really is, whether it is a repository at all, and — for a limited one — which branch its own `origin/HEAD` names. One that cannot answer is left out with a ⚠️ of its own and the daemon runs the rest, because these are separate repositories and an `origin/HEAD` nobody set on one is no reason for the others to stop being published; only a config where not one repository could start is one the daemon exits on. It is read at startup, so a repository that has been fixed is picked up the next time sync starts, which an edit to `hachiko/` already does.

`install.sh` loads it with `launchctl bootstrap gui/$(id -u)`, once `~/projects/docs` is a clone — a Mac whose clone failed is left unsynced rather than restart-looping — and boots an already-loaded one out and back in when the plist has changed, since `kickstart` restarts the job from the copy launchd read rather than re-reading the file and a changed plist would otherwise wait for a reboot. The agent being a link, comparing the target across the bootstrap would say nothing — what the link points at is a file a pull already changed — so `install.sh` keeps a copy of the definition the daemon was last loaded from under `~/.local/state/mac-mini/`, written only once the load succeeded, and compares against that. A daemon that fails on every start retries every ten seconds for as long as the Mac is up, `KeepAlive` and `ThrottleInterval` being the whole of what a LaunchAgent can say about it, and the log is the only place that shows. It also exits non-zero on purpose when the wrapper has replaced its binary, so `KeepAlive` is what puts the new one in.

The subject is written by a model: `subject_model = haiku` in the config, through the Claude Code already logged in on this Mac, so a commit says what changed rather than which files did. It is handed the staged diff of exactly what is about to be committed — capped at 16 KB with the `--stat` above it, so a diff cut off halfway still names every file — and the repository's last ten subjects as the house style, and it answers with one line. An alias and never a pinned model id, which is a model that one day stops answering. The call is isolated because a diff is somebody's text rather than instructions: no tools, no MCP, no skills, none of the account's own customisations, a working directory that is nobody's project, nothing left on disk, and a minute's deadline of its own. The only thing its answer can become is a subject, and that is taken as the first line that says anything, stripped of what wraps it and refused when it is too long to be one. Anything else — a failure, the deadline, an empty or overlong answer, or no model configured at all — is `Update a.md, b.md` as before, with one line in the log and nothing to Discord, because a subject is cosmetic where the work landing is not. A dry run asks nothing of it.

Five seconds after the last write to a watched tree, a burst of edits lands as one local commit, subject `Update a.md, b.md` and a count once there are more than three files where no model wrote one. The commit comes before the rebase, so a pull runs over a checkpoint rather than over a dirty tree. The push waits for `push_delay`, counted from the committer time of the oldest commit in `@{upstream}..HEAD` and read from git on every pass, and then takes everything unpushed at once: a minute for the docs, long enough that a burst of notes goes up as one push and short enough that nobody reads a stale page for long. A steady stream of edits cannot postpone a push past its delay, a held pass still pulls, and a tree is left alone while `HEAD` is detached or a `MERGE_HEAD`, `CHERRY_PICK_HEAD` or `REVERT_HEAD` exists, because a commit there would land inside somebody's rebase or merge. An `index.lock` is a race rather than a fault, because a session in the same tree runs git a few times a second and holds the index for a fraction of one: a pass that meets one does nothing and the next one a second later finds it gone, and only a lock still there a minute later is reported — which is the shape of one a killed git left behind, and nobody's to remove but Tim's. A push is retried with exponential backoff and a bounded number of attempts; one rejected is rebased once and pushed again, and a rebase that conflicts is aborted rather than retried. The fetch interval is the only way another machine's writes arrive, and the recheck is what retries a push on a pass with nothing written. What it means while editing is in `CLAUDE.md`.

It polls `git status` every second rather than watching the tree, which is what a recursive watcher could not do without cgo and could not do cleanly either: a watcher cannot exclude `.git`, so every pass's own writes to the index arrive as events to be filtered out by path, and `git status` already answers what changed with `.gitignore` applied, in under ten milliseconds on a repository of this size. A loop that polls also needs no timer arithmetic — the fetch interval, the recheck and a push deadline are each a comparison on the next tick. And there is no lock: launchd runs one of these at a time, git's own `index.lock` keeps two gits out of one repository, and a lock held for the life of the process would make `--once` a no-op. A repository's loop that dies takes the process down non-zero rather than looking alive and watching nothing.

A failure goes to the Discord channel every other hachiko message goes to: one ⚠️ per distinct failure while it persists and a 🟢 in the same thread when it clears, the same shape as `hachiko gc`'s, with a fetch that fails while there is nothing to push not counted as one. A rebase conflict pauses pulling for that repository and re-arms itself — sync records the local `HEAD` and the upstream ref as they were at the conflict and resumes the moment either one moves, which is anything Tim could have done to fix it.

An agent lives in a GUI login session, so what keeps sync running with nobody at the Mac is the Mac logging itself in, by auto-login or by whoever unlocks FileVault, plus `pmset autorestart` to bring it back after power loss. Until a session exists there is no `gui/<uid>` domain to load the agent into, so an `install.sh` run over SSH against a Mac sitting at its login window says that and leaves the agent unloaded.

What watches it is the five-minute check, through the one liveness check that also watches the worktree sweep and the Discord listener. Sync writes a heartbeat every half minute — the oldest of its repositories' own ticks, so a loop wedged on something no timeout caught stops it advancing — and the check posts when that is over ten minutes old, only once the sync plist is there. With sync alive and reporting nothing wrong it also reads each repository in the config: a commit more than half an hour past its own `push_delay`, or a tree dirty for over ten minutes, is one message and a 🟢 when it catches up. Both readings carry the repository's own pathspec, because what is not sync's to commit is not sync's to be behind on — a session's work left uncommitted all afternoon in this checkout, or a commit of its own waiting to be pushed, is not a sync that has stopped. `HACHIKO_SYNC_STALE`, `HACHIKO_SYNC_LATE` and `HACHIKO_SYNC_DIRTY` are those three thresholds.

## Updates

Nobody is at this Mac, so it keeps itself up to date: `hachiko update` moves its tooling forward once a night and deals with what each upgrade leaves behind. It is the one thing here that moves a version. `install.sh` deliberately does not — it applies the `Brewfile` with `--no-upgrade` and installs mise's tools `--locked`, which is what makes a re-run after every pull safe — and mise holds a release back for its default day: the global config sets no `minimum_release_age`, so `mise up` and `mise self-update` alike take a version once it is 24 hours old, which is long enough for a broken or hijacked release to be pulled and short enough that the Mac is never more than a night behind. A version a lockfile records is installed as recorded, however new.

Those 24 hours are counted from the release date as the index mise reads states it, which is not always a moment. node's `https://nodejs.org/dist/index.json` dates every release by day alone, so a release cut at 23:00 is dated midnight that morning and is eligible an hour later; the same hold on a Homebrew formula or a GitHub release, which carry a timestamp, is the whole day. So the hold is a day for most of this Mac's tooling and as little as an hour for node, and what `hachiko update --security` bypasses with `--minimum-release-age 0d` is already weak there.

The five-minute [hachiko](#hachiko) agent starts it rather than a LaunchAgent of its own, since an agent that fires once a day skips the day on a Mac that was asleep at four in the morning. So the schedule is a stamp in a state directory of its own — past 04:00 local (`HACHIKO_UPDATE_HOUR`), and the last run that finished was before 04:00 today — and a Mac that was off or asleep catches up on its next check instead. What the check starts is a process of its own: an upgrade takes tens of minutes, the check it would otherwise run inside has five, and [shibuya](../shibuya/README.md) reports a Mac offline a quarter of an hour after its last check-in, so an update held inline would page Tim about a Mac that is busy updating. A lock of its own keeps the next check from starting a second one, and one left behind by a run that was killed is taken over after two hours — or at once, where the pid the lock records is no longer running, since a lock is held by a process rather than for a span of time and the age is only the stand-in for asking it. The age rule stays for a pid that still answers, because pids are reused and one that answers may be somebody else's process entirely.

The steps, in order, each of them reported:

- **mise**, with `mise self-update`, since mise comes from its own installer and nothing else on this Mac can move it.
- **The tools mise manages**, with `mise up` for the global config and again with `--local` for this repository's own `mise.toml`, each naming its directory because mise decides what is active from the directory it is asked about and a LaunchAgent starts in `/`. What moved is read off `mise outdated` either side of the upgrade rather than off what the upgrade printed.
- **The lockfiles that rewrote**, committed and pushed to `main`. `~/.config/mise/mise.lock` and `~/.config/mise/locks` are symlinks into this checkout, so upgrading the global tools writes this repository's own files, and a lockfile left on the Mac would mean a rebuilt Mac installing whatever `latest` meant on the day. Every git command is limited to those paths and `mise.lock`, so nothing a session has staged or left dirty here is added, committed or pushed; and nothing is committed at all unless `main` is checked out and the tree is nobody's to finish, since a commit on a session's branch would go up inside their pull request.
- **portless's proxy daemon**, through [the root helper](../README.md#the-root-helper), when node or portless moved. The daemon is root running a path with a version in it and launchd reads its plist once, so a `mise up` that moved either leaves root running a file that is gone — and with it every `.localhost` and `.timche.dev` URL on this Mac.
- **Homebrew**, with `brew update`, `brew upgrade` for formulae and casks, and `brew cleanup`. A cask that will not upgrade stops `brew upgrade` partway, so what moved is read off `brew list --versions` either side of it. The cleanup is the one failure worth expecting: `sudo brew services start` takes root ownership of the keg it runs tailscaled out of, so the first cleanup after a tailscale upgrade meets a root-owned directory — and the message names the one `sudo rm -rf` that clears it.
- **tailscaled**, restarted through the root helper when its formula moved, because launchd reads a plist at bootstrap and the plist names the `opt` symlink rather than a version. Then `tailscale status --json` is read back for up to a minute, and a backend that is not `Running` is an incident: this Mac is reached over the tailnet.
- **herdr**, with `herdr update`, for the reason mise is its own: the update replaces the binary it runs from. The server is left alone — restarting it ends every session on this Mac — and it takes the new binary whenever it next starts, which the summary says.
- **oh-my-zsh**, with `git -C ~/.oh-my-zsh pull --ff-only`. A clone that cannot fast-forward has somebody's commits in it, and merging them is not a decision to make at four in the morning.
- **macOS**, which is the one it only reports. `softwareupdate --install` of a macOS update on Apple silicon wants a volume owner's password — `--user` with `--stdinpass`, both documented as Apple-silicon-only — and this Mac has no MDM to authorise one in its place. Nothing here may hold Tim's password, so `unattended.sh` leaves macOS downloading updates and not installing them, and the summary says what is waiting for him.

What moved goes to the `updates` text channel as one summary, and a night where nothing moved says nothing at all, the way the rest of hachiko does; without that channel configured the summary stays in `~/Library/Logs/hachiko.log`, which has the whole of every run either way.

A step that failed is an incident in the forum every other alert goes to, with [an on-call session](#the-on-call-session) on it — and the update posts nothing about one. It records what it is failing on, and the next five-minute check raises it: one post per incident, with the thread, the session, `hachiko notify`, Tim's reply out of Discord, the raw details if nothing reports and the reminders all belonging to the half of hachiko that already has them. All of one run's new failures go in one incident, kind `update`, because they are one night's news and one session's reading; a step that keeps failing is raised once and no more, since it fails again every night and nightly messages about it are ones Tim stops reading. The line saying a step works again is the update's own, because it is the only thing that ever knows one does, and it goes into that post's thread as the incident's outcome, which closes it.

The hand-off is two files, each with one writer, because the two hold a lock each and an update holds its across however long brew takes. `~/Library/Caches/hachiko-update/failing.json` is the update's: a statement of which steps are failing and since when, with the phrase, what the command said and the one line for Tim, rewritten whole on every run. `~/Library/Caches/hachiko/update-raised.json` is the check's answer: which incident each of those steps was raised as, and the thread of its post. So the check raises what is in the first and not yet in the second, the update reads the second for the thread to clear into, and a step that leaves the first is one nobody is waiting on any more — which is what ends the wait on its incident. A Discord that was down all day loses nothing, since neither file is a queue.

`hachiko update --security <thing>…` is the out-of-cycle run, and the upgrade is here rather than beside whatever named the advisory because of the rule above: the update is the one thing on this Mac that moves a version. Only those things and nothing else that happens to be outdated, since a night's run is a decision about keeping the Mac current and this is a decision about one fault; `--minimum-release-age 0d` on the mise steps, because the day a release is held back for is there so that a hijacked one can be pulled, and that trade is the wrong way round for a version that fixes something already published. A target is matched against five shapes — `mise:<tool>`, `brew:<formula>`, `pip:<python>:<package>`, `mise-self`, `herdr` — and refused otherwise, both where it is built and again where it runs: every one of those names arrived from an advisory feed and ends up in a command line.

Such a run is answerable for two steps and no others, which is what keeps it out of the night's hand-off: a security upgrade that attempted neither `brew update` nor `mise up` says nothing about either, so a step the night is failing on keeps its record and its incident rather than being read as fixed. It writes no last-run stamp either — the stamp is what says a night's run happened, and one written at noon would mean no nightly run that night. It takes the night's own lock, so the two can never move a version at the same time, and the summary reads "Security update" rather than "Nightly update" and goes out even when nothing moved, because something asked for it.

`hachiko update --dry-run` is the explicit "what would move", and takes the readings without changing anything. `hachiko update` is the explicit "update now", for a session that has been waiting on a fix upstream rather than on four in the morning.
