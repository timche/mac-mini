# claude-hooks

`claude-hooks` is the binary every Claude Code hook on this Mac is a subcommand of, so that one build, one cache and one wrapper serve all of them. They are `guard` and `strip-attribution`, both `PreToolUse` on `Bash`, `project-docs`, which runs at `SessionStart`, and `track-session`, which runs at `SessionStart` and at `SessionEnd`. Two more are here for the same build and the same freshness check and are no hooks at all: `statusline`, the `statusLine` command, in [The usage reading](#the-usage-reading), and `resume-session`, a line of the interactive zsh startup, in [The session a terminal comes back on](#the-session-a-terminal-comes-back-on).

`claude-hooks guard` is the `PreToolUse` hook on `Bash` in every Claude session on this Mac. It reads the command a session is about to run and refuses the two kinds that reach out of the session that ran them, each because many sessions share one machine:

- **A kill by name, pattern or port.** Each session runs its own copy of the same dev server in its own worktree, so a process named by its name, a pattern or the port it listens on is every session's copy of it: a `pkill -f portless` meant for one session's server stopped another's. A kill is allowed by pid alone, and a pid read off `pgrep`, `pidof`, `lsof`, `fuser`, `ps`, `netstat` or `ss` is a pid chosen by name or port all the same.
- **Taking the Mac's one foreground without the lock.** The GUI session has one frontmost app, one key window and one pointer, so `cliclick` and an `osascript` that sends a System Events keystroke, raises a window or clicks the screen reach whatever another session has in front. Those run under [`focus-lock`](../../home/.local/bin/focus-lock), which serialises them, and this refuses them outside it. What reaches an app without the foreground — CDP, `perform action "AXPress"`, UTM's `input keystroke`, VNC — is left alone, which is why the check reads what a script does rather than refusing `osascript`. `$PROJECT_DOCS_DIR/shared/macos-gui-automation.md` says which call is which.

`claude-hooks strip-attribution` keeps Claude's attribution off GitHub, which git's own hooks cannot reach. A pull request, issue or comment body goes from `gh` straight to GitHub and never passes through `commit-msg`, and Claude Code's attribution setting only changes what the model is asked to write. So the attribution comes out of any `gh` command, and of any body file that command names — `--body-file`, `-F`, and on `gh api` a `--field key=@path` or an `--input` — before the command runs. Rewritten rather than refused, since a refused command is one an agent retries and works around.

What it does refuse is `--no-verify` on a commit or a push, and `-n` on a commit, which is the same flag there: both skip the `commit-msg` and `pre-push` hooks that keep the attribution off a commit, and the repository's own `pre-commit` with them. On a push `-n` is `--dry-run` and goes through. A permissions deny rule would not do this, since it matches only a command that starts with `git push`, which `git -C <dir> push` and a `cd … &&` chain are not.

Which command a word belongs to is read rather than matched, so `git commit -m "add a --no-verify guard"` is a message and not a flag, a `gh` in a heredoc body is a line of the file being written, and the only path written to is one a `gh` command named itself, resolved through a `VAR=…` the same line set and never through the environment.

It is a compiled binary rather than a script because a hook that cannot run is a hook that is silently off: a Python that a mise or a Homebrew upgrade moved takes the hook with it and nothing in a session says so. This depends on a kernel and nothing else.

## The commands

Each of the two `PreToolUse` hooks reads the hook event as JSON on stdin and prints a deny decision — `hookSpecificOutput`, `permissionDecision` `deny`, and the reason the refusing check gives — or nothing at all, which is how a command is allowed. `strip-attribution` has a third answer: an allow carrying `updatedInput`, the tool input back as it came with the command rewritten, which is what Claude Code then runs. Both exit 0 whatever they answer, and 1 when called wrong; never 2, which is how a `PreToolUse` hook blocks a command, so no bug here can cost a session its shell.

An event neither can read is allowed, and so is a command `guard` cannot read: `internal/shell` splits a command the way Bash would — quotes, `$()`, backticks, process substitutions, redirects, heredocs, `bash -c`, the prefixes that run another command such as `sudo`, `env`, `xargs`, `timeout`, `npx`, `bunx` and `uvx`, and what follows `--` in `mise exec` and `op run` — and an unterminated quote, an unclosed substitution or a nesting deeper than anyone writes comes back as unreadable. A guard on every session's shell that refused what it could not parse would cost them all their shell. So a `pkill` in a commit message, a grep pattern or a heredoc body is an argument and goes through, and `internal/killbypid` and `internal/focus` decide only on a word a shell would run as a command.

`internal/attribution` reads the same command the same way, and falls back on a command it cannot read to matching the whole line as text: a skipped hook is refused and the attribution comes out of the command, but no file is touched, since a path read off a line nobody can split is not a path that command gave `gh`.

## The docs a session starts with

`claude-hooks project-docs` prints `~/projects/docs/shared` and the `~/projects/docs/<owner>/<repo>` folder that belongs to the project the session is in, each as a path followed by its top-level `*.md` files and its subdirectories as a name and a count. Stdout from a `SessionStart` hook is injected into the session context, so finding the docs is a mechanism rather than a rule the global CLAUDE.md asks a session to remember. It reads no event and answers nothing: whatever it could not read — a docs root that is not there, a directory the account cannot open, a git that will not answer — is a line the listing does not have, and it exits 0 either way.

Which folder belongs to the project is the `<owner>/<repo>` its `origin` remote names rather than the directory's name, since a worktree is named for its branch while every branch shares one docs folder; a repository with no remote falls back to the last two components of the directory its main worktree is in, a checkout sitting at `~/projects/<owner>/<repo>`. A checkout's own `docs/` is the project's published documentation rather than its working docs, so it is never looked at, and a project with no folder is not mentioned at all — otherwise every session on every other project would start with an apology.

`internal/collate` is why the order is what it was when this was a `find | sort` pipeline rather than Go's. `sort` in a session's locale compares case-folded, which puts `README.md` among the r's, and gives the punctuation a name is broken up with weights that are not ASCII's, which puts `mac-mini.md` before `mac.md`. Sorting by bytes instead would rewrite a listing in the context of every session for nothing.

## The session a terminal comes back on

Every Claude Code session on this Mac is a program inside a herdr-core terminal, almost always `claude` typed into that terminal's login zsh. A core that stops parks its kept terminals, and the next core start gives each one a fresh login shell in the folder it was last in — the program it lost is never re-run. So after a reboot every session is still on disk and nothing says which terminal it belonged to, and finding out means reading transcripts to work out which tab was on which. herdr-core will do this itself once OSC 7501 carries a resume reference ([herdrdev/herdr-core#15](https://github.com/herdrdev/herdr-core/issues/15)); this is the stopgap until then, and it comes out when that ships.

`claude-hooks track-session` is the recording half, registered for `SessionStart` and `SessionEnd` both. On a start it sets two labels on the terminal — `claude.session`, the session's id, and `claude.cwd`, the folder that session was working in rather than the folder the terminal is in, so a session resumes where it was. Every `source` relabels, `clear` and `compact` included, each of which leaves the terminal on a session with a new id.

What it will not record is anything but the one Claude the terminal is sitting at:

- **A terminal whose own program is `claude`.** hachiko creates those for on-call and for mochi, and replaces the program itself after a core restart, so the shell recovery this is written for never happens to them. The terminal's `argv` being a shell is what says a session was typed in, and so is a shell's to type again.
- **A Claude nested inside another.** A `claude -p` a Bash tool started is a session like any other and fires the same hooks. Claude Code sets `CLAUDE_PID` to its own process, so the test is that pid against the terminal's `foreground.pid`: the Claude in front of Tim matches and nothing underneath it does.

On an end the labels come off, but only for `prompt_input_exit` and `logout`, the two reasons that mean Tim asked for it, and only when the label names the very session that is ending. `clear` and `resume` are each followed by a `SessionStart` that relabels, and `other` is everything else — a reboot and a core stop arrive as `other`, which is the one case this whole arrangement exists for. A session that dies with no hook run at all, from a `SIGKILL` or a crash, leaves the label in place, which is the same answer.

`claude-hooks resume-session <pid>` is the other half, and the only command here a shell runs rather than Claude Code. `home/.zshrc` asks it, with the shell's own pid, and runs `claude --resume` on the two lines it prints, the session then the folder. It answers nothing — and so leaves a shell a shell — when:

- there is no `HC_TERMINAL_ID`, which the zsh block checks before it so much as finds the binary, so a shell outside a terminal of one pays nothing;
- the pid it was given is not the terminal's own `pid`, which is every nested zsh and every shell of Claude's own: one of those resuming would take the session off the shell that is already on it;
- there is no label, which is a terminal nobody has run Claude in and one whose session was deliberately ended;
- the session has no transcript left, which `--resume` would open an empty window on. Which project folder it is under is a glob rather than a slug this would have to spell the same way Claude Code does.

Two plain lines rather than anything the shell would evaluate, and a session id checked against the shape Claude Code writes before it reaches either the glob or the shell, because what is printed comes out of a label and a label is written by whoever can reach the core.

The zsh block runs once per shell by construction: claude exiting leaves the shell at its prompt without re-reading `.zshrc`. The one case the pid cannot tell apart is an `exec zsh`, which keeps the pid, so the block exports `_CLAUDE_RESUMED` before it runs claude — a session already resumed once is not that shell's to take again.

## The usage reading

Every Claude Code session on this Mac spends one account's 5-hour and 7-day usage limits, so running out of them is the ceiling on how much work can be going at once — and the only place Claude Code says how close that is, is the status line's event: `rate_limits`, a `used_percentage` and a `resets_at` per window. There is no API here that may be asked instead.

So `claude-hooks statusline <command>` is the tap in front of whatever draws the line: it writes `rate_limits` as it arrived, with the time it was read beside it, to `~/.hachiko/state/usage/latest.json`, and then runs `<command>` with the same event, handing back its stdout, its stderr and its exit status untouched. [hachiko](../hachiko/README.md)'s five-minute check is what reads that file and says in Discord that a window is nearly spent. The object goes in verbatim because the shape is Claude Code's and documented, and which windows matter is hachiko's — a format described on both sides would be two descriptions of one file. `HACHIKO_USAGE_STATE_DIR` is hachiko's own variable and moves the file for the writer and the reader together.

It is a command here rather than in hachiko because of where it runs: on every draw in every session, several times a minute. This is the binary a session already runs directly, which checks its own sources rather than paying for a shell, a `find`, a `shasum` and a `mise` in front of each run.

Everything it does of its own is silent. The line is redrawn for as long as a session is open, so an event that carries no `rate_limits` — which is every event until a session's first API response — leaves the last reading where it is, and a state directory that cannot be written, an event that will not parse and a rename that fails are each nothing at all. What Tim sees is the drawing program's output and no more, and Claude Code says nothing about a `statusLine` command that fails, which is why the exit status is that program's rather than anything of the tap's.

## How it is wired

`home/.claude/settings.json` registers the two `PreToolUse` hooks once each for every Bash command, with no `if` filter, `project-docs` once for every `SessionStart`, `track-session` once for every `SessionStart` and once for every `SessionEnd`, and `statusline` as the `statusLine` command, with mise's `ccstatusline` shim as the program it draws through. A filter would be a second list of the programs a hook reads, kept in step by hand with the first, and Claude Code's matching sees through only its own fixed set of wrappers, so any runner missing from the filter would be a command that hook never saw. The timeout is 130 seconds on a Bash hook, since a rebuild runs inside it and the wrapper's two steps may take sixty each, and 10 on the others, each with a session waiting on it — on `SessionEnd` that 10 is also what raises Claude Code's own budget for the event, a second and a half by default, above what reaching the core can cost.

`home/.zshrc` runs `resume-session` the same way the hooks are registered: the built binary, with the wrapper behind it for a cache that has none, so the handoff keeps an edit live there too.

What it registers is the built binary, `~/Library/Caches/claude-hooks/claude-hooks`, and the wrapper that builds it only when there is none: a shell, a `find`, a `shasum` and a `mise` before every Bash call in every session cost several times the check they are there for. So keeping an edit live is the binary's own job. The wrapper writes the folder it built from, and its own path, into the binary at build time; the binary, before it reads the event, compares the times of that folder's `*.go`, `go.mod` and `go.sum` and of the folders themselves — a deletion or a rename shows on the folder alone — against the newer of itself and `attempted`, and execs the wrapper with the event unread when the sources have moved. What answers the command is then a build of the sources as they are now. `CLAUDE_HOOKS_FRESH` says that handoff has happened, so there is only ever one.

## Setup, state and logs

Nothing to install: `mise.toml` links `home/.local/bin/claude-hooks` into `~/.local/bin`, and that entry builds the binary into `~/Library/Caches/claude-hooks` over the `home/.local/libexec/build-tool` every Go tool here shares, whose header has the arrangement. What is claude-hooks' own is the sixty seconds a step, which leaves room for a build and a whole test suite compiled from an empty Go cache on a machine many times slower than this Mac, the two source paths written into the binary, and that it is the tool the attempt-once rule was written for. A wrapper run from a linked worktree builds into `~/Library/Caches/claude-hooks/worktrees/<name>` instead, since the hook runs the default cache's binary and that binary follows the sources it was built from. Sources whose times moved but whose contents did not are not rebuilt, and the wrapper touches `attempted` so the binary stops handing off. The wrapper's one-line failures go to the session's stderr, which Claude Code reports as a hook error; there is no log file.

The state is the binary and `attempted`, which holds the hash of the sources at the last build attempt whether that attempt worked or not, and in its time when it was made. So a tree that does not compile is built once rather than before every command the session runs while it is fixing it, and the binary has something to measure the sources against. A cache with no binary in it is built from whatever `attempted` says, that being the one case where the hook reaches the wrapper at all.

`CLAUDE_HOOKS_CACHE_DIR` moves the cache, which is how a session tries a change without touching the one every other session is running.

## The tests are the specification

What the guard refuses is what `internal/killbypid` and `internal/focus` refuse in their tests, case by case, and what `strip-attribution` refuses, rewrites and leaves alone is the table in `internal/attribution`, each case a command a session really ran. What the tap keeps, passes on and stays silent about is `internal/statusline`, over a stand-in for the drawing program that records the event it was handed. What a session is told about its docs is the table in `internal/projectdocs`, a docs root and a repository per case, and the order those names come in is `internal/collate`'s, each of its cases an order `sort` itself produced. Which terminal is labelled with which session, and which shell is told to come back on one, is `internal/resume` — a terminal and an event per case, over a core behind an interface, with the commands the real core is sent read off a stand-in `hc` that records its arguments. `test/assert.sh` checks only that the binary is linked, that every hook the usage names is registered as the command above and for every event it answers, that each answers, that the `statusLine` is the tap in front of mise's `ccstatusline` and draws a line with the reading written, that the zsh startup asks `resume-session` and is left a shell when it answers nothing, and that an edit reaches a session: the handoff, a tree that does not compile, and a cache with no binary in it. A new way of killing by name, of taking the foreground or of sending a body to GitHub is a case in a table, not a line there.
