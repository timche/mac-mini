# mochi

`mochi` is Tim's own Claude Tag for Discord. He replies to a message in a server mochi is in and mentions it with an instruction; a Claude Code session starts on this Mac, in that server's herdr workspace, with the lead workflow, his instruction and the conversation around it, and he carries on in herdr. It is a tool of its own rather than a hachiko command, because hachiko is scoped to looking after this Mac: a Go module in `mochi/` with its own wrapper in `~/.local/bin/mochi`, built the way [Layout](../README.md#layout) describes, its own LaunchAgent `io.github.timche.mochi` and its own log `~/Library/Logs/mochi.log`. The one link between the two is the heartbeat below.

Everything Discord goes through [`discord/`](../README.md#layout), the repository's own client on the standard library alone, with resuming and rate limits handled there, its own tests the statement of it.

## Configuration

`~/.mochi/` is mochi's folder in `HOME`: the config and the token's references are links into it from this repository's `home/.mochi/`, and everything mochi records about itself is in it — the marks, the sessions it is running, the questions it is waiting on, the heartbeat, each session's attachments. Only the build output is elsewhere, in `~/Library/Caches/mochi/`, where the wrapper puts it and where a folder macOS may clear holds nothing but a binary that can be built again. A command that finds state left in that folder takes it over on its way in, under a lock of its own and never over a file the new folder already has.

Who and where is `home/.mochi/config.json`, linked to `~/.mochi/config.json`. `user` is the one Discord account whose mention does anything. `server` is a list with one entry per server mochi is in: `guild`, the server's id; `workspace`, the herdr workspace the session's tab goes in, found by that label and made when there is none; `repo`, the checkout the tab starts in, so the session has that project's instructions loaded; and `split`, the `model` and `effort` of the classifier below, `sonnet` at `medium` when left out. Every id is a snowflake as a string, copied from Discord with Developer Mode on. None of it is a secret — a user id is on Tim's own profile and a guild id in every message's URL — so it lives in the repository rather than 1Password; the bot token, which is, is a reference in `mochi.env.op` beside it.

What is a project's own lives in `.mochi/` at the root of its repository, so a session changes it like any other change and it applies once merged into the main checkout. `.mochi/config.json` holds `forum`, a forum channel's id, so a session started from a channel gets a post there rather than a thread on Tim's message; `announce`, the channel `mochi announce` posts to; and `links`, what a post may link to — a domain, which covers its subdomains, or an entry with a scheme in it, allowing that one exact address, such as `chrome://extensions`. `.mochi/instructions.md` holds standing instructions for mochi's sessions in that repository alone, which ordinary sessions never load. Both are read at every use from the mapped checkout, as regular files that stay inside the repository once links are followed; a channel Discord does not put in the mapped server is refused, as is a file with an unknown key or an id that is not a snowflake, and `mochi/internal/project` and its tests are which shapes are refused. A broken one is logged and counts as none for that use, and with none the forum, the announce channel and the links are each off. A mapped repository with no `.mochi/config.json` at all is logged once, so a forum that is missing for that reason shows in the log.

## What a mention does

A mention is of mochi's user, `<@id>` or `<@!id>`, never of a role, mochi's own included: a role mention stays in the instruction as text. A mention in a server with no entry is ignored, as is every author but the configured user, bots included: what anybody else wrote reaches a session only as fenced data, and only his words arrive as an instruction.

What a mention gathers depends on where it is: the discussion a moderator's suggestion gets is mostly plain messages rather than replies, and no fixed window of the latest holds it. A reply in a channel gets the replied-to message, its reply chain upward, about fifty messages either side and any later reply to it; one inside a thread or forum post mochi did not open gets that thread from its starter; one that replies to nothing gets the channel's last fifty. It arrives in two labelled sections, FOCUS and then SURROUNDING CHANNEL, marked as possibly unrelated; a prompt too large to paste loses the oldest of the second, never the first. Every attachment is downloaded into `~/.mochi/sessions/<thread>/`, outside any repository, and listed by path beside its message, because Claude reads an image from a path and Discord's attachment URLs expire; 25 MB a file and 100 MB a session.

One mention can start several sessions: "research a, b and c separately" is three, and Claude decides that rather than a rule about the wording. Before a new session mochi runs one headless `claude -p` with no tools and no settings and a minute to answer; it sees Tim's instruction and the message he replied to, fenced, and answers with a decision — one session, one per item, or ask — a title and kind of work for the whole, and each item as a title and a self-contained instruction. `mochi split-eval --model <m> --effort <e> < cases.jsonl` scores JSON-lined cases (`{"instruction":…,"replied":…,"want":N}`, `"decision":"ask"` for one that should be asked about) through the same prompt, schema and flags, which is how the model in `split` is chosen. One task, or any failure, is one session with Tim's own words; more than five is a ❌ and nothing started. On "ask", mochi replies with two buttons, takes a word in their place and counts nobody else's answer; the question waits a day in `~/.mochi/pending.json`, so a restart still takes it, and after that it is edited to say it expired and he mentions mochi again. The buttons arrive over the gateway like messages, needing no intent and no permission beyond posting the question. A follow-up is never classified.

The session is a new tab in the mapped workspace, started in the repository with `MOCHI_THREAD=<thread id>` in its environment and the whole opening pasted as a prompt, at Tim's own default model and effort. The opening carries `claude-plugins/mochi/briefing.md` whole, the project's `.mochi/instructions.md` as a block of its own, where the session posts, and Tim's words and everybody else's fenced the way hachiko's on-call brief is, so nothing quoted can pass for an instruction. That briefing and the `mochi` skill are where a session's orders live — the fence, follow-ups, the two audiences, the post shapes and flags, the allowed links, and what may never be named — so read those two rather than looking here. A briefing that cannot be read starts no session: the log says why and Tim gets a ❌.

The skill, the briefing and the four session hooks are a Claude Code plugin, `mochi`, in this checkout's own marketplace, `claude-plugins/`, so a session in a repository mochi does not serve has none of them; `claude/mochi-plugin.sh`, from `install.sh`, turns it on in the `.claude/settings.local.json` of each mapped repository and nowhere else.

## What mochi posts on Discord

A session gets a thread opened on Tim's message, or a post in the `forum` where the project's `.mochi/config.json` has one, since new messages bury a thread. Its first message mentions Tim — "Session started for <@Tim>'s message: <link>" — with the replied-to message and his words as block quotes and the classifier's summary; that mention subscribes him, since he keeps Discord's notifications to mentions, and he is made a member of the thread as well. A forum post is tagged with the classifier's kind of work, skipped when the forum lacks that tag, and his mention gets one reply naming the post. A thread or post mochi did not make keeps its author's title and is the session's thread, since a thread cannot hold a thread.

The state is in the name of the thread or post mochi made, in front of its title: `⏳` a session working, `❓` waiting on Tim — a question to answer, or a result to review — `✅` done with nothing left for him, `❌` failed, `⏸` stopped. The session moves it with `mochi post --review` and `--done`, and a follow-up of Tim's puts it back to ⏳ until the session's next such post. Discord allows a thread two renames in ten minutes, so only the latest name wanted is sent, never the states in between. A post that still carries a state tag from an older scheme loses it with its next change. The states and the names are kept in `~/.mochi/marks.json`, under a lock a session's `mochi post` takes too, so a restart renames from the right state.

His message gets two reactions and nothing else: 👀 while mochi is handling the mention, and 👍 in its place, which stays, once what he asked has reached a session — herdr took the prompt, every session a split started has its opening, or a stop went through. A failure leaves a ❌ and one line saying why, in the thread or, with no thread yet, as a reply to his message. Tim stops a session with a mention whose whole instruction is "stop" or "cancel": mochi sends it an esc, prompts nothing, never asks the classifier, shows ⏸ until his next follow-up and says "Stopped. Mention mochi to continue."; "stop showing the old elo" is an instruction like any other.

mochi pings Tim in one place. The plugin's hooks run `mochi session-event` when a session stops, when it is about to ask him something and when he has answered in it; each writes one small file into `~/.mochi/events/` and always exits 0, so the turn and the tool go on exactly as without it. The listener reads that folder every second, waits three seconds so a follow-up queued behind the turn cancels it, then shows ❓ and posts "The session is waiting on <@Tim>." — the one post allowed to ping anybody, him alone. Not for a session that said it is done, nor for a turn that ended with subagents or shells still running, and not again until his next word reaches the session; `waits.json` holds that, so a restart neither pings twice nor forgets. A ping that fails is retried after 30 seconds, doubling to an hour, and a thread Discord no longer has is left alone. Every other post has `allowed_mentions` empty, and no word mochi posts names a tool behind the work, since moderators read it; the tab and workspace are in the log for Tim.

A mention inside a session's thread is a follow-up, relayed to the same agent as a new prompt with everything posted there since his previous mention, fenced, with mochi's own posts and Discord's notices left out; nothing in the thread reaches the session unless he mentions mochi, and when the agent is gone a new one starts with the whole thread as context. A follow-up to a session waiting on a question, which herdr will not prompt, is his answer to it: mochi cancels the question with an esc, reads `herdr agent get` until herdr stops calling the agent blocked, and then prompts it with a brief saying he answered in Discord instead; a question still up after five seconds of that is a ❌ and nothing prompted. `~/.mochi/state.json` maps each thread to its agent, its source and his last mention; a record untouched for a week whose agent is gone is dropped with its attachments. A forum post three days done is archived rather than deleted, and comes back to the list when somebody writes in it.

## A session's own commands

`mochi post [--review | --done [--close]] [--pr <url>] [--type <kind>] [--file <path>]... [<text>]` posts into the session's own thread, split between lines past Discord's 2,000 characters, and takes its text on stdin when there is no argument, so several lines need no shell quoting. `--review` needs an answer from Tim or the team and sets ❓; `--done` is a task complete with nothing left for him and sets ✅; neither moves the state. `--close` goes with `--done` and asks for the tab, which mochi closes a minute later when Tim's last word came from Discord and nobody can be using it; the record stays, so a later follow-up starts a new session. `--type` refiles a forum post as feature, bug, improvement or research. `--pr` takes only a pull request of the session's own repository, from the mapped checkout's origin remote, and adds `#<number> (<url>)` as a paragraph of its own. `mochi history [--post] [--before <id> | --after <id> | --around <id>] [--limit <n>]` prints up to a hundred more messages of the channel the session started from, or of its own thread or post with `--post`, fenced the same way with their attachments downloaded. Both read the thread from `MOCHI_THREAD`, refuse one mochi has no record of, and read only the source in that record, so a session cannot browse the rest of the server.

A post may reach its own thread and its server's announce channel and nowhere else. `mochi announce [--pr <url>] [--file <path>]... [<text>]` is that second place, for any session, one mochi did not start included, and needs no `MOCHI_THREAD`: it posts to the `announce` channel of the server whose mapped repository shares an origin remote with the session's checkout, a worktree's own included. It is held to everything `mochi post` is, moves no state, opens no thread, mentions nobody, Tim included, and prints the posted message's link.

A session posts without anybody reading it first, so it can take back what it got wrong: `mochi edit [--drop-files] [--pr <url>] <message link> [<text>]` replaces a message's text, from the argument or stdin, and `mochi delete <message link>` takes it down, both in any session. The message has to be mochi's own and in that session's reach: its server's announce channel, or, from a session mochi started, that session's own thread or post. A thread's or post's first message is edited but never deleted, since deleting it leaves the post with nothing on top. An edit is held to a post's rules and to Discord's 2,000 characters, since it cannot be split, and pings nobody, the first post that mentions Tim included; `--drop-files` takes the attachments down with it.

Three rules hold for all of them, and they are boundaries rather than implementation. A `--file` goes up only from inside the checkout the session runs in, a checkout of its server's repository, or Claude Code's scratch folder for either, by its real path once links are followed, and never a `.git` file, a file named as secrets are kept, one hard-linked under another name, or one git ignores unless it is an image, a video or a zip; ten files at most, each within what the server takes. Before anything is sent, the text and every attachment but images and videos go through betterleaks, the scanner of the account's own pre-commit hook, with the checkout's own configuration and none from the session's: a finding refuses the post with its rule and where it was, never the secret, and a scan that cannot run refuses it too. Text carrying a link, a Discord invite or a file path is refused with the reason, bar an `https://` link on one of the server repository's `links` or a subdomain of one, and bar an exact address such as `chrome://extensions` that `links` allows; a look-alike, a bare host, `www.`, `http://` or that address with a path added is a link again. The file rules and the scan guard against a session's mistakes, such as naming the wrong file, rather than against one that means harm, which runs as the account and can reach the files by other ways. What can be refused before `op run` is, so a refusal costs no 1Password read — and since the session's server is not known until then, the text is held to every server's domains there and to its own server's once it is.

A pull request posted with `--pr` is watched until it merges or closes, in `~/.mochi/prs.json`, which the listener reads with `gh api` on the account's own `gh` login: merging makes the session ✅ with a line in its thread, closing without merging says so and leaves the state alone. A failed check run on the head commit is told to the session once per push, which puts it back to ⏳ and never reaches Discord.

## The listener and its agent

The token is the `bot token` field of the `mochi-discord` item in the `dev` vault, referenced from `home/.mochi/mochi.env.op`, which mise links into mochi's folder. Every command that needs it re-enters the binary under `op run --env-file`, so it is in one process's environment and never in an argument, a file or the log, and taken out of any error text before that is logged. A start that got no token, as does one Discord refused, leaves a marker in mochi's folder, and the next start waits half an hour out from it: `ThrottleInterval` alone would be an `op run` every five minutes for as long as the item does not resolve. A gateway that will not connect is retried with backoff and jitter, never sooner than five seconds after the last identify of any mochi process, which is Discord's limit; enough failures and the listener exits, since only a fresh start under `op run` picks up a rotated token.

While the gateway is connected — Discord acknowledging its heartbeats — mochi writes `~/.mochi/heartbeat` every half minute, and hachiko's watch reads its age the way it reads sync's: ten minutes without one is a ⚠️ naming `launchctl kickstart -k gui/<uid>/io.github.timche.mochi` and the log. When the wrapper has built a new binary behind it, mochi becomes that binary in the same process, between mentions and never inside one, so the token carries over and no second `op run` is spent; only when that fails does it exit, for `KeepAlive` to start it again behind the plist's five-minute throttle. Nothing else runs mochi's wrapper on a timer, so the listener runs `~/.local/bin/mochi version` itself every five minutes, which is what builds an edit. A message sent while it is reconnecting is not replayed, so a mention that got no 👀 is one to send again.

## Setting it up

A Discord application of its own called mochi, separate from the hachiko-discord admin bot, with Public Bot off and the Message Content intent on, invited to each server with View Channels, Read Message History, Send Messages, Create Public Threads, Send Messages in Threads, Add Reactions, Embed Links and Attach Files, which in a forum also covers making posts and editing the name, tags and archiving of mochi's own; no Manage Channels or Manage Threads. Its token goes in the `bot token` field of the `mochi-discord` item in the `dev` vault, and the server gets a config entry. A forum a project points `.mochi/config.json` at carries the tags mochi files a post under — `Feature`, `Bug`, `Improvement`, `Research` — by those names. `install.sh` links the rest and loads the agent.

## Environment knobs

`MOCHI_CONFIG`, `MOCHI_STATE_DIR` (everything mochi records about itself, `~/.mochi` by default), `MOCHI_ENV_FILE`, `MOCHI_BRIEFING`. `MOCHI_CACHE_DIR` is the wrapper's alone: where it builds the binary.
