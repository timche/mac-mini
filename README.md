# mac-mini

[![test](https://github.com/timche/mac-mini/actions/workflows/test.yml/badge.svg)](https://github.com/timche/mac-mini/actions/workflows/test.yml)

The Mac mini Claude Code runs on and controls: a headless Apple Silicon Mac that exists for agentic coding, several sessions at a time, reached over the tailnet from somewhere else. This repository is the whole of it — the machine and the account on it — and one command puts it there. As the account the machine is for, which unlike a VM's already exists:

```sh
curl -fsSL https://raw.githubusercontent.com/timche/mac-mini/main/bootstrap.sh | bash
```

A fresh Mac has no git and no package manager, so there is nothing to clone this with — which is what `bootstrap.sh` is for. It installs Homebrew, which brings the Xcode command line tools through `softwareupdate` rather than the dialog nobody is in front of, clones this repo to `~/.mac-mini` and runs its two phases: `machine.sh` builds the Mac, `claude.sh` makes it the one Claude Code works from.

The clone stays, because a Mac is a machine you pull and re-run rather than one you reprovision from a URL — hidden because it is machinery rather than work:

```sh
git -C ~/.mac-mini pull
~/.mac-mini/machine.sh
~/.mac-mini/claude.sh
```

`MAC_MINI_DIR` puts it somewhere else. It is not a clone to delete: everything in `$HOME` is a symlink into it, and the LaunchAgents launchd loads are links into it too, so moving the checkout means re-running `claude.sh` to point the links at the new place.

Both phases are safe to re-run, and both are careful about what is already there. That is the difference from provisioning a VM: a VM is thrown away and built again, while this Mac is re-run in place and is reached over the sshd and the tailnet the run itself configures, so a rewritten sshd or a bounced tailscaled would cut the run off from the machine it is running on.

## A fresh Mac

What the scripts cannot do happens at the Mac itself, with a screen and a keyboard, before the first run:

1. Setup Assistant: the account the machine is for, as an administrator. An Apple ID only matters for Xcode, which `xcodes` downloads with it; the iCloud features can all stay off.
2. FileVault off, then Automatic login for that account in System Settings > Users & Groups. Auto-login needs FileVault off, and everything that lives in the login session waits for it after every restart.
3. Remote Login and Screen Sharing on, in System Settings > General > Sharing: the first is how the bootstrap is run from another machine over the LAN, the second is how everything that needs a click gets done once the screen is gone, including the [privacy permissions](#privacy-permissions) below. Screen Sharing is the one of the two no script can turn on, because that pane is also what registers the rights the sharing agent needs.

Then, over SSH on the LAN, the command above. It asks, in order, for the sudo password, a tailnet login URL, the Apple ID and a 2FA code for Xcode, then a GitHub device code, a Claude Code login and the 1Password service-account token.

Afterwards, over Screen Sharing: the [privacy permissions](#privacy-permissions) below, System Settings > Lock Screen > "Require password after screen saver begins or display is turned off" set to Never, and OrbStack opened once — its welcome screen is where OrbStack's terms are accepted and where Docker is chosen, and no script can click either. `machine.sh` names all three every time it runs, so a Mac that is missing one says so rather than being quietly unable to take a screenshot or start a container.

And in the Tailscale admin console: add an `ssh` rule for whoever should reach the Mac, and disable key expiry for it, since a node whose key expires drops off the tailnet after 180 days until somebody logs in at it again.

## The machine

`machine.sh` installs Homebrew and the `Brewfile`'s packages, turns Remote Login on if it is off, brings tailscale up as a system daemon serving Tailscale SSH, puts docker on the Mac as OrbStack, installs Rosetta for the x86_64 tools a Windows build of an Electron app runs, hardens sshd down to keys only, no root, one user, installs the one [root helper](#the-root-helper) a session may run under sudo, and — only where there is a terminal to type an Apple ID at — installs Xcode.

Every package is the `Brewfile` at the repo root, applied with `brew bundle --no-upgrade`: by `bootstrap-system.sh` here, and by `install.sh` in the account phase, one declarative list for both. `--no-upgrade` because this Mac is re-run in place over the very sshd and tailnet a run touches; `brew bundle upgrade` is the deliberate version of that. A failed package is not fatal — the exception is `gh`, `jq` and `op`, which `bootstrap-system.sh` stops on, since nothing after it works at all without them.

`xcodes` and `aria2` are the two packages the `Brewfile` deliberately leaves out. Both exist only for the Xcode download, which happens only where there is a terminal, so declaring them would install them on every unattended provision for a step it is never going to run — and `aria2` is optional even there, a faster download rather than a dependency. `xcode.sh` installs both itself, once it has decided it is going ahead.

`unattended.sh` is the part that makes several parallel sessions on it possible, and all of it is one idea: nothing on this Mac may stop and wait for a click that nobody is there to make.

- **Restart after power loss, and never sleep.** `pmset autorestart 1`, `sleep 0`, `disksleep 0`, `displaysleep 0`. A Mac nobody can walk up to is otherwise gone until somebody does. `displaysleep` is in that list although there is no display, because a `screencapture` taken while the display is asleep comes back a black frame, which is exactly what a missing Screen Recording grant looks like.
- **No crash dialogs.** `com.apple.CrashReporter DialogType none`, per user. The Electron apps under development here crash as part of the work, and each crash otherwise leaves Problem Reporter's window on the screen with the crashed process waiting behind it. The report still lands in `~/Library/Logs/DiagnosticReports`, which is where it is any use. Per user rather than per machine because the two `ReportCrash` processes read the domain of whoever owns the session the crash happened in.
- **No screensaver.** `defaults -currentHost write com.apple.screensaver idleTime -int 0`, in the ByHost domain even though the engine that reads it runs in a sandbox. This is the half of the screen lock a script can still write; the lock itself is in the pane-only list below.
- **macOS updates download but never install.** `AutomaticDownload` on and `AutomaticallyInstallMacOSUpdates` off, in `/Library/Preferences/com.apple.SoftwareUpdate`, plus `softwareupdate --schedule on` for the check itself. An update that installs itself restarts the Mac, and a restart takes every session's worktree state, every running build and every browser with it, then sits at the login window if auto-login is off. Downloaded means installing it is a decision somebody makes, and takes minutes rather than an hour — Tim's decision, because installing one unattended is not open to this Mac at all: [the nightly update](#updates) says what is waiting and why it cannot install it. `ConfigDataInstall` and `CriticalUpdateInstall` stay on — XProtect and the security data files install in place, with no restart and no dialog. Background Security Improvement is not settable here at all: it lives in declarative device management, which needs a supervised MDM enrollment. It is on, and it can restart the Mac.
- **No Spotlight indexing.** `sudo mdutil -a -i off`. A checkout is a few thousand files; the same checkout with `node_modules` in it is a few hundred thousand, and every worktree is another copy, so `mds` spends a core walking files nobody on a headless Mac will ever search for by name — again after every install. `mdutil -s /System/Volumes/Data` reads the result back without sudo, so `assert-machine.sh` asserts it rather than reporting it. What goes with it: ⌘Space and Finder search at the Mac itself, `mdfind`, and the dSYM lookup that symbolicates a native crash report.
- **No media analysis.** `launchctl disable gui/<uid>/com.apple.mediaanalysisd`, then the running copy stopped by its pid, since System Integrity Protection refuses a `bootout` of the job. `mediaanalysisd` analyses photos and runs on-device text embedding for search, on the CPU, and after a reboot it can hold two cores for hours on a Mac nobody searches from. The disable is the account's override and holds across reboots; a macOS update can clear it, which the next run puts back. What goes with it: Photos analysis, Live Text and visual search in images, and Spotlight's search by meaning. `launchctl enable` and a reboot undo it.

Three things it deliberately does not do, because each needs somebody looking at the screen, which on a headless Mac means Screen Sharing. All three are named on every run rather than assumed:

- **Auto-login.** This matters more than it looks: a LaunchAgent lives in the `gui/<uid>` domain, which exists only while somebody is logged in at the console, so a Mac sitting at its login window is a Mac where neither docker nor any of the agents below are running. Tailscale is deliberately not in that list — its daemon is a LaunchDaemon and comes up without a session, which is why the Mac stays reachable even when this goes wrong. Turning auto-login on means writing the account password to `/etc/kcpassword`, obfuscated rather than encrypted, and that is a decision for whoever owns the Mac rather than for a script. It needs FileVault off. System Settings > Users & Groups > Automatic login.
- **Screen Sharing.** `launchctl enable system/com.apple.screensharing` clears the `Disabled` flag exactly as `remote-login.sh` does for sshd, and for this job that is only half of it: the screen recording rights the sharing agent needs are registered by the Sharing pane itself, so a Mac enabled from a script comes out with the job loaded, the toggle still reading off and nothing answering on port 5900. So `unattended.sh` looks at the port rather than at launchd's opinion of the job, and asks for System Settings > General > Sharing. It is the one to fix first, since it is how the screen lock below and the privacy permissions get done.
- **The screen lock.** System Settings > Lock Screen > "Require password after screen saver begins or display is turned off", set to Never. A locked session keeps running — sshd answers, launchd keeps its jobs, builds finish — but every screenshot and recording taken over SSH comes out black, so a session cannot show that what it changed works. On macOS 27 this is the pane's alone: the setting is in no preference domain, `com.apple.screensaver` has no `askForPassword` and its ByHost half holds `idleTime` and nothing else. `sysadminctl` is not a way in either: it answers "screenLock delay is immediate" with the pane set to Never, so its reading cannot be trusted and nothing asserts it, and `sudo sysadminctl -screenLock off -password -` over Tailscale SSH fails with `MKBDeviceSetGracePeriod error -17` and changes nothing. So `unattended.sh` names the pane setting and neither writes it nor reads it back. What the pane actually did is checked by watching the session: `pmset displaysleepnow`, and a `screencapture` that comes back a real desktop rather than a login window.

`harden-ssh.sh` refuses to disable password logins unless the user has a key sshd could actually let them in with, because on a Mac there is no provider console to fall back to. A Mac reached with a password comes out of a run unhardened and told what to do about it. `FORCE_HARDEN=true` overrides that if you are certain of another way in.

`root-helper.sh` runs after it, because nothing in the way this Mac is reached depends on the helper. It skips itself with a message where sudo would have prompted and there is no terminal to answer at, and `machine.sh` names it among what is left — a Mac without it is a Mac where every root command waits for Tim, which is where this started.

## The root helper

sudo on this Mac asks for Tim's password, and a session has no terminal to type it at, so every privileged step is a command printed for him to run. `root-helper.sh` carves out one exception: `/usr/local/libexec/claude-root`, a script that takes a fixed set of actions and refuses everything else, and a sudoers rule letting the account run that one path with no password.

Narrow rather than blanket, and narrow against mistakes rather than against the account. Nothing here defends root from a session that set out to have it: sessions run with permissions bypassed, portless's root daemon runs JavaScript this account owns, `home/.zshenv` is a symlink into a checkout the account writes with `~/.local/bin` first on the PATH it sets — so a session can capture Tim's own `sudo` — and Homebrew's `tailscaled` runs as root out of a prefix the account owns. What the narrow rule buys is the other half: an agent acting on its own can bounce `dasd` or flush DNS and nothing else, and what it is trusted with is a list somebody can read rather than the whole machine. Two rules decide what may be an action, and the second is the one that is easy to get wrong.

The helper takes no path, no command, no signal and no pid from its caller; the only argument any action takes is a name matched against a list compiled into the script, by string equality and never as a pattern. `sudo /usr/local/libexec/claude-root --list` prints the actions and the daemons:

- `restart-daemon <name>` — `launchctl kickstart -k system/<label>` for a daemon on the list, `dasd` and `tailscale` so far. Some of Apple's own daemons are protected from being told to restart, and launchctl says so rather than doing half the job — dasd is one, refused with "Operation not permitted while System Integrity Protection is engaged" — so the fallback is `kill -TERM` of the pid launchd is watching and letting launchd bring it back, which SIP allows; either way what is reported is the old pid and the new one, read back from `launchctl print`, because a kickstart that returned 0 has only queued the work. tailscale is on the list for [the nightly update](#updates), which is what restarts tailscaled when its formula moved; a session should leave it alone, since the restart drops every tailnet connection including the one somebody is typing in.
- `flush-dns` — `dscacheutil -flushcache` and `killall -HUP mDNSResponder`.
- `reinstall-portless` — `portless service install` again, on whichever node and portless the account's mise has now. It takes no argument, reads the account off `/dev/console` rather than from its caller, asks that account's own login shell which node and which portless are current, and serves the TLDs the helper spells out — checked against the `PORTLESS_TLD` in `home/.zshenv`, so a reinstall cannot quietly take a dev URL off the Mac.

Every action writes one `logger -t claude-root` line with its name and its argument, after the argument is validated and before anything privileged runs. That line is the only trace a run leaves: sudoers can be asked to log an allowed run of this one command against this Mac's `!log_allowed` default, and with the rule installed the entry reaches neither `/var/log/system.log` nor the unified log — so the drop-in does not ask. It is a record rather than evidence, since `logger` is open to every process and the account can write the same line; `/usr/bin/log show --predicate 'eventMessage beginswith "claude-root:"'` reads them back, with the full path because zsh's own `log` builtin shadows it and silently prints nothing.

And no action touches a path the account can write, even one the helper spells out itself. A root command aimed at a file in a home directory is a root command the account aims wherever it likes: it replaces the file with a symlink and the copy writes through it, or the chown hands it a root-owned file, or the truncate empties whatever the link points at. This is not hypothetical — an earlier shape of the helper capped the machine's own logs under `~/Library/Logs`, and that one action was passwordless sudo for everything, since `hachiko-sync.log.0` could be a symlink to `/etc/sudoers.d`. Capping those logs needs no root at all, and [hachiko](#hachiko) does it as the account. An action that needs root needs it for a path only root can write, and `assert-machine.sh` reads the helper back to say so.

`reinstall-portless` is the one named exception, and nothing else may follow it. portless's root daemon already runs the account's own node and the account's own JavaScript as root — portless's design rather than this repository's choice, and the trade is in `$PROJECT_DOCS_DIR/mac-mini/decisions.md` — so reinstalling it opens no route that is not open already, while what it buys is that a `mise up` which moved node or portless does not leave every dev server on this Mac without a proxy until Tim is awake. The assert cuts that one function out of the file before it reads the rule off everything else.

The helper and the sudoers rule are both root-owned copies, never links into the checkout, which is what makes an edit to either reach the Mac only when Tim runs the installer — and sudo ignores a drop-in under `/etc/sudoers.d` that is not a root-owned 0440 regular file in any case. The rule is checked with `visudo -cf` before it is moved into place, since a sudoers file sudo cannot parse takes sudo away from Tim as well, and it names the helper through a `Cmnd_Alias` because the secrets scan every commit here goes through reads a path after `NOPASSWD:` as a password being set. The account name is rendered in at install time, because nothing here is written for one account, and `dscl` is asked whether that account exists: a rule naming one that does not — a typo, or a placeholder that survived the rendering — would leave this Mac with no sudo at all.

Adding a daemon to the allowlist is an edit to `system/libexec/claude-root` followed by `~/.mac-mini/root-helper.sh`, which asks for Tim's password. That is the point: what a session is trusted with changes only when he says so.

So the installer shows what is about to change and asks before it writes: a `diff -u` of each of the two files against the copy already installed, the whole file where there is none yet, and then `Install? [y/N]` where there is a terminal to answer at. A session cannot run the installer, but it can write the two files a run of it copies, and one of them is a command sudo will then run as root without asking again — so read the diff rather than typing through it. Where there is no terminal and sudo wants a password, the step skips itself with a message instead, and `machine.sh` names it among what is left. A run with nothing to change writes nothing and says so, which is what makes it safe to re-run: each file is compared with what this repo says it should be, contents, owner and mode.

`CLAUDE_ROOT_DRY_RUN=1` makes an action say what it would do and change nothing, which is how the argument handling is tested without sudo anywhere near it; it reaches the helper only from a shell, never through sudo, and it is checked after the validation rather than before, so it is no way past the allowlist.

## Privacy permissions

Three grants that no script can make, granted once each over Screen Sharing and then good until somebody revokes them. TCC only ever asks the screen, and there is no supported way in from an SSH session: the consent dialog cannot appear in a session with no window server of its own, and writing the grant into `TCC.db` by hand needs SIP off.

Which process is asked depends on how the session arrived. Every Claude Code session is a pane of the herdr server launchd runs in the GUI session, so the grants that matter day to day are that job's — and the job starts `~/.local/libexec/herdr-launcher`, which runs herdr as its child, so the launcher is the path every grant below is given to. macOS asks TCC's questions of the responsible process rather than of the one that called: launchd makes a job's own process responsible for itself, and a child inherits that unless it disclaims. That indirection exists because herdr's release binary is ad-hoc signed, macOS pins a grant to an ad-hoc binary's exact contents, and `herdr update` replaces it — which used to drop every grant until somebody re-granted them on the Mac's own screen. The launcher's bytes move only when `launchd/herdr-launcher.c` does, so an update to herdr is now invisible to TCC. Over the tailnet without herdr the process TCC asks about is `tailscaled`, which answers Tailscale SSH itself; on the LAN it is sshd, where the entries are `/usr/libexec/sshd-keygen-wrapper` and `com.apple.sshd-session`, either of which can be the one that gets asked. The panes take no drag from a remote session, so use the **+** button and ⇧⌘G to type a path.

- **Screen Recording** — System Settings > Privacy & Security > Screen & System Audio Recording. For `screencapture` and every recording taken over SSH, which is how a session shows a change working rather than asserting it, and for herdr, which reads the panes it drives. Without it `screencapture` still exits 0 and still writes a PNG; the PNG is black.
- **Accessibility** — System Settings > Privacy & Security > Device Control and Data Access, the pane macOS 27 folds Accessibility into; the Accessibility link opens it. The same entries. This is what lets a session reach into another app's windows — focus, keystrokes, clicks — which is how herdr drives anything with a GUI.
- **Full Disk Access** — for the launcher, so that a session can write Claude Code's native messaging host into `~/Library/Application Support/Google/Chrome` and read the profile back. Without it both are "Operation not permitted".
- **Notifications** — System Settings > Notifications, per app rather than per binary. For the Electron app under development, so that a notification it posts is delivered rather than dropped. Its entry only exists once the app is signed and has asked for permission at least once, so the order is run it, let it ask, then allow it; before that there is nothing in the list to switch on.

To check them afterwards, over SSH:

```sh
screencapture -x /tmp/shot.png && ls -l /tmp/shot.png
```

A real desktop is hundreds of kilobytes. A black frame is a few, whatever the resolution — which is the tell, since the exit status and the file are the same either way. Copy it off and look at it if the size is ambiguous. Nothing has to wake the display first: `unattended.sh` sets `displaysleep 0`, because a capture of a sleeping display is the same black frame a missing grant gives.

```sh
osascript -e 'tell application "System Events" to count processes'
```

Accessibility: a count means the grant is there, and `-25211 osascript is not allowed assistive access` means it is not.

macOS also puts up a "requesting to bypass the system private window picker" dialog every so often, even with the grant in place. It is the one modal this repo cannot switch off, and it needs Screen Sharing and a click — worth knowing about when screenshots start coming back wrong for no reason.

A session shows its own app rather than the display, which carries every other session's windows: `window-shot <owner> <out.png> [title]` captures one window without its shadow, Electron's child views included. It is `screencapture -x -o -l <window id>`, and the id is the part macOS has no command for, so the script asks `CGWindowListCopyWindowInfo` through the Command Line Tools' `swift`, about a quarter of a second with nothing to compile or install. The owner is the process name the window list uses — `Electron` for an unpackaged Electron app, the product name for a packaged one — and the list comes front to back, so the frontmost of that owner's on-screen windows wins unless a title substring picks another. No match exits 1 and names what is on screen instead.

## Tailscale

`tailscale.sh` runs the open-source `tailscaled` the `Brewfile` installed as a root system daemon and sets the prefs this Mac is on the tailnet with: Tailscale SSH on, and no advertised routes — neither a subnet nor an exit node. Agents run unattended here, so a route through this Mac would put the LAN behind it, and all of a client's traffic while it used the Mac as an exit, within reach of whatever one of them ran. A subnet router or exit node belongs on a machine that runs nothing else.

The daemon rather than the standalone app, even though both can serve Tailscale SSH. A system daemon runs before anybody logs in, so a Mac whose auto-login fails or whose GUI session dies is still on the tailnet and still reachable — where the app is a login item inside a session, which is the dependency that already makes docker and the herdr server wait for one.

Root runs Homebrew's own `tailscaled` under the LaunchDaemon `brew services` writes, which is the install [Tailscale document](https://github.com/tailscale/tailscale/wiki/Tailscaled-on-macOS#installing-tailscaled-from-homebrew): `sudo brew services start tailscale`, which `tailscale.sh` does where the daemon is not registered already. The label is Homebrew's to choose and it has renamed it once already, so `tailscale.sh` and `test/assert-machine.sh` both ask `brew services info` what it is rather than naming it; today the answer is `sh.brew.tailscale`, and `/Library/LaunchDaemons/sh.brew.tailscale.plist` is a root-owned copy of the one in the keg, which `brew services stop` takes back out again. It is `KeepAlive`, `RunAtLoad`, logs to `/opt/homebrew/var/log/tailscaled.log`, and passes no arguments, so tailscaled keeps its macOS defaults: the state in `/Library/Tailscale` and the socket at `/var/run/tailscaled.socket`. Naming either would move it, and moving the state logs this Mac out of the tailnet.

What that accepts: the daemon's `ProgramArguments` is `/opt/homebrew/opt/tailscale/bin/tailscaled`, and every directory on the way to it belongs to the account, as does the log it appends to — so the account can put its own binary at that path for root to run at the next daemon start. `$PROJECT_DOCS_DIR/mac-mini/decisions.md` has the trade. It is not the only such route on this Mac, and the account has read-write access to tailscaled's own API without any of it: tailscaled grants that to members of the macOS `admin` group, which is why nothing in `tailscale.sh` reaches the prefs through `sudo`.

Upgrading is `brew upgrade tailscale` and then `sudo brew services restart tailscale`. **Run the restart from the LAN**, `ssh timche@<the Mac's 192.168.x.x address>` rather than over the tailnet, because it drops every tailnet connection including an SSH session over one. The restart is a step of its own because `brew upgrade` has no part in services: launchd reads a plist at bootstrap and not again, and the plist names the opt symlink rather than a version, so the formula moving under it leaves the running process on the binary it already exec'd. `sudo brew services start` also takes root ownership of the keg it runs out of, and says which paths it took — so the keg left behind by a later `brew upgrade` is root's, and clearing it is `sudo rm -rf /opt/homebrew/Cellar/tailscale/<old version>`.

A session over Tailscale SSH is a child of tailscaled, so macOS asks tailscaled for any privacy grant something in it needs: the first `osascript` to System Events, which `test/assert-machine.sh` runs to read the login items, puts an Automation dialog on the Mac's screen and waits for it. Homebrew's tailscaled is ad-hoc signed, so the grant is tied to that one build, and every upgrade asks again. Over the tailnet, a suite that stops after the docker checks is waiting for that click, over Screen Sharing.

A node that has never logged in needs `tailscale up`, which prints a URL to open on a machine that has a browser and then waits for it — so `tailscale.sh` runs it only where there is a terminal to wait at, and prints the command when there is not. Everything after that is `tailscale set`, which changes prefs without starting a login, and which only runs where the prefs differ from what the script asks for. A node already set the way this asks comes out of a run untouched; one still advertising routes has them withdrawn.

MagicDNS is the daemon's own: tailscaled writes `/etc/resolver/<tailnet>.ts.net` and a file per reverse zone, each marked `# Added by tailscaled`, which send tailnet names to 100.100.100.100 and leave every other lookup with the resolvers the Mac already had. `tailscale.sh` leaves them alone, since tailscaled rewrites and removes the files it recognises as its own.

One thing only the tailnet can do, in [the admin console](https://login.tailscale.com/admin): allow Tailscale SSH to it with an `ssh` rule saying who may connect and as whom. Until that rule exists nothing reaches the SSH server tailscaled is running.

To see where it is:

```sh
tailscale status                       # the node, the tailnet, and who else is on it
tailscale debug prefs                  # RunSSH true, and AdvertiseRoutes empty
sudo brew services info tailscale      # whether it is started, and as what
sudo launchctl print system/sh.brew.tailscale   # whether the daemon is loaded, and on what
tail -f /opt/homebrew/var/log/tailscaled.log    # what it has to say
scutil --dns | grep -B2 -A2 100.100.100.100   # tailscaled's resolver files, as macOS reads them
```

## Docker

Docker here is OrbStack, the one cask `docker.sh` configures: it runs the Linux VM under Virtualization.framework and links its own `docker`, `docker compose` and `docker buildx` into `/usr/local/bin` and `~/.docker/cli-plugins`, so no docker formula is installed beside it. Its memory is dynamic and returns to macOS as the VM stops using it, on a Mac whose parallel sessions run browsers and Electron *outside* the VM and want that memory for themselves — so `memory_mib` is a ceiling rather than a reservation and `docker.sh` leaves it at OrbStack's default of half the machine.

The one thing it costs: OrbStack is free for personal use, and commercial use needs a paid licence bought per seat. A Mac that builds anything sold from it needs one, and nothing in this repo can buy or apply it — an unlicensed install runs on a Pro trial and then asks.

The first run is the app's own and needs somebody at the screen, which on this Mac means Screen Sharing: a welcome screen whose Next accepts OrbStack's terms, then a choice between Docker and Linux machines. `docker.sh` stops at `orb status` — the only thing it asks of OrbStack until that answers `Running`, since an install with no first run behind it has no settings to read and `orb config show` against one hangs rather than failing — and says what to click; `machine.sh` lists it under what is left. Everything OrbStack links — the CLIs, the plugins, the `orbstack` docker context, the `Include ~/.orbstack/ssh/config` in `~/.ssh/config` — it does for itself at that first run. It also appends a `# Added by OrbStack` block to `~/.zprofile`, which sources `~/.orbstack/shell/init.zsh` for the completions and `~/.orbstack/bin`; `~/.zprofile` is a link into this checkout, so that block is tracked here and stays.

After it, `docker.sh` settles two settings and only where `orb config show` disagrees: **start at login**, and **every core but two**, read from the hardware so that a different Mac needs no edit. It restarts the VM with `orb stop && orb start` only when the core count changed, since that is the one of the two the VM reads when it boots. A re-run on a settled Mac prints where it stands and touches nothing.

Start at login means a login item, and a login item lives in the GUI session — so docker is running only once the Mac has logged itself in, exactly like hachiko and the herdr server. A Mac at its login window has no docker.

To see where it is:

```sh
orb status                       # whether the VM is up
orb config show                  # every setting, including the two docker.sh sets
docker context show              # orbstack, the context OrbStack sets for itself
docker run --rm hello-world
```

## Xcode

`xcode.sh` installs the full Xcode, which this Mac needs for signing builds of an Electron app with a Developer ID certificate — the command line tools Homebrew brought are enough to compile but not the whole toolchain electron-builder reaches for. It is the one step of the machine `machine.sh` will not do unattended: Apple hands nobody an Xcode without an Apple ID, a 2FA code typed in while it is still valid, and the account password for the privileged end of the install. `machine.sh` runs it when there is a terminal and lists it under what is left when there is not.

`rosetta.sh` is the other machine step a Developer ID build leans on, and it needs nothing typed: `softwareupdate --install-rosetta --agree-to-license` under the sudo `machine.sh` already holds, so running `machine.sh` is what agrees to Apple's Rosetta licence. It asks an x86_64 `true` whether Rosetta runs rather than `pkgutil`, where `RosettaLinux` is the Linux VMs' and translates nothing on the Mac.

```sh
~/.mac-mini/xcode.sh
```

It stops before downloading anything if `/` has less than 40GB free, since the xip is around 11GB and unpacks to more than twice that before the copy into `/Applications`. The download comes through [`xcodes`](https://github.com/XcodesOrg/xcodes) — `--latest`, so a release and never a beta — and then the script selects what it installed, accepts the licence and runs the first launch, each one guarded so that a re-run asks for nothing.

`xcodes` remembers the Apple ID and keeps its password in the login keychain. This Mac is reached over SSH, where a keychain that needs to ask for anything cannot, so that write may be refused — in which case xcodes says so and asks for the Apple ID again next time, `XCODES_USERNAME` and `XCODES_PASSWORD` in the environment answer it without a keychain at all, and `xcodes signout` clears whatever is stored.

To see where it is:

```sh
xcode-select -p        # /Applications/Xcode-<version>.app/Contents/Developer
xcodebuild -version
xcodes installed       # every Xcode on the Mac, and which one is selected
```

Nothing here installs the Developer ID certificate, and nothing should: electron-builder takes it from `CSC_LINK` and `CSC_KEY_PASSWORD` and imports it into a keychain of its own for the length of a build. A project resolves both from 1Password with `op run` at that point, as below, so the login keychain never holds it and a Mac reprovisioned from here has nothing to re-import.

The intermediate that issued it is another matter. The certificate is from Apple's G2 Developer ID authority, macOS ships only the original one, and codesign may not build the chain from the copy inside the `.p12`, so `install.sh` adds the G2 intermediate to the login keychain from apple.com, with its SHA-256 pinned. An intermediate changes no trust, so this takes no sudo and no dialog on the screen. Both authorities have the common name `Developer ID Certification Authority`, so the check before it is by the OU, `G2`, and not by name.

## The account

`claude.sh` is the second phase and the part that needs an account. It installs no packages of its own — every package is the `Brewfile`'s — and runs four steps in order:

1. `install.sh` links this checkout into `$HOME` and `~/.claude` and installs the tooling those files configure.
2. `claude/login.sh` logs in to GitHub and to Claude Code, both of which want a browser on some other machine, and reruns `install.sh` for the half that wanted a token.
3. `claude/signing-key.sh` writes the commit-signing key into `~/.ssh` and registers its public half.
4. [shibuya](#shibuya) is deployed, and its ping token made if the Mac has none, so a fresh Mac checks in rather than being reported offline a quarter of an hour after its first sweep.

`install.sh` first, because `login.sh` logs in to a Claude Code that `install.sh` is what installs, and `signing-key.sh` writes the `user.email` from the `.gitconfig` `install.sh` links. shibuya last, because `shibuya/deploy.sh` and `shibuya/secrets.sh` both reach 1Password through `op run` with the service-account token `signing-key.sh` stores — a Mac that has no token file yet has shibuya skipped and said so, and a deploy that fails is reported rather than fatal. This is the only deploy nobody asks for; `install.sh` runs neither step. Run `claude.sh` again when a token expires; run `install.sh` alone after a pull that changed a link or a tool.

The GitHub token goes in a file rather than the login keychain (`gh auth login --insecure-storage`). This Mac is reached over SSH and does its work from LaunchAgents, and both of those meet a keychain that will not answer with a prompt nobody sees. Claude Code keeps its own credential in the keychain and falls back to `~/.claude/.credentials.json` when the write is refused, which is what an SSH session usually gets; if the login does not take, `claude setup-token` prints a token that lasts a year and `CLAUDE_CODE_OAUTH_TOKEN` carries it instead.

`.claude` sits under `home/` rather than at the repo root because a `.claude` directory at a repo root is *project* configuration to Claude Code — this repo would load its own global settings and skills a second time whenever it was the working directory.

Everything else here is a shell script, and the tools at the root are the exception. There are two kinds of them, a folder each. The one compiled thing that is neither is `launchd/herdr-launcher.c`, which is not a tool at all and so not a folder at the root: it is the program the herdr agent starts, C rather than Go and built once by `install.sh` rather than by a wrapper, for the reason [The herdr server](#the-herdr-server) gives — its bytes are an identity macOS pins privacy grants to, and a rebuild costs them. A compiled tool is Go and `CGO_ENABLED=0`, the standard library for what is trivial and a popular, battle-tested module pinned in `go.mod` and `go.sum` for what is not, built with the `go` the root `mise.toml` declares, and run from this Mac. A Worker is TypeScript, deployed to Cloudflare by a script of its own, and runs nowhere near this Mac — which is the point of the only one there is: [shibuya](#shibuya) is what notices that hachiko has stopped reporting, and nothing on a Mac can notice that about itself. Everything below is about the compiled kind. A tool's `main` package is at the folder's root, because that is the package the wrapper builds, and holds the argument parsing and a dispatch and nothing else; what the tool does is a package under its `internal/`, one per command and one per thing several commands share, so a command added is one case in main and one package behind it. There is no release pipeline and nothing to publish, because there is nowhere to publish to — the wrapper in `home/.local/bin/<tool>` builds from the checkout's own working tree, so an edit is a running binary on the next run after it is written, committed or not. It hashes the tool's sources, `go.mod` and `go.sum` among them, and when that hash has moved it rebuilds into `~/Library/Caches/<tool>` and moves the result into place in one step; when the sources do not compile it logs one line and keeps the last binary that did, which is the whole point where a half-written edit is live on the Mac before the next write finishes it. Between that build and that move it runs the whole module's `go test ./...`, because a binary that compiles is not one that works and the agents it feeds include the one that commits and pushes the project docs; a failing test keeps the last binary exactly as a failing build does, logs one line naming the failure, and records no hash, so the next run tries again. It is the only gate there is, main being what lands. Every other way the build can fail ends the same way and says which: a folder a pull has moved away, a mise that is not there, a go that is not installed — the last binary that worked keeps running, and the wrapper never downloads a toolchain from inside a LaunchAgent, which is `install.sh`'s job. The build and the test run each get two minutes of their own rather than one budget between them, since a slow build sharing one would leave the tests seconds and make a suite that ran fine look hung. A run with nothing to build never reaches for mise at all, and the binary it execs is static: only the rebuild depends on the tooling, so a LaunchAgent keeps watching while mise or Homebrew is the thing that broke.

The links themselves are declared in `mise.toml` under `[dotfiles]` and applied by `mise bootstrap dotfiles apply`, which recognises links that already point at the right source and replaces anything else at a target: with the `--force-dotfiles` `install.sh` passes, a real file left at a link's target is overwritten, with no backup kept.

A tool that edits a linked file by writing a new one and renaming it over the path replaces the link with a regular file, and from then on its edits and every later one stay off GitHub. Re-running the bootstrap at that point discards the tool's edits, so fold them in first: `cp ~/.claude/settings.json ~/.mac-mini/home/.claude/settings.json`, then `ln -sfn ~/.mac-mini/home/.claude/settings.json ~/.claude/settings.json`. `test/assert.sh` fails on any link that has become a file.

## The account, and no account name

Nothing under `home/` spells a home directory out, so the account can be called anything: `timche` on the Mac, `runner` under CI. The hook commands in `settings.json` go through `$HOME` — they run through a shell, so it expands — the statusLine command names no path at all, and the LaunchAgents, in which launchd expands neither a `~` nor a `$HOME`, each answer for themselves: every one of them runs `/bin/sh -c` and leaves every path to the shell, which is the one thing launchd hands a `HOME`. `test/assert.sh` fails on a `/home/<name>` or `/Users/<name>` anywhere under `home/` or in `mise.toml`, because a path written for one account is a hook that never fires for another, and it fails silently rather than loudly.

`env` in `settings.json` is the one place a `$HOME` would not work: Claude Code reads those values straight out of the file, so `CLAUDE_CODE_TMPDIR` is exported from `.zshenv` instead.

## The shell and the tooling

`install.sh` makes zsh the login shell if anything has moved the account off it. A Mac logs in to `/bin/zsh` already, and the check is `dscl . -read /Users/<name> UserShell` rather than `getent`, which macOS does not have — read rather than assumed, because a `chsh` that has nothing to change would still ask for a password nobody is there to type. Nothing else here needs root, Homebrew wanting none of it.

mise is a version manager for language runtimes and nothing else. The global tool list in `home/.config/mise/config.toml` is `node`, `bun` and `python`, the three whose version can differ per project, and a runtime a repository needs for itself is declared in that repository's own root `mise.toml` — which is why `go` is in this one's, for the compiled tools under their own folders, and why another project's `go` or `rust` stays in that project's. `install.sh` runs `mise install --locked` from inside the checkout so that both lists are installed, and says so when the `go` it asks for could not be: a Mac without it keeps running the binary each wrapper already built and quietly stops picking up changes. Everything else the Mac has is in the `Brewfile`, while mise, Claude Code and herdr are their authors' and portless, ccstatusline and chrome-devtools-mcp are npm packages mise's npm backend keeps on the node it already provides.

mise itself is the exception to the rule it enforces, and it is the same exception Claude Code is: the authors' own installer beats a package of it. `install.sh` runs `curl -fsSL https://mise.run | sh` into `~/.local/bin` when that binary is missing. [mise's install page](https://mise.jdx.dev/installing-mise.html) calls that the recommended route and Homebrew's formula not the preferred one — Homebrew builds mise separately from the official release binaries, the formula trails upstream, and only a standalone install supports `mise self-update`.

Claude Code is nobody's package. Anthropic's installer puts it at `~/.local/bin/claude` and it updates itself in the background on the default `latest` channel, which is the point of taking it from there: a pinned Claude Code is a day behind by the afternoon, and mise would spend every install putting the pin back over the updater's work. `install.sh` runs `curl -fsSL https://claude.ai/install.sh | bash` when that binary is missing and leaves it alone afterwards. Nothing sets `DISABLE_AUTOUPDATER`.

Neither rc file names a path for mise. `.zshenv` puts the shims, then `~/.local/bin`, then Homebrew's prefix in front of the system directories, and both shells activate whichever `mise` that finds; `.bashrc` builds the same order for itself, since bash reads none of the zsh files. `~/.local/bin` ahead of Homebrew's prefix is what keeps a `brew install mise` from answering first, and `install.sh` asks whether `~/.local/bin/mise` exists rather than asking PATH for the same reason. `test/assert.sh` checks the binary every kind of zsh resolves, through `whence -p` rather than `command -v`, since `mise activate` leaves a shell function of that name in an interactive one.

Homebrew is also why there is a `.zprofile`. Its prefix is on no default PATH, so `.zshenv` puts `/opt/homebrew/bin` behind the mise shims and `~/.local/bin` and in front of the system directories; but macOS runs `path_helper` from `/etc/zprofile` in every login shell, which rebuilds PATH with the system directories first. `.zprofile` runs after that and re-reads `.zshenv`, and `typeset -U` there keeps the second pass from listing anything twice.

herdr is the third: its installer puts it at `~/.local/bin/herdr` when that binary is missing, and `herdr update` replaces it in place. That is why it is not Homebrew's — `herdr update` overwrites whichever binary it runs from, which under Homebrew is a Cellar path the formula then no longer matches.

ccstatusline is `"npm:ccstatusline"` in mise's tool list, and `settings.json` runs it through its shim. Installed once rather than fetched per draw: `npx -y ccstatusline@latest` measured about 710ms a draw and `npx --offline` still 625ms, because the cost is npm starting node twice rather than the registry, while an installed copy draws in about 320ms.

Every session has two MCP servers whichever project it is in, registered at user scope by `install.sh`. `chrome-devtools` is Google's Chrome DevTools MCP, `"npm:chrome-devtools-mcp"` in mise's tool list and run through its shim: it drives a page and also reads what a screenshot cannot — performance traces, network requests with their bodies, source-mapped console output, throttling. It runs `--headless --isolated`, so each session launches a Chrome of its own with a throwaway profile rather than sharing one signed-in profile in windows on the Mac's screen; the installed Chrome trusts portless's CA from the system store, so `https://<name>.localhost` loads without a warning. It writes a screenshot, snapshot or recording only inside the session's workspace and refuses any other path. `--browser-url` pointed at a debugging port attaches the same server to a running browser or an Electron app instead, which a project declares in its own `.mcp.json` under a name of its own, since a project server shadows a user one of the same name. `context7` is Context7's hosted server, current documentation for the version of a library a project uses, with no key and so at the free tier's rate limit. Claude Code keeps user-scope servers in `~/.claude.json`, which is its state as much as its configuration, so they are written with `claude mcp add-json` rather than linked, and only when the definition in `install.sh` differs from what is there.

`.gitconfig` runs [Betterleaks](https://github.com/betterleaks/betterleaks) before every commit in every repository on the Mac, `hachiko sync`'s included, so a token pasted into a file stops at the commit rather than at a push nobody reviews. It is a hook defined in config, `[hook "betterleaks"]`, which git 2.54 runs beside a repository's own `.git/hooks` or `core.hooksPath`; a global `core.hooksPath` would have switched off each project's lefthook or husky instead. It scans only what is staged and redacts what it finds, a missing betterleaks warns rather than refusing every commit, and `git commit --no-verify` is the deliberate way past a false positive. `.github/workflows/secrets.yml` is the second line: it scans the full history of every push with the same config, from Betterleaks' own image pinned to a version, so a commit that skipped the hook or came from anywhere but this Mac is still read.

A second config hook, `[hook "worktree-install"]`, installs a JS project's dependencies into a worktree as it is added, because a worktree with no `node_modules` is one where the repository's own lefthook or husky pre-commit finds no linter and passes having checked nothing. `~/.config/git/worktree-install` runs on `post-checkout` and acts only on `git worktree add`: a null previous HEAD in a repository whose git directory is not the common one. A clone reports the same null HEAD from its main worktree and is deliberately left alone — installing there would run the lifecycle scripts of a repository nobody has read yet. It also wants a `package.json` at the new worktree's top level, no `node_modules` there, and `node_modules` in the main worktree, which is what says a person has already installed and so trusted this project by hand. The package manager comes from the lockfile — `bun.lock` or `bun.lockb`, `pnpm-lock.yaml`, `package-lock.json`, `yarn.lock`, and nothing at all without one — and the tools come from the mise shims on PATH. A main worktree with no `node_modules` gets the commands printed instead: the first install in the main checkout, `mise install` included when it has a `mise.toml`, and then the one for this worktree. Nothing here clones a project or makes that first install, since that is the person's decision to trust it. An install that fails prints the command to run by hand and exits 0, since the worktree exists either way.

Two more keep Claude's attribution out of every repository, because Claude Code's own setting only changes what the model is asked to write. `[hook "strip-claude-attribution"]` runs on `commit-msg` and deletes any `Co-Authored-By:` line naming Claude or `anthropic.com` and any `Generated with Claude Code` line, keeping a person's co-author; it strips rather than refuses, since a refused commit is one an agent retries and works around. `[hook "refuse-claude-attribution"]` runs on `pre-push` and refuses the push when a commit in it still carries one, which is what catches `--no-verify`, a cherry-pick and a commit made elsewhere. A pull request body never passes through git, so neither hook reaches it; a Claude Code `PreToolUse` hook on Bash, `home/.claude/hooks/strip-claude-attribution.py`, takes the same lines out of any `gh` command and any body file it names before it runs. The same hook refuses `--no-verify` on `git commit` and `git push`, and `-n` on `git commit`, anywhere in a command, since skipping the hooks is the one way past all of this; a permissions deny rule would match only a command that starts with `git push`.

`.gitconfig` includes `~/.gitconfig.local` last, which is where anything machine-local goes. It is untracked and written by hand, and `test/assert.sh` asserts that the signing key it leaves effective is the one the tracked config names.

## The signing key

The key is the same one every machine here signs with, and it lives in 1Password. `claude/signing-key.sh` writes it to this Mac as two files: `~/.ssh/id_signing`, mode 600 in a directory at 700, and `~/.ssh/id_signing.pub` beside it, which is what `.gitconfig` names as `user.signingkey` — git expands the `~` itself and finds the private half by the name. Nothing asks an ssh-agent for a key.

The private half goes from `op read` down a pipe into a temporary file in `~/.ssh` under `umask 077` and then a rename, so it is never under a world-readable `TMPDIR`, never briefly readable at its final path, and never in a variable, a trace or an argument. What bounds it is the account: anything running as the account can read that file, and anything running as the account can read the service-account token in `~/.config/op/service-account-token` and fetch the same key from 1Password. FileVault is off, because auto-login needs it off. The key signs commits and authenticates nothing, and GitHub revokes it in one click.

The third derived file is `~/.ssh/allowed_signers`, a principal and a public key so that git can verify what it signs. None of the three is a second source: `claude/signing-key.sh` rewrites the trust list from 1Password on every run, so a rotated key takes the line for the old one with it, and it reads the private half again whenever the file is missing or holds a different key from the one in the vault. A run against a key that is already there spends no `op read` on the private field, which matters because every one of them counts against the service account's day.

What it expects:

- A 1Password item with the key in it, at `op://dev/ssh-commit-signing`, whose `private key` and `public key` fields are the two halves. `SIGNING_KEY_OP_ITEM` names a different one.
- A 1Password service account with read access to that vault. `claude/op-token.sh`, which `claude/signing-key.sh` calls, asks for its token once, without echoing it, checks it can read the item, and stores it in `~/.config/op/service-account-token`, where `signing-key.sh` reads it and the `op` wrapper for every `op run`. After rotating the token in 1Password, run `claude/op-token.sh --replace` at a terminal to store the new one.

Nothing has to be running for a commit to sign, which is the whole of the operational story: there is no job to load, no socket to find, and a session that reaches the key file reaches it whether it came in over SSH, out of a LaunchAgent, or from a pane of the herdr server. To see where it is:

```sh
ls -l ~/.ssh/id_signing ~/.ssh/id_signing.pub         # the key, 600 and 644
ssh-keygen -y -f ~/.ssh/id_signing                    # the public half it carries
git commit --allow-empty -m test && git log --format='%G?' -1
```

`error: No private key found for public key "/Users/…/.ssh/id_signing.pub"` from that commit means the public half is there and the private one is not, which is a `claude/signing-key.sh` away. `error: user.signingKey needs to be set for ssh signing` means the config itself is not in place, so `./install.sh` has not linked `.gitconfig`.

## Auto-sync

[`hachiko sync`](#hachiko) gets everything written in the project docs upstream on its own: it commits, pulls and pushes `~/projects/docs` with nobody asking it to, which is what makes a note taken in one session readable from another device a minute later. Every repository `~/.config/hachiko/sync` lists is watched by the one process. The config is read once at startup, so another repository is one `repo =` line and a restart; `mode = dry-run` in it reports what each pass would do and changes nothing, which is how a change to sync itself is watched before it is trusted.

The second entry is this repository, and it is there for one folder: `paths = home/.claude`. The rest of it is committed and pushed by the session that changes it, as `CLAUDE.md` says, but the global `CLAUDE.md`, the settings, the skills, the agents and the hooks are written through the `~/.claude` symlink by Tim, by his tools and by Claude Code itself, outside any change anybody set out to make — so nothing commits them, and they sit in the tree being read by every session and published by nobody. A `paths =` line, repeatable and relative to the repository's root, is what makes a daemon on a tree a session also writes to safe: every command a pass runs against the tree carries those paths, which for `git commit` is git's own `--only`, so a change a session has staged elsewhere stays staged and out of the commit, one it has not staged stays where it was, and the subject names the synced files alone. Inside those paths the opposite holds, and deliberately: `--only` commits the working tree as it stands, so a file under `home/.claude` that somebody staged in part is committed whole. Those files are sync's, and half of one on the remote would be a file nobody wrote. A `repo =` with no `paths =` is the whole repository, which is the docs.

Three rules come with a limited repository. It does not pull and may not be told to: `git pull --rebase --autostash` stashes and reapplies the whole working tree, which is precisely the work outside those paths that this exists to leave alone, and git has no pull a pathspec can narrow — so `fetch_interval` does nothing, nothing ever rewrites the tree, and a rejected push is a failure posted to Discord rather than something to rebase. It syncs on one branch, the one its own `refs/remotes/origin/HEAD` names, read once at startup: a commit on a branch somebody checked out here would carry files that are nobody's work in progress onto it and the push would publish that branch, with nothing to bring them back. And a push publishes the branch rather than a commit, so sync marks its own commits with a `Synced-by: hachiko sync` trailer and pushes only when there is one of them waiting, counting the push delay from the oldest. A session's commits are never what starts a push — one it is still shaping would be published, and one it then amends or squashes is one it can no longer push without forcing — but they do go up underneath sync's when it has something of its own to send, which is how a session's work reaches the origin without it having pushed. A repository synced whole, which is the docs, pushes every unpushed commit on the branch as it always has. A tree sync may not commit in — mid-rebase, mid-merge, or on another branch — is left alone with one line in the log saying why, said once rather than once a second.

Two minutes of quiet rather than the docs' five seconds before `home/.claude` becomes a commit, and then the same minute's push delay. The Mac reads those files through the symlink the moment they are written, so what goes to GitHub is the history rather than the live copy: a session's run of edits across `CLAUDE.md` and `settings.json` lands as one commit, and a `settings.json` caught half-written is that much less likely.

It runs as a LaunchAgent labelled `io.github.timche.hachiko-sync`:

```sh
launchctl print gui/$(id -u)/io.github.timche.hachiko-sync         # loaded, and what launchd makes of it
tail -f ~/Library/Logs/hachiko-sync.log                            # why something did not land
launchctl kickstart -k gui/$(id -u)/io.github.timche.hachiko-sync  # after editing the config
hachiko sync --once                                                # one pass in the foreground: sync now
```

The agent is a symlink into this checkout like everything else, which launchd accepts: it resolves the link when the job is bootstrapped and reads the file behind it. It has nothing to render because it names no path of its own — launchd expands neither `~` nor `$HOME` inside a plist, and a `$HOME` in `StandardOutPath` is an `EX_CONFIG` failure at load with nothing anywhere saying which key was wrong, but launchd does hand a gui-domain agent a `HOME`. So `ProgramArguments` is `/bin/sh -c`, and the shell exports the PATH and opens the log before `exec`ing the wrapper: the PATH because launchd hands a job almost none and every pass shells out to git, and `exec` because the status `KeepAlive` reads has to be the daemon's rather than the shell's. Nothing else is exported, these commits being signed from the key file `~/.gitconfig` names. There is no `WatchPaths`, the one key that would have to arrive absolute, because it polls `git status` itself rather than being woken by a write. `test/sync-agent.sh` proves all of it against launchd itself, under a label of its own and with a stand-in for the wrapper, because an assert that only reads the file passes on a plist launchd would refuse.

Each repository is asked once, before any pass, where it really is, whether it is a repository at all, and — for a limited one — which branch its own `origin/HEAD` names. One that cannot answer is left out with a ⚠️ of its own and the daemon runs the rest, because these are separate repositories and an `origin/HEAD` nobody set on one is no reason for the others to stop being published; only a config where not one repository could start is one the daemon exits on. It is read at startup, so a repository that has been fixed is picked up the next time sync starts, which an edit to `hachiko/` already does.

`install.sh` loads it with `launchctl bootstrap gui/$(id -u)`, once `~/projects/docs` is a clone — a Mac whose clone failed is left unsynced rather than restart-looping — and boots an already-loaded one out and back in when the plist has changed, since `kickstart` restarts the job from the copy launchd read rather than re-reading the file and a changed plist would otherwise wait for a reboot. The agent being a link, comparing the target across the bootstrap would say nothing — what the link points at is a file a pull already changed — so `install.sh` keeps a copy of the definition the daemon was last loaded from under `~/.local/state/mac-mini/`, written only once the load succeeded, and compares against that. A daemon that fails on every start retries every ten seconds for as long as the Mac is up, `KeepAlive` and `ThrottleInterval` being the whole of what a LaunchAgent can say about it, and the log is the only place that shows. It also exits non-zero on purpose when the wrapper has replaced its binary, so `KeepAlive` is what puts the new one in.

The subject is written by a model: `subject_model = haiku` in the config, through the Claude Code already logged in on this Mac, so a commit says what changed rather than which files did. It is handed the staged diff of exactly what is about to be committed — capped at 16 KB with the `--stat` above it, so a diff cut off halfway still names every file — and the repository's last ten subjects as the house style, and it answers with one line. An alias and never a pinned model id, which is a model that one day stops answering. The call is isolated because a diff is somebody's text rather than instructions: no tools, no MCP, no skills, none of the account's own customisations, a working directory that is nobody's project, nothing left on disk, and a minute's deadline of its own. The only thing its answer can become is a subject, and that is taken as the first line that says anything, stripped of what wraps it and refused when it is too long to be one. Anything else — a failure, the deadline, an empty or overlong answer, or no model configured at all — is `Update a.md, b.md` as before, with one line in the log and nothing to Discord, because a subject is cosmetic where the work landing is not. A dry run asks nothing of it.

Five seconds after the last write to a watched tree, a burst of edits lands as one local commit, subject `Update a.md, b.md` and a count once there are more than three files where no model wrote one. The commit comes before the rebase, so a pull runs over a checkpoint rather than over a dirty tree. The push waits for `push_delay`, counted from the committer time of the oldest commit in `@{upstream}..HEAD` and read from git on every pass, and then takes everything unpushed at once: a minute for the docs, long enough that a burst of notes goes up as one push and short enough that nobody reads a stale page for long. A steady stream of edits cannot postpone a push past its delay, a held pass still pulls, and a tree is left alone while `HEAD` is detached or a `MERGE_HEAD`, `CHERRY_PICK_HEAD` or `REVERT_HEAD` exists, because a commit there would land inside somebody's rebase or merge. An `index.lock` is a race rather than a fault, because a session in the same tree runs git a few times a second and holds the index for a fraction of one: a pass that meets one does nothing and the next one a second later finds it gone, and only a lock still there a minute later is reported — which is the shape of one a killed git left behind, and nobody's to remove but Tim's. A push is retried with exponential backoff and a bounded number of attempts; one rejected is rebased once and pushed again, and a rebase that conflicts is aborted rather than retried. The fetch interval is the only way another machine's writes arrive, and the recheck is what retries a push on a pass with nothing written. What it means while editing is in `CLAUDE.md`.

It polls `git status` every second rather than watching the tree, which is what a recursive watcher could not do without cgo and could not do cleanly either: a watcher cannot exclude `.git`, so every pass's own writes to the index arrive as events to be filtered out by path, and `git status` already answers what changed with `.gitignore` applied, in under ten milliseconds on a repository of this size. A loop that polls also needs no timer arithmetic — the fetch interval, the recheck and a push deadline are each a comparison on the next tick. And there is no lock: launchd runs one of these at a time, git's own `index.lock` keeps two gits out of one repository, and a lock held for the life of the process would make `--once` a no-op. A repository's loop that dies takes the process down non-zero rather than looking alive and watching nothing.

A failure goes to the Discord channel every other hachiko message goes to: one ⚠️ per distinct failure while it persists and a 🟢 in the same thread when it clears, the same shape as `hachiko gc`'s, with a fetch that fails while there is nothing to push not counted as one. A rebase conflict pauses pulling for that repository and re-arms itself — sync records the local `HEAD` and the upstream ref as they were at the conflict and resumes the moment either one moves, which is anything Tim could have done to fix it.

An agent lives in a GUI login session, so what keeps sync running with nobody at the Mac is the Mac logging itself in, by auto-login or by whoever unlocks FileVault, plus `pmset autorestart` to bring it back after power loss. Until a session exists there is no `gui/<uid>` domain to load the agent into, so an `install.sh` run over SSH against a Mac sitting at its login window says that and leaves the agent unloaded.

What watches it is the five-minute check, through the one liveness check that also watches the worktree sweep and the Discord listener. Sync writes a heartbeat every half minute — the oldest of its repositories' own ticks, so a loop wedged on something no timeout caught stops it advancing — and the check posts when that is over ten minutes old, only once the sync plist is there. With sync alive and reporting nothing wrong it also reads each repository in the config: a commit more than half an hour past its own `push_delay`, or a tree dirty for over ten minutes, is one message and a 🟢 when it catches up. Both readings carry the repository's own pathspec, because what is not sync's to commit is not sync's to be behind on — a session's work left uncommitted all afternoon in this checkout, or a commit of its own waiting to be pushed, is not a sync that has stopped. `HACHIKO_SYNC_STALE`, `HACHIKO_SYNC_LATE` and `HACHIKO_SYNC_DIRTY` are those three thresholds.

## Finding the project docs

A `SessionStart` hook, `project-docs.sh`, prints the project's docs folder and its shape — stdout from `SessionStart` goes into the session context, so Claude starts already knowing the docs are there. It looks only at `~/projects/docs/<repo>`, the project's folder in the separate docs repository; a checkout's own `docs/` is the project's published documentation, not its working docs, so it is never read. A project with no folder there produces no project output. Before the project's folder it lists `~/projects/docs/shared`, which holds what applies to every project, such as the Cloudflare account's conventions; that listing comes in every session, in a repository or not.

The repository name comes from the `origin` remote rather than the directory, because a worktree under `~/.herdr/worktrees/<repo>/<branch>` is named for the branch while every branch shares one docs folder. Subdirectories collapse to a name and a count: listing every file put fifty lines into every session on the largest project, and the shape is the part worth injecting.

It prints one line and the file list, and stops there. What a project's docs are and how they are meant to be used differs per project and belongs in its own `README.md`; how the folder syncs, and that they should be read before the work, is the same everywhere and belongs in the global `CLAUDE.md`.

## The project docs

Plain markdown throughout, cross-linked with relative links rather than wikilinks so it renders wherever it is read — on github.com or the GitHub mobile app, where mermaid renders and there is nothing to pull.

## Worktree isolation

Several sessions run at once, a worktree each — herdr puts its own at `~/.herdr/worktrees/<repo>/<branch>` and Claude Code puts its own at `<repo>/.claude/worktrees/<name>` — and every name two of them agree on is shared state: one compose project is one database, one host port belongs to whichever session bound it first, one Electron profile is one lock file.

portless is the machine's rather than a project's, `"npm:portless"` in mise's global tool list. Its own README asks for the global install, and the reason is that all three of the things it owns exist once: the proxy holding port 443, the certificate authority signing for every `.localhost` name, and the routes registered in `~/.portless`. mise's npm backend is that global install without `npm install -g`'s flaw: the package lands in mise's own install directory rather than inside whichever node was current, so a node upgrade does not take it along, and the lockfile pins it like any other tool. `install.sh` trusts the CA, once: the check is `security verify-cert` against `~/.portless/ca.pem` rather than `portless doctor`, which reports trust in prose with no machine-readable form, and a missing certificate means portless has never run at all. Doing it there is what keeps portless from asking for a sudo password in whichever session starts a dev server first; it reads from `/dev/null` so a sudo that wants a password fails instead of holding an unattended provision open, and it is never fatal — an untrusted CA costs a browser warning, not a shell. Over SSH it is not attempted at all: adding a certificate to the system trust store puts a confirmation dialog on the Mac's own screen as well as a sudo prompt on the terminal, so `install.sh` sees `SSH_CONNECTION` set and prints the one line to run in Terminal over Screen Sharing, `portless trust`.

Port 443 on `127.0.0.1` is root's on macOS, and a session has no terminal to answer sudo from, so a proxy that is not already running is one the first dev server of a session cannot start: portless exits rather than falling back. The proxy therefore runs as portless's own LaunchDaemon, `sh.portless.proxy`, installed once by hand with `sudo portless service install` and the TLD list below. It is the one root daemon this repo depends on and does not own, because launchd will not take a system job from a symlink in a user's checkout. The daemon records the absolute paths of the node and the portless that installed it, both under mise's versioned install directories, so a `mise up` of either leaves it pointing at a file that is gone; `install.sh` reads both paths back and prints the reinstall command when one is missing.

Dev servers open from the MacBook under a name of their own, `https://<branch>.<app>.timche.dev`, the same shape as the `.localhost` one. `.zshenv` sets `PORTLESS_TLD=localhost,timche.dev`, so the one proxy serves every route under both; `.localhost` stays first because `PORTLESS_URL` takes the first TLD. A wildcard record at Cloudflare points `*.timche.dev` at this Mac's tailnet address, DNS only, which is harmless in public DNS since nothing off the tailnet can reach it. Resolvers with DNS-rebinding protection, NextDNS among them, return nothing for a public name pointing at such an address, so the tailnet's DNS settings route `timche.dev` to Cloudflare's `1.1.1.1` as split DNS, and a tailnet device gets the answer on any network. And `install.sh` has Tailscale Serve hand the tailnet's port 443 to the proxy as raw TCP: portless keeps TLS and routes by hostname, and the MacBook trusts portless's CA once.

A name per app rather than a port per app is the point of the arrangement. Browsers key cookies by host and ignore the port, so portless's own `--tailscale`, which puts every app on the Mac's own `<node>.<tailnet>.ts.net` name and a port each, gives every dev server one cookie jar on the MacBook: two worktrees of one app overwrite each other's session, and an app inherits the localStorage and service worker of whichever app held its port last. Nothing Tailscale offers gives a name per app today — wildcard MagicDNS is in the client but not enabled on the coordination server for any tailnet ([tailscale/tailscale#1196](https://github.com/tailscale/tailscale/issues/1196)), Tailscale Services stop at ten per user, and a tsnet node per dev server makes every worktree a device.

`COMPOSE_PROJECT_NAME` is the one that bites with nothing configured at all, so `.zshenv` sets it. Compose names a project after the directory it was started from, which for a herdr worktree is the branch alone — so `fix-ui` in two repositories would share one project, and with it one set of containers, one network and one database volume. `<repo>-<branch>` instead: the repository from the `origin` remote, for the same reason `project-docs.sh` takes it from there, the branch from `HEAD` or the worktree folder when HEAD is detached, lowercased with everything outside `[a-z0-9_-]` replaced, which is compose's own rule for a name it would otherwise reject. Recomputed on every `chpwd`, because a shell outlives the directory it started in, and unset outside a work tree, which leaves compose on its own default. In `.zshenv` rather than `.zshrc` so that a script, a hook and an agent get the same name a prompt does.

`worktree-info.sh`, a second `SessionStart` hook beside `project-docs.sh`, prints the names the worktree owns and nothing else: the compose project, with the reminder that `docker compose down -v` takes the database with it and that a fixed host port in a compose file is a collision waiting for the second session; portless's URL, `https://<branch>.<name>.localhost` in a linked worktree and `https://<name>.localhost` in the main one, which is portless's own rule; and, for an Electron project, that a dev run takes a user-data profile named for the branch and a debug port of `0`, read back from `DevToolsActivePort` in that profile. Each line only when the project has the thing — a compose file at the worktree root, a `package.json` script that runs portless, `electron` among its dependencies — and a project with none of the three prints nothing at all. Where the name cannot be derived with certainty it is not guessed at: portless resolves a workspace root against the packages under it and rewrites a branch name that is not a hostname label, so for either the hook says that `portless list` prints the URL rather than printing a URL that might not exist.

It reads the worktree from the `cwd` field of its own stdin. `CLAUDE_PROJECT_DIR` is documented as staying at the directory the session started in rather than following it into a worktree, and `CLAUDE_ENV_FILE`, the other way to hand a session a name, is unreliable across `/clear`.

Cleaning up after a removed worktree is a garbage collector, `hachiko gc`, rather than a hook on the removal, because no removal reliably hands us one: herdr removes worktrees, so does Claude Code, so does `git worktree remove` by hand, git has no post-remove hook at all, and Claude Code's `WorktreeRemove` does not fire for a git worktree ([anthropics/claude-code#94212](https://github.com/anthropics/claude-code/issues/94212), open). Registering `WorktreeCreate` and `WorktreeRemove` would be the wrong trade even if it did: the docs say configuring them *replaces* Claude Code's own `git worktree` behaviour rather than adding to it, so a hook that cleaned up would also own creating the worktree.

So the trigger is time. Three of its six sweeps are about a worktree that is gone, and none runs unless it is: a compose project whose `com.docker.compose.project.working_dir` label points inside a worktree root that no longer exists, with `com.docker.compose.project.config_files` as the second opinion, removed with `docker compose -p <name> down -v --remove-orphans`; the named volumes that project left behind; and a process whose current directory is a removed worktree, SIGTERM and then SIGKILL ten seconds later. The label rather than `docker compose ls`, which reports the config files alone and so misses a project started with `-f` or from a file named something else. Inside a worktree root — `~/.herdr/worktrees/<repo>/<branch>` or `<repo>/.claude/worktrees/<name>` — and nowhere else, which is not the same as a folder that does not exist: a daemon shared with another machine reports projects whose working directory was never on this disk, and `down -v` on one of those deletes a database over a path that only looks missing. It never touches pid 1 or its own process tree, never signals a process another account owns, holds a `mkdir` lock of its own at `~/Library/Caches/hachiko-gc.lock` — not the watch's, so a sweep and a check never wait on each other — takes over a lock older than the interval or one whose holder has gone, and answers `--dry-run` by printing what it would do.

The volumes are the one thing no label can decide, because a volume carries only `com.docker.compose.project` and nothing about the folder: `repeek-main_postgres-data` is the main checkout's database, which looks exactly like a worktree's. So the sweep writes down every compose project it sees with a container inside a worktree root, and which worktree, in `~/Library/Caches/hachiko-gc/state.json`; a named volume no container is using goes only when its project is in that record and the recorded folder is gone. A project never seen running in a worktree is never touched however its volumes are named, an anonymous volume is never touched at all, and a record is forgotten once its worktree is gone and nothing of the project is left.

The other two are about a session that is over rather than a folder that is gone. Claude Code gives every session a scratch folder, `${CLAUDE_CODE_TMPDIR:-~/.cache/claude-tmp}/claude-<uid>/<project-slug>/<session-id>/`, and removes none of them, so the sweep removes one whose name is a session id, that no running session claims, and that nothing was written under for a week. Live is what `~/.claude/sessions/<pid>.json` says, by the pid in its name rather than by the record being there, since the record outlives the process. The week of grace is for `claude --resume`, which reuses the folder, and herdr resumes every session it had after a restart. A project folder goes with `rmdir` once the last session folder in it has, so anything else left in it keeps it, and anything not named like a session id is left alone — `bash-edit-diff` and `tasks` beside the session folders, `cc-socks` and `tart` a level above them.

The last is `git worktree prune` in every repository directly under `~/projects`, which is `HACHIKO_GC_PROJECTS` where a check needs it somewhere else. git's own prune rather than a rule of this script's: it drops the metadata of a worktree whose folder git cannot find and nothing more, so a session still working keeps its entry, and it reports what it pruned on stderr with `-v`, which is where each line of the log comes from. A `.git` directory rather than a `.git` file, since the file is what a worktree has.

The sixth is the one pass that is about nothing having been left behind, and the reason it is here rather than anywhere else: docker's build cache and the images nothing refers to grow whether or not a session ever ended, and neither of them goes when a worktree does. So `docker builder prune --force --filter until=168h` and `docker image prune --force --filter until=168h`, once a day (`HACHIKO_GC_PRUNE_EVERY`), with the age as docker's own `until` filter takes it (`HACHIKO_GC_PRUNE_AGE`, passed as written since the format is docker's to decide) — a week, because a layer from this morning is one today's build is about to want. Never volumes, never containers, never networks, which is why it is two commands rather than one `docker system prune`: a volume here is somebody's database and goes only by the rule above. And no `-a`, so an image a project still names by tag stays however long it has been since anybody built with it, the next build having only to pull it again.

Once a day rather than every ten minutes because the first prune of a day reclaims what the ones after it would have, and a prune walks every layer and cache record the daemon has: six an hour would be a hundred and forty subprocesses to be told nothing a hundred and thirty-nine times. When it last ran is in the sweep's own state, written to that file before either command runs rather than left to the save at the end of the sweep: these two are the longest-running thing the sweep does, and a sweep killed or timed out between them is exactly the one that never reaches that save and would prune again ten minutes later. One line in the log with the space each half got back, nothing at all where both got nothing, and the next prune is as soon as there is a daemon again where docker was down — being down spends no day. A prune that exits non-zero is a failure like the rest, with one difference: the nine sweeps an hour that did not prune are not sweeps where it has started working, so what is open stays open until a prune actually runs.

Routine cleanup is a log line and nothing else; what reaches the Discord channel is only what the sweep could not do — a compose down or a volume removal that exited non-zero, a process still there after SIGKILL, a folder that would not go, a worktree prune or a docker prune that failed. One message per distinct failure while it persists rather than one every ten minutes, with a 🟢 line in the same thread when it clears — sent as that incident's outcome, so the post is retagged `Resolved` and closed, and goes with the rest three days later — and the dedupe lives in the state file beside the record of the projects. Docker being absent or its daemon down is not a failure and says nothing at all: a Mac with OrbStack stopped has no containers to sweep.

A LaunchAgent runs it, `io.github.timche.hachiko-gc`, with `RunAtLoad` for what the machine lost while it was off and `StartInterval` 600, which is the whole of the trigger. There is no `WatchPaths`: it is not recursive, so a worktree at `~/.herdr/worktrees/<repo>/<branch>` is two levels below anything a watch on that root would see, and Claude Code's worktree roots are per repository, which no single path watches — a removal is caught by the next sweep rather than by a write. So the plist is a symlink into this checkout like the agents beside it, with `/bin/sh -c` exporting the PATH and opening the log before it `exec`s the wrapper, and `install.sh` loads or reloads it as it does the others. The log is `~/Library/Logs/hachiko-gc.log`, and a sweep that finds nothing writes nothing to it.

What the sweep cannot report is not running at all, so it writes the time it finished into `~/Library/Caches/hachiko-gc/last-run` and the five-minute check reads that stamp's age — over an hour, `HACHIKO_GC_STALE`, and one ⚠️ says so with the `launchctl kickstart` that starts it again. It is one of the three agents the watch checks the liveness of the same way; [hachiko](#hachiko) has how that reads and why nothing is said on a Mac with no gc plist.

## The herdr server

Every Claude Code session is a pane of one herdr server, and that server is started by launchd inside the logged-in GUI session, `io.github.timche.herdr`, rather than by the first `herdr` a remote client runs. Tim attaches from the MacBook with `herdr --remote`, which runs `herdr remote-client-bridge` over Tailscale SSH and only talks to the server's socket, so where the server was started decides what its panes are. Started over SSH, every pane carries `SSH_CONNECTION`, `SSH_CLIENT` and `SSH_TTY`, and Claude Code withholds computer use from such a session: the built-in `computer-use` server is missing from `/mcp` although every documented condition holds, and appears once those three variables are unset. Anthropic documents none of this, and the strings in the binary put the three names among its terminal-identity checks, beside "[computer-use] terminal not detected; falling back to sentinel host", which fits computer use needing to find the terminal it keeps out of its screenshots. From launchd, a pane is genuinely a local session, and macOS asks its privacy grants of this job rather than of `tailscaled`.

What the job starts is not herdr but the launcher, `~/.local/libexec/herdr-launcher`, which runs `~/.local/bin/herdr server` as its child. It is there for one reason: a privacy grant is pinned to the exact contents of an ad-hoc signed binary, herdr's release binary is ad-hoc signed, and every `herdr update` therefore cost all of [the grants](#privacy-permissions) and an afternoon of Screen Sharing to give them back. TCC asks the responsible process, which for a launchd job is the job's own process and for that process's children is it again, so the grants belong to the launcher and herdr may change underneath as often as it likes.

Which is why the launcher is the parent and never execs herdr — an exec would put herdr's contents back in front of TCC — and why, being a parent nothing else needs, it has to behave as though it were not there: it forwards `SIGTERM`, `SIGINT` and `SIGHUP` to herdr, and exits with herdr's status or dies of herdr's signal, so `KeepAlive` and `launchctl bootout` see exactly what they saw when the agent ran herdr itself. `test/assert.sh` proves both halves — the signals against a fixture herdr, and the attribution by running the launcher under a throwaway `launchctl submit` job whose child reports the pid macOS holds responsible for it.

It is C, one file in `launchd/`, and `install.sh` compiles it to that fixed path when the SHA-256 of that file no longer matches `~/.local/state/mac-mini/herdr-launcher.sha256`, and otherwise leaves it entirely alone. Deliberately not the build-in-place wrapper the Go tools use: that rebuilds whenever its sources move and against whatever `go` mise resolved that day, and a rebuild for any reason at all is new bytes and so a dropped grant. A build is therefore a re-grant, which the install says out loud, and the only ones there should ever be are a fresh Mac — where the grants have to be given anyway — and a deliberate change to the launcher. It is compiled under its final name, because the ad-hoc signature the linker writes takes its identifier from the output's basename and that identifier is part of the bytes, and moved into place with a rename, because writing over the binary launchd is running fails outright.

`KeepAlive` is unconditional, unlike the sync agent's, because a missing server — even one stopped on purpose — would otherwise be replaced by the next remote client starting its own over SSH. `install.sh` loads the agent but never boots it out or restarts it: it usually runs inside one of that server's panes, and restarting the server ends every session on it, the one running the script included. A server already running outside launchd, or a plist changed since launchd read it, is reported with the commands to run from a shell outside herdr, a plain `ssh timche@mac-mini`, once no session needs the server. A Mac with no launcher built is one where the agent is left unloaded and reported instead, since a job pointed at a binary that is not there is one launchd retries every ten seconds for the life of the Mac. The log is `~/Library/Logs/herdr.log`.

What stays unsolved either way is approval: computer use asks for each app once per session, in the session's own terminal, and nothing pre-approves apps for a session nobody is watching ([anthropics/claude-code#47796](https://github.com/anthropics/claude-code/issues/47796), closed without it).

## Projects and 1Password

A project that resolves its secrets with `op run --env-file .env.op -- <cmd>` gets the same token from `~/.local/bin/op`, a wrapper ahead of Homebrew's `op` on PATH, so the project never learns how `op` signs in and the same command works on a Mac where the 1Password app does it. When `OP_SERVICE_ACCOUNT_TOKEN` is unset and the token file is readable, it sets the variable for that one `op` process and nothing else, where exporting it from `.zshenv` would put it in every process and so in transcripts and logs. `op run` hands its own environment to the command it starts, so for `op run` the wrapper puts `env -u OP_SERVICE_ACCOUNT_TOKEN` right after the first `--`; a command that calls `op` by name comes back through the wrapper and is signed in again. This keeps the token out of projects and build tools' environments rather than away from the account, which can read the file anyway. The scripts here read the file themselves and do not depend on it.

`.zshenv` and `.bashrc` set `DO_NOT_TRACK=1`, the cross-tool opt-out at donottrack.sh, so no CLI a session runs sends usage analytics or writes an install id.

Signing and notarising a macOS build is the project's own configuration, in a `.env.signing.op` it runs the build under, rather than a wrapper here: meru resolves its Developer ID certificate, its notarisation credentials and its provisioning profile that way.

## hachiko

`hachiko` watches the two failures a Mac with no screen cannot notice, every five minutes from the `io.github.timche.hachiko` LaunchAgent. Named for Hachikō, the Akita who waited at Shibuya station every day. The other thing a Mac with nobody at it needs looking after is in [Worktree isolation](#worktree-isolation): `hachiko gc`, on a ten-minute agent of its own, sweeping what a removed worktree and a finished session left behind. `hachiko sync` is the third, a long-running agent that commits and pushes what gets written in the project docs and in this repository's `home/.claude`; [Auto-sync](#auto-sync) has it. `hachiko update` is the fourth, and the one thing on this Mac that moves a version: the five-minute check starts one a night, in [Updates](#updates). One binary, one command and one package each. `hachiko status` is the odd one out, in [One screen of it](#one-screen-of-it): nothing runs it on a timer, it is read by a person or a session in a terminal, and it only reads.

The first is a process that lost something it retries on and is logging the mistake into a file nothing bounds — a worker whose Redis went away writes the same connection error a few hundred thousand times a second, which is tens of gigabytes an hour into a path somebody chose because it was convenient. On a machine somebody is sitting at, the fans say so; on this one the first symptom is a build failing for want of space, hours later, with the disk already full. The second is a process still spending a core on work nobody is waiting for, which is what a worker left behind by a session that ended looks like.

It is one of the repository's compiled tools, a Go module in `hachiko/` built in place by the wrapper in `~/.local/bin/hachiko`; [Layout](#layout) has how that works and why there is nothing to install. Standard library only, so the binary the agent runs depends on nothing — not mise, not Homebrew, not a runtime — which matters because a Mac whose tooling has broken is exactly a Mac worth watching. `go test ./...` in `hachiko/` is its behaviour: the clock, the free-space reading, the file walk, the process sample, `lsof`, herdr and the sender are all injected, so every rule below is checked without filling a disk, waiting an hour or opening a session.

What it reads: free space on the Data volume from `statfs`, which is what `df` reads without the parsing, and every regular file over a gigabyte under `/private/tmp` and `$HOME`, staying on one volume and pruning `.git` and `node_modules` — walked sixteen directories at a time; the walk and the process sample together take about a second. A file that has gained two gigabytes since the last sample is growing fast, and `lsof` names the process writing it. Growing fast is not on its own an alert: what the files found growing are gaining between the two samples, against the free space they are eating into, has to put the volume within six hours of full (`HACHIKO_FILL_HOURS`) before anybody is woken for it, and otherwise the log says what is growing and how long the space would last. Free space already under 20 GB is the exception, where the growth is the emergency rather than the evidence for one and every path below behaves as if there were no horizon. Sizes are the allocated ones, from the block count rather than the apparent length, because a VM's sparse disk image is apparently hundreds of gigabytes it is not occupying.

What it does not read is the whole of `~/Library` except `Logs` and `Caches`, and `~/Desktop`, `~/Documents`, `~/Downloads`, `~/Movies`, `~/Music`, `~/Pictures` and `~/Public`. Under launchd an unsigned binary is its own TCC-responsible process with none of the grants a herdr pane has, and what it meets in those folders is not a refusal: a folder behind Full Disk Access answers "operation not permitted" at once, but one behind a consent prompt makes `open()` wait for a dialog on a screen this Mac does not have — so the sweep never returns, never releases its lock, and the machine's only monitor is the thing that is stuck. `~/Library` goes wholesale because it is every other app's data and macOS guards it under Device Control and Data Access; `Logs` and `Caches` are walked as roots of their own, being the machine's own output rather than anybody's. None of this can be discovered at runtime, because the same binary run from a session walks all of it fine — which is why `test/assert.sh` runs one sweep through `launchctl submit` and asserts it finishes, raises no dialog, and leaves no unanswered request in `tccd`'s log.

Behind that list is a deadline, because the next folder macOS decides to guard should not cost the Mac its monitor either: a directory that has not answered in three seconds is abandoned, named once in the log and remembered in the state file so later runs skip it without waiting, and the walk as a whole gives up after a minute so the CPU check and the alerts still run. Both of the calls that touch a directory are inside that deadline — reading it, and asking which volume it is on, which is an `lstat` that hangs just as readily on a mount whose server has gone away, and `~/OrbStack` is NFS.

A skip is not permanent, because a read goes slow under disk pressure and disk pressure is exactly what a runaway writer causes: a directory that stopped answering is tried again an hour later, which costs one more three-second wait if it is still gone, and if it answers it is put back in the walk and said so once. Otherwise one slow read during the incident this exists for would have blinded the watch to `/private/tmp` for good.

CPU is the difference in cumulative CPU time between two samples over the wall clock between them, from one `ps -A` for the whole machine, taken in the C locale because the start date it prints is half of a process's identity. Never ps's own `%cpu`, which on macOS is a decaying average over the process's whole life: it understates a worker that has just gone wrong and overstates one that has finished. A process is reported when it has held half a core or more across every interval for an hour, which is twelve intervals of five minutes and so thirteen samples; a sample that comes in low starts the hour again, and because the window is a span of time rather than a count of runs, an interval the agent missed costs nothing. Identity is the pid and its start time together, since a pid is reused and the history behind one belongs to whoever held it. `~/.config/hachiko/cpu-allow` is a glob per line for the things expected to burn a core here — the OrbStack VM, a UTM guest, Spotlight, Time Machine, a macOS update, the window server — and hachiko never reports its own process tree.

Who owns a hot process is read out of the same `ps` sample, `uid` for anything that decides by it and `user` for the message, since macOS keeps its daemon accounts in Directory Services rather than in `/etc/passwd` and `ps` is the only thing here that can resolve one. A process of this account's whose parent is launchd and whose working directory is inside `~/projects` or a worktree root is called out as left behind by the session that started it, which is the shape of a worker whose session is gone; everything else with a parent of launchd is called a system process owned by whoever owns it, because every daemon launchd starts has ppid 1 and calling one orphaned describes how macOS starts daemons rather than anything being wrong with it. A hot process that is not this account's also gets a line of its own in the first message and in the brief, naming the owner and the one command that would deal with it: `sudo /usr/local/libexec/claude-root restart-daemon <name>` when the daemon is one the [root helper](#the-root-helper) allows, which costs no password, and otherwise the `sudo kill` it would take and the fact that launchd starts most daemons again. The allowlist is read out of the installed helper rather than copied here, by string equality against the name `ps` reported, so a daemon Tim adds to it is named in the next alert and a process cannot talk its way into a command. The helper's command is the one sudo the session's limits allow, and one of the few fixes it may carry out before anybody has answered, since the helper restarts nothing off its list; a `sudo kill` stays on the never list, so that line is Tim's to decide on and the session's only to recommend.

The thresholds: under 100 GB free, under 20 GB free, a gigabyte to be worth watching, two gigabytes of growth between samples, six hours from full for that growth to be worth an alert, half a core for an hour. Each is an environment variable (`HACHIKO_LOW_GB` and the rest), which is what lets the tests trip the same arithmetic with megabytes and minutes rather than filling a disk to prove it.

One message per incident per state change. A file still growing is the same incident until it stops, low space stays one alert until free space is back over 100 GB, and 20 GB is an escalation that is allowed to say so once. A hot process is one incident for as long as it stays hot, and a disk and a CPU incident in the same run are one message and one session.

Under 20 GB free, hachiko truncates the fastest growing file, and only that one: the biggest offender or nothing, since a check working its way down the list would reach a file that is somebody's. Only under `/private/tmp`, the Claude Code scratch root or `~/Library/Logs`, and only when the name ends `.log`, `.out`, `.err` or `.output` or contains `.log.`. Never an `rm` and never a `kill`: the writer keeps its descriptor and its offset, so a log it appends to goes on working and the space comes back at once, where an unlinked file frees nothing until the writer exits and a killed worker takes a session's work with it. What to do about the writer is a decision for a person.

Every sweep also caps this machine's own logs, which is the other half of a disk nobody is watching: an agent that runs for ever writes for ever, and what the thresholds above catch is the emergency rather than the drift. Six files, by exact path and never by pattern, all under `~/Library/Logs`: over 10 MB (`HACHIKO_LOG_CAP_KB`) one previous generation is kept as `<name>.0`, replacing the one before it, so each log is bounded at twice the threshold. One line in the log per cap, nothing to Discord — this is hygiene rather than news — and one `lstat` per file on a sweep with nothing to cap, which is nearly all of them.

Each of them is copied and then emptied in place rather than renamed, which is the thing newsyslog gets wrong: against a writer holding the descriptor, a rename-and-recreate leaves the writer appending to the archive and the empty file at the path never grows enough to be rotated again, so rotation there is worse than doing nothing. And every one of these has such a writer — `herdr.log`, `hachiko-sync.log`, `hachiko-listen.log` and `mochi.log` for the life of the Mac, `hachiko.log` and `hachiko-gc.log` for the length of a sweep, each opened with `>>` by the shell in its plist, so the writer's next line lands at nothing rather than leaving a sparse hole, and it never knows. Between the last byte copied and the truncate the writer may append a line, and that line is lost — accepted, because the window is microseconds, these are logs read only when something is wrong, and the alternative is stopping the writer, which for herdr is every session on this Mac.

A copy fills `<name>.0.tmp` and only becomes the generation on the way out, with an exclusive create and a rename, because the thing that makes a log worth capping — a disk with nothing left — is also what makes a copy fail halfway. Writing the generation directly meant a failed copy had already destroyed the one good copy of the log and left half of it in its place, at the worst possible moment to lose it; now a failure leaves the generation before it exactly where it was and takes its own half-written file with it. A copy left behind by a sweep that was killed between the two is this sweep's to take back, the name being hachiko's own, and anything at that path that is not a plain file is what the exclusive create refuses to go round. The generation keeps the log's own permissions, so it is readable by whoever could read the log and no wider.

A cap that cannot happen is said once and not again until that log caps: the full disk, or the link somebody left, is still there five minutes later, and the watch runs twelve times an hour for ever. The state remembers which logs are owing a complaint, and forgets one the moment the log is capped or is nothing to complain about.

Nothing follows a link at any of the three paths. These are account-owned paths and hachiko runs as the account, so there is no privilege to be had through one of them — that was the whole reason this is hachiko's and not the [root helper](#the-root-helper)'s — but a write through a link somebody swapped in is still a write nobody asked for: all three are `lstat`ed and a link at any of them is refused and said so, the copy is one `O_RDWR|O_NOFOLLOW` descriptor so the file read is the file emptied, and both files it writes are opened `O_NOFOLLOW` too.

Every message has one shape, and `hachiko/internal/wording` is the whole of it: a lead line — one marker, a space, and one short plain sentence, which is all a lock screen shows and all a forum post's name holds — then `**Label:** value` lines for the findings there were and a `- ` bullet each where there are several, then the one thing Tim can do, then the incident id and the machine as Discord subtext, which is the one line in it he never acts on. One blank line between each of those and the next, because Discord renders consecutive lines as one block of text and a message of four findings is read on a phone; inside one of them nothing is spaced, so a label keeps its own bullets and a bullet keeps its continuation line. Six markers and no others: 🔴 critical with nobody acting, 🟢 clear again, ⚠️ degraded or a deadline coming, ℹ️ nothing wrong, 💾 the disk, 🔥 a process on the CPU. Sizes read "4.3 GB", rates "about 52 GB an hour", durations "1 hour 5 minutes", times "at 17:20" or "yesterday at 17:20", a process "dasd (pid 147)"; a path or a command line is in an inline code span whose fence is a backtick longer than the longest run inside it, so a file named with one cannot style the rest of the message. A name that has to read as prose rather than as code — the lead's, a process's, the account that owns it — is escaped instead, character by character, because a worker called `[Fix it](https://wherever)` would otherwise arrive as a link Tim is invited to click and one called `**You can run:**` as a line of hachiko's own. Not in the post's title, which Discord renders as plain text: the title is the lead line with that escaping taken back out. The standing orders hold the session to the same shape, so a thread reads as one voice rather than as a watch and an agent taking turns — and `shibuya/src/message.ts` is that file's counterpart on the other side, since the two post into the same channel. `go test -run TestMessages -v ./...` in `hachiko/` prints every message there is to read end to end.

Alerts go to a private Discord forum through a bot, which is the one way anything hachiko has to say leaves the Mac, and the same token is what reads a reply back out of the thread it opened; see [Answering from Discord](#answering-from-discord). Its token is the `bot token` field of the `hachiko-discord` item in the `dev` vault, referenced from `home/.local/bin/hachiko.env.op` beside the wrapper and resolved by `op run --env-file` only when there is something to send, since every run counts against the service account's daily limit. The token reaches one process and one request header: `op run` re-enters the binary with `--send`, which reads the message on stdin and posts it with `net/http`, so it is in no command line `ps` shows the machine and in no file — and net/http's own error text is redacted before it reaches the log. A send that fails leaves the incident unraised, so the next check tries again rather than going quiet about it; a channel nobody has configured is one of those failures rather than a message quietly dropped.

What hachiko cannot notice is itself not running, so every sweep checks in with [shibuya](#shibuya), which is a Worker rather than anything on this Mac: the reading when the sweep read what it meant to, and a failure when it ran and came back knowing less than it should. A quarter of an hour without one is shibuya's message to send.

The other agents it can notice, and does, in one table-driven check: the worktree sweep, sync, the Discord listener and [mochi](#mochi) each write a file as they go, and the age of that file is the whole of what the watch knows about one. Each reports its own failures, and what nothing can report about itself is not running at all. None of them is an incident and none opens an on-call session — the one answer is the `launchctl kickstart -k gui/<uid>/<label>` the message carries, and it is Tim's — so it is one ⚠️ naming the agent's own log, and a 🟢 in the same thread when it comes back. The thresholds are an hour for the sweep, which is six of its own intervals (`HACHIKO_GC_STALE`), and ten minutes for the other three (`HACHIKO_SYNC_STALE`, `HACHIKO_LISTEN_STALE`, `HACHIKO_MOCHI_STALE`), which is longer than a whole retry ladder against an unreachable remote and longer than the five minutes the listener's agent and mochi's throttle a restart by.

Nothing is said at all where the agent is not there to be running, which is the only way to tell a Mac that was never meant to run one from a Mac where it has stopped: a fresh Mac has no stamp because nothing has ever run, and alerting on that would fire on every machine this repository provisions until `install.sh` reached the agent. For the sweep, for sync and for mochi, which ships configured, that is the plist, and where the plist is there and no stamp is, the clock runs from the plist's own modification time — so an agent that was installed and never ran is caught rather than excused. The listener is the one with no such fallback: it writes a heartbeat only once a channel and a user are configured, and answering from Discord ships off, so a missing heartbeat is the feature being off rather than a listener that died. A listener with nothing configured removes its own heartbeat on the way into that idle state, which is what keeps an alert already open on it from standing for the life of the Mac with nothing left to answer it.

Once the feature is on, every way out of the listener that is not the poll is a listener which has stopped, and each of them leaves the watch something to find too old: one whose token stopped resolving keeps the heartbeat it has, and one that has never once polled at all — no `op` to resolve the token with, no env file naming it, a vault that will not answer — writes one where there is none, so the ⚠️ fires ten minutes later rather than never. Only where there is none, which is the whole of it: launchd starts that agent again every five minutes for as long as it keeps exiting, and a heartbeat rewritten on each of those starts would be the one alert here that can never fire.

The beat itself is a pass that found Discord answering, and not a pass that happened. A token Discord rejects, or a permission taken off the bot, is a listener that polls for ever and reads nothing, with every reply Tim sends reaching nobody — and the only thing on this Mac that could notice is the heartbeat it stops writing. A thread whose last read failed counts as one it cannot reach, and so does a thread inside its backoff: with up to five minutes between tries, almost every pass of a failing listener is a pass that asked nothing, and reading those as healthy is what would let a rejected token keep its heartbeat. Nothing open is not trouble, which is also the limit of what this can see — there is no thread to read, nothing is asked of Discord, and a token it would reject is not found out until an incident gives the listener something to read.

The exception is an agent that goes while the watch has an alert open on it, which gets one ℹ️ in that same thread saying it is no longer installed, and then nothing further. Silence under a ⚠️ is the one thing this watch never leaves, and an agent being removed answers "it has stopped" as much as its coming back does — without that line the last word in the thread is a warning about something that has since ceased to exist.

`~/Library/Logs/hachiko.log` is the log, one line per thing that happened and nothing at all on a quiet check. `hachiko --dry-run` reports what a check sees and changes nothing, `hachiko --test-alert` proves the way out to Discord, and `hachiko --help` has the rest.

### One screen of it

`hachiko status` is the command nothing on a timer runs: one screen for a person or a session in a terminal, saying whether the machinery above is healthy without reading four logs and running a `launchctl print` each. Five sections, a few lines apiece — the agents, free space, what the watch has open, every repository sync keeps upstream, and the logs it caps. Plain text in columns, and colour only where stdout is a terminal, and then one colour meaning one thing: this is degraded. A pipe gets none, because the first thing done with the output is to grep it or paste it into a message.

Each agent is two readings rather than one, since they answer different questions: `launchctl print gui/<uid>/<label>` says whether launchd has the agent at all and the pid when it is running something this minute — an agent on an interval has none between runs, which is not the same as not being there — and the stamp says whether it is doing its job. The stamps, their thresholds, the labels and the logs come from the same table the watch decides liveness by, so a screen cannot say an agent is fine while the watch is alerting about it. The watch's own agent is on the list and is the one with no threshold, because nothing on this Mac can tell whether the thing doing the checking is running; the screen says so and names [shibuya](#shibuya). launchd's output is parsed defensively — a whole key matched, the first match taken, anything unparsed read as an agent running nothing — since that block is nested, undocumented and launchd's to change.

The incidents are the watch's own words, out of its state file: what it has open and since when, which tab the on-call session is in, and the three things it says once and then remembers having said — an agent that has stopped, a repository sync is getting nowhere with, and a log it could not cap. An alert nobody was ever told about is not an open alert and is left out. The repositories are measured again instead, by two read-only git commands apiece and a read of sync's own record of a conflict, because what sync wrote down is what it has told Tim and what this screen answers is what is true now. A limited repository's row names the paths it is limited to, since every other cell in it is measured inside those and nowhere else in the checkout. Late is the watch's own rule, the repository's `push_delay` plus `HACHIKO_SYNC_LATE`, for the same reason the thresholds are one table.

Both of those commands, and the watch's own two, run `git --no-optional-locks`, because read-only is not the same as lock-free: a plain `git status` refreshes the index and takes `index.lock` to do it, and the repositories being read are the ones `hachiko sync` is committing in every few seconds. A screen somebody opened to see whether sync is working, or a check asking whether it has fallen behind, may not be the reason a commit fails.

It only reads. No state is written, the watch's lock is never taken — a sweep holds that one across a herdr call and an `op run`, so a screen that waited for it would hang for minutes — nothing is sent anywhere, and `op` is never called, since a screen somebody opens twice a day may not spend the service account's day. It exits non-zero only where it could not run at all: a reading it could not take is a line in its own section, because this reports problems rather than being one more thing that has them.

### The on-call session

An alert that says a file is growing is a page in the middle of the night that still needs somebody to read a process listing. So hachiko opens a Claude Code session to do the reading: `hachiko oncall <name> <brief-file>` puts a tab in the herdr workspace for this repository, with this checkout as its directory so the session starts with the machine's own instructions loaded, and starts an agent called `oncall-<name>` in it. herdr rather than a `claude -p` of its own, because Tim attaches to the same server from anywhere with `herdr --remote`, the session is still there hours later, and an agent waiting on `AskUserQuestion` shows in his sidebar as `blocked` — which is the point, since everything the session may not fix by itself ends in a question for him. Never focused, since he may be in the middle of something, and one session per incident name: a second alert while the first is still being worked is an update to that session rather than a second agent on the same disk.

That update does not always land. herdr refuses a prompt to an agent that is already waiting on a question, and waiting on a question is where the standing orders leave an on-call session that could not fix what it found — so the commonest second alert of an incident would reach nobody. What hachiko does instead is cancel the question: `herdr agent send-keys oncall-<kind> esc`, then `herdr agent get` to see that the agent really did leave `blocked`, and then the prompt. The order is the whole of it, since a prompt sent first is one herdr refuses and a step recorded as delivered is one never tried again, and the esc is read back rather than assumed because `send-keys` answers for the keys reaching the pane and not for what the agent did with them. The options in the old question were about the incident as it stood when it was asked, so the session asks again with ones that fit what it is now. Only when the question survives the esc does the old path stand: the message names the tab, says the update was not delivered, and carries the whole of the detail, because nothing in that tab is going to read it for him. The same goes for a session that started but that the brief never reached — the tab is named rather than left unmentioned, and nothing waits ten minutes for a report that cannot come.

The model is Opus at medium effort, passed through to Claude Code as `-- --model opus --effort medium` on the `agent start`. It is the only thing reading a process listing at four in the morning, and the only thing deciding what to do about what it read.

What reaches the channel either way is one message per state change. A truncate is the exception that always sends: it is the one thing here that changes somebody's disk, so it is an incident of its own even on a run where the file was already flagged and the threshold was already crossed.

What the session is handed is a prompt whose orders come first, then the findings between two markers carrying a nonce that prompt alone knows, then a line saying that was the data. Everything in that block — a path, a command line, a log line quoted back by `lsof` — was chosen by whatever filled the disk, so it is the one part of the prompt an attacker writes: the fence is what keeps a file named "ignore your orders" from reading as a turn in the conversation, backticks go out of it, and nothing inside it can spell the end of it. Paths and arguments are clipped on the way in for the same reason Discord's 2,000 characters are respected.

The order the alert goes out in is the session first, then one short line from hachiko — what fired, and that an agent is looking into it in a named tab. The session investigates read-only, and its first duty is to send its own message: what is happening, the cause as far as it knows it, and then either the one fix it is about to carry out or the options it is about to offer and which one it recommends. It sends that with `hachiko notify <incident> <file>`, which is the only way anything but hachiko reaches the channel and which is handed no URL of its own. That command takes no lock and writes no state: a sweep holds its lock across a herdr call and an `op run`, which together can outlast the five minutes the session is told to report within, so the report leaves a marker and the next sweep is what clears the incident. Then it either carries out the one fix described below or waits in `AskUserQuestion` with two to four options, recommendation first. Afterwards it sends the outcome as `hachiko notify --outcome <incident> <file>` and writes a note under `$PROJECT_DOCS_DIR/mac-mini/incidents/`. That flag is on that one message and no other, which is the whole of how hachiko tells the message that resolves an incident from the several a session sends while it is still waiting; `--outcome` is a constant word rather than anything of the incident's, so it is one of the few things here allowed to be an argument, and `--attempt` below is the other.

The fallback is why hachiko speaks first and keeps its own details. The session depends on herdr being up, on a Claude login and on usage being left, and a watch that only ever spoke through an agent would be silent exactly when that chain broke. So: if the session cannot be started, the first message carries the full raw details and says so; if a session started but has not reported ten minutes later, hachiko sends the details itself and says the agent did not report; and under 20 GB free, or after a truncate, the first message carries the whole of it immediately rather than waiting for anybody to finish reading.

Three kinds of incident reach a session, and the third is nothing like the other two. A disk filling and a core burning are measured every five minutes and fixed by stopping something; a step [the nightly update](#updates) could not do is measured by nothing at all and fixed by a version. So an `update` session reads before it fixes anything: the failure it was handed, `~/Library/Logs/hachiko.log` for the run it came from, the step's own code under `hachiko/internal/update` in this checkout and what the tool itself says about its own state. Then it makes the one attempt below, and what it may run for it is the step again or `hachiko update` — `hachiko update --dry-run` for the readings alone — a run from inside a herdr pane working because the step that updates herdr drops herdr's own variables for that one command. The markers it may write and the orders it is given are shaped for it, the autonomy below among them.

### Nobody answers

A question in front of a sleeping man is not a resolution. Whatever the session could not fix itself, it asks about and then waits — and if Tim is asleep or in the middle of something, the options go stale, the writer goes on writing, and the incident is never closed by anybody. So the wait is a timeline rather than an open end, and at the end of it the session decides.

hachiko reads where the agent is from `herdr agent get oncall-<kind>`, one call per kind per check. `blocked` is the whole of how it knows nobody has answered yet, and the clock starts when a check first sees that rather than when the brief went out: the wait being measured is his, and until the agent has asked him something there is nothing for him to answer.

What ends a wait is something that says what happened, and an agent that has left `blocked` is not one of them. Tim picking an option, hachiko's own `esc`, and a session that gave up on its turn are one reading from herdr, and ending the wait on it closed an incident on the strength of hachiko's own cancel and then told nobody. So the three endings are a `hachiko notify --outcome`, which is the message that says the incident is resolved; a session Tim closed, which there is nothing left to hand anything to; and the handover followed by the same minutes of silence the session was given to report its findings in. Only that flag ends it the first way, because a session sends more than two messages — its analysis, the same question posted into the Discord thread, an update when the situation moves — and reading any second report as the outcome ended the wait on the strength of a message saying the question was still open.

A session that was briefed and has not got as far as a question keeps its wait for an hour, and the clock starts whenever that first `blocked` sighting comes. The ten-minute deadline above is for its first message and not for its question — the question comes after the reading — and a wait dropped at that deadline threw the whole timeline away for a session that asked two minutes later.

So answering in herdr is not by itself an answer as far as hachiko is concerned. Picking an option there and leaving the session to it reads exactly like the two things that are not an answer, and the timeline goes on until the session says what came of it with `--outcome`. That is the right way round: what he picked still has to be carried out, and nothing but the session knows whether it was.

In between, an agent that is `working` is working on his answer or on what hachiko handed it, and nothing goes out on top of that while the turn is fresh: no reminder, no warning, no handover over the work hachiko asked for. That pause is the minutes a session is given to report in and no more, because a turn hung on a tool call reads as `working` for as long as the Mac is up and a wait that deferred to it without limit would have no reminder, no warning and no handover at all — the silence the whole timeline exists to prevent, reached through the one state that looks reassuring. The early handover is the exception the pause does not hold, since a disk that will be full before he wakes does not wait for a tool call either.

An agent with no question up and nothing in flight keeps the timeline running, with each step sent as a prompt alone: there is no question of its own to cancel, and an `esc` to an agent that is not on one takes away whatever it has started. An unblock hachiko did not cause gets the same few minutes first, in case it is him answering with the agent between turns; one hachiko caused itself gets none, that being the reading none of this trusts.

Every way a wait ends with no outcome reported posts one line saying so, and so does a handover that reaches nobody — once per incident, however long it goes on failing. Without those, the last word in the channel about an incident nothing resolved is the warning that the agent would decide in a quarter of an hour, and nothing after it.

A marker merges with the one before it rather than replacing it, so a later message that happens not to repeat the `If no answer:` line keeps what the last one said — overwriting lost the option the warning has to quote. And that line is read as a line of its own, the last of them: a session quotes log lines into its report, and anything looser handed Tim an option chosen by whatever filled the disk.

At an hour, a short reminder with this check's numbers — free space, what the file is now and how fast, what the process is spending — and the tab it is still waiting in. At two hours forty-five, a warning that in fifteen minutes the agent will act on its own, quoting the option the session itself named. At three hours, the question is cancelled and the session is told to decide. Each step sends once and only once it has actually sent: a Discord that was down for the one check an hour came up on tries again on the next rather than losing the step, and a step that fires marks the earlier ones done, so a check coming back after an outage does not send an hour's reminder about a question already past its deadline. Nothing of hachiko's own goes to the channel at the handover itself — the session's own message is what says what it did and why, and two messages about one decision would be one too many.

The `esc` that cancels the question is read back until the agent has actually left `blocked`, for about five seconds. send-keys answers for the keys arriving in the pane and not for what Claude Code did with them, and the real herdr was measured answering `blocked` on the first read after the `esc` and `done` 152 to 160 ms later: one read, taken straight afterwards, is what concluded that the question was still up and sent no prompt at all. When the `esc` lands and the prompt that was to replace it does not, hachiko remembers owing that prompt and the next check sends it on its own — a second `esc` would cancel whatever the session has started since, and there is no question left to cancel. The standing orders say the other half of it to the session: a question cancelled while it waits is hachiko's doing and not Tim declining, and hachiko's prompt follows.

Three attempts in a row that do not land are the end of it until the agent is seen off its question. An `esc` that keeps failing is a question taken away every five minutes with nothing put in its place, and an agent sitting on one herdr will not cancel is the one state nothing can be delivered in at all — so the messages to Tim go on, the line the failed handover posted is what names it for him, and nothing of the agent's is touched again until there is no question there.

Three hours is Tim's number: long enough that he is asleep rather than busy, short enough that a disk losing 90 GB an hour has not taken it. Reminders and the handover carry numbers re-measured on the check they go out on rather than the ones the question was asked with, because an answer to a three-hour-old question is about a machine that has moved.

Which option the warning quotes is the session's own. Any message of its that leaves something for Tim to answer has to carry a line reading `If no answer: <the single option you would take>`, and `hachiko notify` reads that line out of the message rather than taking it as a flag of its own. It is a line Tim reads too, so stating it to him and stating it to hachiko are one act — and nothing the session writes about an incident goes in a command line, where every process on the machine reads it and a path chosen by whatever filled the disk would be an argument. The marker the report leaves is where it is kept until the next sweep picks it up.

A question in front of a sleeping man resolves nothing, so the session fixes one thing before it asks anybody. Which fix depends on the kind. On a disk filling or a core burning it is emptying or deleting files under `/private/tmp`, the Claude Code scratch directory or `~/Library/Logs`, and inside a project's own log or tmp folder only files whose name says they are a log — `*.log`, `*.out`, `*.err`, `*.output` or `*.log.N`, which is the same rule the truncate above obeys and for the same reason: a project's tmp folder holds a build somebody is waiting on as readily as a log, and "its log folder" is a licence to empty the log files in it rather than the folder — or running the [root helper](#the-root-helper)'s `restart-daemon` for the busy daemon, exactly as the brief gives it and never spelled by the session, because a daemon loop is the incident the helper exists for and forbidding it left dasd spinning through two nights with the fix one passwordless command away. Stopping a process is not among them, whatever it is costing: a kill takes whatever the process was halfway through with it, and nothing in a reading of the disk prices that, so it waits for Tim or for the handover. On a failed update step it is the step run again or `hachiko update`, a tool reinstalled or rolled back through mise or brew, or the configuration or code fix in this checkout — made in a worktree, tests green, as one commit pushed to `main`, which is what every session here does and so needs nothing of him.

One attempt per incident, and an attempt is one change plus the reading that says whether it worked: the step run again, or the numbers taken again. If that reading says it did not work, the session puts its own change back where it can — `git revert` of its commit, the version it replaced reinstalled — and hands the incident to Tim with what it tried, what it saw and two to four options with its next idea first. The second attempt is where a fix on a machine nobody is looking at starts making the incident worse, so there is not one: the message that goes out before the change is `hachiko notify --attempt <incident> <file>`, which records the attempt in the wait, and every prompt that reaches the session after it — a question cancelled and asked again, the handover, his reply out of Discord — says that the attempt is spent. Only Tim picking something gives the session anything further to carry out. A fresh incident of the same kind gets its own attempt, because a disk that filled again after the log was emptied is a new fault with a new reading behind it.

What it may do at the three-hour handover is then one thing more: stopping the process or processes causing the incident, SIGTERM and then SIGKILL only if it is still there ten seconds later. Always the least destructive thing that actually resolves it, and if the only effective fix is on the never list, nothing destructive happens at all: it says which fix it is, why it stopped, and goes on waiting. All of it is in the opening prompt rather than only in the prompt that hands it over, so the session knows from the first minute what it would be allowed to do and can name the option while the whole incident is still in front of it.

The never list is the same for every kind and whatever has been handed over: any sudo but the root helper's `restart-daemon` as the brief gives it and its `reinstall-portless`; deleting or emptying anything outside those three roots and a project's own log files, `~/Library/Caches` included, since hachiko's own state directory and the binary the wrapper builds are in it; a force-push, a branch deleted, or a push to any repository but this one and any branch but `main`; an edit under `~/.claude` or `home/.claude`, which is every session's configuration and the on-call session's own permissions with it; restarting herdr, the Mac or a launchd job other than through the root helper; a live Claude session's processes, unless that process is itself what is causing the incident, in which case it is that pid and never a name every session answers to; and anything that touches 1Password. Deleting or modifying source outside that one fix, a repository, a database or a docker volume, and a merge or a deploy, need him too — and on an update incident, his approval code. That code reaches what is his rather than what is on the never list: the hook refuses a never-list action however it has been approved, so one of those is a command he runs himself, and the session's part is to say exactly what it is.

That list is a hook rather than a paragraph, because these sessions run under `bypassPermissions` and now act before anybody has read what they decided to do. `hachiko oncall` creates the tab with `--env HACHIKO_ONCALL_SESSION=<kind>`, so the marker is in the environment of Claude Code, of every subagent it spawns and of every hook run for either — all of them one process tree — and `home/.claude/hooks/oncall-guard.py` is a `PreToolUse` hook on `Bash`, `Edit` and `Write` that exits before reading its own stdin in every session without that marker. For a marked one it reads the command, refuses anything on the list with exit code 2 and the reason on stderr, which is the refusal that stops the call before the permission rules — which in one of these sessions allow everything — are read at all, and which the agent reads as the denial reason. The daemons it will allow under sudo are read out of the installed helper, like the brief's own line, so a daemon Tim adds to it is one the guard allows the same night. A guard against this session's own mistakes and not a sandbox: the account already has root by other routes and writes the hook itself, so what it has to catch is the plausible wrong move at four in the morning rather than a determined one, and where a rule cannot be read off the command — whether the brief really gave that daemon, whether the one attempt is already spent — the orders and the partner hold it instead.

Every session, marked or not, also runs `home/.claude/hooks/kill-by-pid.py`, a `PreToolUse` hook on `Bash` that denies `pkill`, `killall`, `fuser -k` and a `kill` whose pids come from `pgrep`, `lsof`, `ps`, `netstat` or `ss`, since every session runs its own copy of the same dev servers and a name, pattern or port reaches all of them. It reads the command the way the shell splits it, so a mention in quotes goes through, and lets through anything it cannot parse rather than cost every session its shell.

Every autonomous decision gets a second pair of eyes before it happens, the one attempt included. The session spawns `oncall-partner`, a Fable agent with Read, Grep, Glob and Bash and a prompt that forbids anything but inspection, hands it the incident and the action it proposes, and acts only if it agrees. On the attempt a disagreement means nothing is carried out and the incident goes to Tim with both views; after a handover it means the less destructive of the two proposals where both are inside the limits, and otherwise nothing destructive at all. The message after acting says the partner reviewed it and what it found, and quotes the limit the action was allowed under, so what was permitted is in the record rather than in somebody's reasoning. An answer from Tim needs no partner — he is the authority the partner stands in for.

The handover reaches no update incident. There is nothing to project about a step that failed and nothing a crossed free-space mark says about one, and once the session's own attempt is spent nothing on this Mac retries the step again — retrying is moving a version with nobody watching, which is the one thing here that happens only on the schedule Tim set. So its clock is the reminder at an hour and then one line at two hours forty-five saying that nobody has answered and that nothing retries it, quoting the option the session named, which for one of these says what is left rather than what it would do: usually that tomorrow night's run tries the step again. Nothing is handed over at three hours and nothing further is sent, the question stays in front of him, and what resolves it is his answer in the thread or in herdr — or the step working on a later night, which is the update's own 🟢 into that post and the end of the wait. A session he closes and a herdr nothing can reach end it the way they do for any other incident.

Two things cut the three hours short, because a disk that will be full before he wakes is not something to wait out. hachiko projects, each check, how long until free space reaches 20 GB at the faster of the two rates there are to go by — what the files it can see are gaining, and what the volume is actually losing, which catches a writer the walk never found — and hands over early when that comes before the handover would or inside the hour, whichever is sooner. Two checks in a row have to say so, because that is an extrapolation from one interval and one interval is where every way of being wrong lives: one burst of writing that stops by itself, a volume somebody freed and refilled, a sample taken late. Five more minutes is nothing against three hours, and a single subtraction is not enough to hand a session the authority to stop a process. A span the check had to invent rather than measure is no projection at all — a Mac that slept, or a clock somebody set, divides a real growth by a made-up second and says the disk is about to go — so the projection is skipped outright on one of those. The other trigger needs no rate and no second opinion, being a measurement rather than a projection: a quarter of the free space there was when the question went up is gone. The numbers are hachiko's, since it is the only thing sampling the disk every five minutes while the agent sits on its question; the judgement is the session's. It may agree that waiting costs more than acting and act, or decide the writer is about to stop by itself and ask again with fresh options — and it says which it chose either way. An early handover is its own step and not the deadline's: a session that judged waiting safe and asked again still has three hours coming, which is what the clock was for.

Short of a handover, a question that has gone stale is cancelled and asked again rather than left standing: a file that has doubled since it was asked, a free-space threshold crossed in either direction, or a writer that was not there before. Only against writers that were actually recorded, since a file between writes when the question went up has none and the next one found would otherwise look new on nearly every incident. The three-hour clock keeps running from the first question through all of it, and so does a new alert for the same kind: he has been unanswered since then either way, and a writer that worsens every hour would otherwise push the deadline out for ever. The steps do reset with a new incident, because the handover is a decision about an incident and each one gets its own.

An incident that has stopped by itself is the one piece of news that comes before everything on the clock and outlives a handover already made. A check that finds nothing growing fast enough to reach the end of the volume with free space over every threshold, or nothing over the CPU share, hands the session that reading the way it hands it a change: verify it against the machine rather than taking the reading for it, and if it really has resolved, report the outcome and close. Two checks in a row have to say so, the same rule the projection above obeys and for the same reason: one interval is a writer between bursts or a daemon between runs as readily as an incident that is over, and what this hands the session is a reason to close one. Said once per incident, because every check after the first says the same thing about the same quiet Mac, and never off a reading that is missing rather than clear — a walk that ran out of its seconds saw part of the disk, a directory it was told to skip may be holding the very file the question was asked about, and a check with no process sample saw no processes. Without any of it a daemon that stops spinning by itself leaves a session waiting on a question about a process that is no longer there, and nobody is told until somebody asks.

The last way this ends badly is a session Tim closed. An agent herdr has never heard of is gone rather than an error, and at the deadline hachiko says so itself: no agent left to decide, nothing was done, and the numbers as they stand.

herdr not answering at all is neither an answer nor a closed session, so one check that cannot reach it leaves the wait exactly as it was — a server being restarted or a configuration being reloaded is not something to wake anybody about, and the next check asks again. An unbroken run of them is the other thing entirely: there is no session to remind, nothing to hand a decision to and no way to tell whether anybody answered, so after the same minutes a session gets to report in, one line says the session cannot be reached and nothing is being worked, and the wait stops being counted. Any answer at all ends the run, so an outage that came back and went again is two outages, each measured from itself.

### Answering from Discord

Reading a reply is the half that is optional, and off until the config file names the account it is taken from. Attaching to herdr from a phone is three minutes of work and reading a message is none, so the question is answerable in the thread the alert is already in — one reply, or one digit.

What this needs is `~/.config/hachiko/discord`, which ships empty: a `channel` and a `user`, both Discord snowflakes and neither a secret, which is why they are a file in the checkout rather than a 1Password reference. Anything in there that is not a snowflake is read as nothing, since both end up in a request path. The channel is what every message goes to, so a Mac with none configured has nowhere to send an alert at all; the account is what reading a reply needs on top of it, since a channel with nobody named behind it would be a listener that obeys anybody who can see it.

The two secrets are `HACHIKO_DISCORD_BOT_TOKEN` and `HACHIKO_APPROVAL_TOTP`, `op://` references in `home/.local/bin/hachiko.env.op` beside the wrapper, which is the one env file hachiko has: `op run` is given it whenever there is something to send or a listener to start, and it refuses a reference it cannot resolve, so both fields have to exist on the item before either command works. The token reaches one process's environment and one `Authorization` header, and every error text that leaves the bot has it taken out first.

A bot that will not post — a token Tim revoked, an application somebody deleted, a channel the bot was removed from — is a send that failed, and there is nowhere else for the message to go. The error goes to the log and the incident is left unraised, so the next check sends it again rather than the watch going quiet about a disk filling because of a permission. A thread that could not be opened is the other way round and not a failed message at all — the message is already posted, so the rest of that incident goes to the channel rather than being sent a second time.

One incident, one thread. The channel is a forum one, so that thread is a post and the first message of an incident is the message that opens it: one `POST /channels/<forum>/threads` carrying the post's name, its tags and the message together, and the post's id — which is the starter message's id as well — is what comes back. On a text channel it is two calls instead, the message and a thread started from it. Which of the two it is comes from Discord rather than from the config file, `GET /channels/<id>` and a `type` of 15, one extra call per incident and nothing to get wrong in a file; a channel whose type could not be read is treated as a text channel, and a forum that then refuses a plain message is a send that failed, which the next check tries again. Either way every message after the first — the session's analysis, the reminder, the warning, the outcome — goes inside, so a reminder three hours later is under the alert it is about. The thread id is in the state against the incident, which is how `hachiko notify` finds it without taking the lock, and once nothing is pending or waiting on that incident it moves to a list of closed threads, so the listener stops polling it, and stays there for a week: a wait can end before the session reports, when its question went away with the session, and the outcome it sends hours later still goes under the alert rather than opening a second post.

The forum's two tags are what makes it readable at a glance, and they are found by name on the channel Discord describes rather than by an id written down here: the ids are the forum's own, and one in the source would tag whatever a forum rebuilt from scratch happens to have in that slot. A post is opened tagged `Open`; the message that says the incident is over — `hachiko notify --outcome`, whose flag travels to the `--send` child as an argument with the thread and the channel, being one word and nothing of the incident's — takes `Open` off, puts `Resolved` on and archives the post, which closes it without locking it, so what is left open in the forum is what is still running. A tag the forum does not have is skipped rather than an error: the alert is the point, and the forum is Tim's to set up. The retag comes after the message and never before it, because Discord unarchives a thread anything is posted into; and it is reported rather than returned, since the message has already gone out and a label that would not go on may not reach the session as a report that did not send. The archive is nothing to the listener: Discord still answers a bot reading an archived post's messages, and by then the incident is closed, which has already taken its thread out of the list being polled.

`hachiko listen` is the half that reads. Its own LaunchAgent, `io.github.timche.hachiko-listen`, with `KeepAlive` because the poll is the job: a reply is worth seconds rather than five minutes, and a process sitting in a poll has no business holding the lock the sweep needs. It writes nothing the sweep owns — the threads it polls come from the state read-only, and what it remembers about them is files of its own. It re-enters itself under `op run` so the token is resolved once per start and not once per poll, which is what keeps a five-second loop off the service account's daily limit. Unconfigured, it exits at once and the plist's five-minute `ThrottleInterval` is what it costs: one start and one exit every five minutes, no network, no `op`, and a line in the log only when that state changes. It writes down what it last said so that turning the feature on or off gets a line and nothing else does — a line per start would be a line every five minutes for the life of the Mac about something that is not wrong.

While it is polling it writes a heartbeat into `~/Library/Caches/hachiko/listen/heartbeat` every half minute, beside what it already keeps there and in no file the sweep owns, and the five-minute check reads its age the way it reads the sweep's stamp and sync's. Only while it is polling, and the two ways it stops polling are not the same thing. With nothing in the config file nobody asked for replies at all, so it removes that heartbeat on its way into the idle state and the check reads the feature as off rather than as a listener that died ten minutes ago — which also gives an alert already open on it something that clears it. With a channel and a user set and only the token unresolved, somebody does mean replies to work: that is a listener which has stopped, so the heartbeat is left exactly where it is to go stale and be reported, and the ⚠️ points at `~/Library/Logs/hachiko-listen.log`, where the line it wrote on the way in says the token is what failed.

It also exits when the wrapper has built a new binary behind it, the way `hachiko sync` does, since neither has an interval of its own and nothing would otherwise run an edit to the listener until the Mac restarted. The exit falls between passes and never inside one: a pass that has taken a reply off Discord has already marked it seen, so one abandoned halfway through would drop the reply it was handing to the session. `KeepAlive` is unconditional here rather than `SuccessfulExit`, because both of the ways this listener exits on purpose are clean ones. `ThrottleInterval` counts from one start to the next rather than from the exit, so a listener that has been up longer than five minutes — which a configured one always has — is restarted at once; only a replacement inside the first five minutes waits out the remainder, which is the gap the heartbeat's ten minutes has to cover.

Every five seconds it asks each open thread for the messages after the highest id it has seen — an id and not a time, so a listener that was down for an hour reads what it missed. They come back sorted by snowflake, which is a timestamp, rather than reversed on an assumption about which order Discord sent them in: it documents newest first for a plain fetch and oldest first for an `after`, and guessing wrong hands the agent a conversation backwards and remembers the oldest id as the newest. Only messages whose author is the configured user count: everybody else in the channel is somebody who can see it, the bot's own messages are hachiko talking to itself, and an instruction to an agent with authority over this Mac comes from the one person who owns it. Every message is marked seen whether or not it could be acted on, or one Discord will not let the bot react to would be handled for ever.

A thread that will not answer — no permission on it, or Tim deleted it — is backed off, doubling from one poll to five minutes, and said once rather than every five seconds. One line when it stops answering, one when it starts again, and nothing in between: the same rule the rest of this log is written to, and twelve identical lines a minute would bury the ones that matter.

A reply reaches the session the same way everything else does, cancel-then-prompt, with his words fenced and the marker labelled as his rather than as incident data: the fence keeps an instruction out of a log line and keeps one in here, and the agent has to be able to tell the two apart. A bare number is read as the option he picked and said so in the prompt. It is the answer the standing orders were waiting for, so the clock stops on its own — the agent leaves `blocked` with nothing having recorded a nudge, which the next sweep reads as him having answered, because he has. An agent that is not on a question is prompted without an esc and the reply queues behind what it is doing. He gets a tick on his own message, or a line in the thread if the bot cannot react.

The never list still needs him, and a Discord account somebody has taken over is not him. So an action on that list needs a code as well: the session registers the one action with `hachiko approval-request <incident> <file>`, posts in the thread what it is asking to be allowed to do, and he replies `approve` with the six digits from his authenticator. The code is checked here — RFC 6238, SHA-1, thirty seconds, one step either side — against a secret the session is never given, and the approval it is told about names the action it registered rather than whatever it has decided since. One request, one approval, and the step a code belonged to is remembered and refused the second time, because a code is good for thirty seconds and would otherwise be good for all of them. Three wrong codes and the request itself is cancelled: six digits over three steps is about one chance in a thousand a try, which is hours rather than years for an account somebody has taken over, and that is no protection at all when what it reaches is deleting a repository. The session then has to register the action again, which it cannot do without saying in the thread what it is asking for, where Tim can see it. The count is against that action, so asking to be allowed something else starts from nothing. A code with nothing open to approve and a wrong code are answered with the same four words, since a hint is a hint to whoever is trying codes.

A post about an incident that is over goes three days after it was resolved (`HACHIKO_POST_KEEP`), which the watch does once an hour — housekeeping rather than watching, and it costs an `op run`. It is the one thing hachiko does that cannot be undone, so what may go is narrow and every part of it is read off Discord rather than off hachiko's own state: the post is in that forum, it carries the `Resolved` tag, it is archived — which is what closed means on a forum — and its archive timestamp is older than that. So an open incident is never touched, nor a post somebody reopened by writing in it, nor anything in a forum with no `Resolved` tag. Only the closed listing is read, since an open post cannot be resolved, and it is paged through to the end. A post Discord refuses to delete is one line and left alone: it would refuse again in the same way, and a retry loop would spend the sweep on one post. [shibuya](#shibuya)'s posts go the same way, being in the same forum with the same tags.

Setting it up: a Discord application with a bot, the Message Content intent turned on, invited to the private server with permission to read messages, send them, send them in threads, create public threads, manage threads, add reactions and read message history; a forum channel with an `Open` tag and a `Resolved` one; a `bot token` field and an `approval` one-time-password field on the `hachiko-discord` item in the `dev` vault; and the channel and user ids in the config file. `updates` beside them is a plain text channel for [the nightly update](#updates)'s summary, which is not an incident and has nothing to answer; without it that summary stays in hachiko's log. Manage Threads is the one that is easy to miss and the one that tags and closes a post — a post's tags are not something its own author may change without it. The `approval` reference is the field's own value rather than `?attribute=otp`, which is the current code — hachiko verifies codes itself, so it needs the secret, and it reads either the `otpauth://` URI or a bare base32 string, since which of them `op` hands back for a one-time-password field is 1Password's business rather than this one's.

## Updates

Nobody is at this Mac, so it keeps itself up to date: `hachiko update` moves its tooling forward once a night and deals with what each upgrade leaves behind. It is the one thing here that moves a version. `install.sh` deliberately does not — it applies the `Brewfile` with `--no-upgrade` and installs mise's tools `--locked`, which is what makes a re-run after every pull safe — and mise holds a release back for its default day: the global config sets no `minimum_release_age`, so `mise up` and `mise self-update` alike take a version once it is 24 hours old, which is long enough for a broken or hijacked release to be pulled and short enough that the Mac is never more than a night behind. A version a lockfile records is installed as recorded, however new.

The five-minute [hachiko](#hachiko) agent starts it rather than a LaunchAgent of its own, since an agent that fires once a day skips the day on a Mac that was asleep at four in the morning. So the schedule is a stamp in a state directory of its own — past 04:00 local (`HACHIKO_UPDATE_HOUR`), and the last run that finished was before 04:00 today — and a Mac that was off or asleep catches up on its next check instead. What the check starts is a process of its own: an upgrade takes tens of minutes, the check it would otherwise run inside has five, and [shibuya](#shibuya) reports a Mac offline a quarter of an hour after its last check-in, so an update held inline would page Tim about a Mac that is busy updating. A lock of its own keeps the next check from starting a second one, and one left behind by a run that was killed is taken over after two hours — or at once, where the pid the lock records is no longer running, since a lock is held by a process rather than for a span of time and the age is only the stand-in for asking it. The age rule stays for a pid that still answers, because pids are reused and one that answers may be somebody else's process entirely.

The steps, in order, each of them reported:

- **mise**, with `mise self-update`, since mise comes from its own installer and nothing else on this Mac can move it.
- **The tools mise manages**, with `mise up` for the global config and again with `--local` for this repository's own `mise.toml`, each naming its directory because mise decides what is active from the directory it is asked about and a LaunchAgent starts in `/`. What moved is read off `mise outdated` either side of the upgrade rather than off what the upgrade printed.
- **The lockfiles that rewrote**, committed and pushed to `main`. `~/.config/mise/mise.lock` and `~/.config/mise/locks` are symlinks into this checkout, so upgrading the global tools writes this repository's own files, and a lockfile left on the Mac would mean a rebuilt Mac installing whatever `latest` meant on the day. Every git command is limited to those paths and `mise.lock`, so nothing a session has staged or left dirty here is added, committed or pushed; and nothing is committed at all unless `main` is checked out and the tree is nobody's to finish, since a commit on a session's branch would go up inside their pull request.
- **portless's proxy daemon**, through [the root helper](#the-root-helper), when node or portless moved. The daemon is root running a path with a version in it and launchd reads its plist once, so a `mise up` that moved either leaves root running a file that is gone — and with it every `.localhost` and `.timche.dev` URL on this Mac.
- **Homebrew**, with `brew update`, `brew upgrade` for formulae and casks, and `brew cleanup`. A cask that will not upgrade stops `brew upgrade` partway, so what moved is read off `brew list --versions` either side of it. The cleanup is the one failure worth expecting: `sudo brew services start` takes root ownership of the keg it runs tailscaled out of, so the first cleanup after a tailscale upgrade meets a root-owned directory — and the message names the one `sudo rm -rf` that clears it.
- **tailscaled**, restarted through the root helper when its formula moved, because launchd reads a plist at bootstrap and the plist names the `opt` symlink rather than a version. Then `tailscale status --json` is read back for up to a minute, and a backend that is not `Running` is an incident: this Mac is reached over the tailnet.
- **herdr**, with `herdr update`, for the reason mise is its own: the update replaces the binary it runs from. The server is left alone — restarting it ends every session on this Mac — and it takes the new binary whenever it next starts, which the summary says.
- **oh-my-zsh**, with `git -C ~/.oh-my-zsh pull --ff-only`. A clone that cannot fast-forward has somebody's commits in it, and merging them is not a decision to make at four in the morning.
- **macOS**, which is the one it only reports. `softwareupdate --install` of a macOS update on Apple silicon wants a volume owner's password — `--user` with `--stdinpass`, both documented as Apple-silicon-only — and this Mac has no MDM to authorise one in its place. Nothing here may hold Tim's password, so `unattended.sh` leaves macOS downloading updates and not installing them, and the summary says what is waiting for him.

What moved goes to the `updates` text channel as one summary, and a night where nothing moved says nothing at all, the way the rest of hachiko does; without that channel configured the summary stays in `~/Library/Logs/hachiko.log`, which has the whole of every run either way.

A step that failed is an incident in the forum every other alert goes to, with [an on-call session](#the-on-call-session) on it — and the update posts nothing about one. It records what it is failing on, and the next five-minute check raises it: one post per incident, with the thread, the session, `hachiko notify`, Tim's reply out of Discord, the raw details if nothing reports and the reminders all belonging to the half of hachiko that already has them. All of one run's new failures go in one incident, kind `update`, because they are one night's news and one session's reading; a step that keeps failing is raised once and no more, since it fails again every night and nightly messages about it are ones Tim stops reading. The line saying a step works again is the update's own, because it is the only thing that ever knows one does, and it goes into that post's thread as the incident's outcome, which closes it.

The hand-off is two files, each with one writer, because the two hold a lock each and an update holds its across however long brew takes. `~/Library/Caches/hachiko-update/failing.json` is the update's: a statement of which steps are failing and since when, with the phrase, what the command said and the one line for Tim, rewritten whole on every run. `~/Library/Caches/hachiko/update-raised.json` is the check's answer: which incident each of those steps was raised as, and the thread of its post. So the check raises what is in the first and not yet in the second, the update reads the second for the thread to clear into, and a step that leaves the first is one nobody is waiting on any more — which is what ends the wait on its incident. A Discord that was down all day loses nothing, since neither file is a queue.

`hachiko update --dry-run` is the explicit "what would move", and takes the readings without changing anything. `hachiko update` is the explicit "update now", for a session that has been waiting on a fix upstream rather than on four in the morning.

## shibuya

`shibuya` is hachiko's dead man's switch, and the one piece of this repository that does not run on the Mac. Named for the station Hachikō turned up at every day, which is the whole of what it does: hachiko checks in after every sweep, and a quarter of an hour without a check-in is a message in the same Discord channel the alerts go to.

It exists because a watch cannot report its own silence. A LaunchAgent that never loaded because the Mac is sitting at its login window, a sweep hung on a mount whose server went away, a Mac that lost power, a binary that stopped compiling and left the last one that did — every one of those is hachiko saying nothing, which is also what a quiet Mac looks like. The only thing that can tell the two apart is something off the machine.

A Cloudflare Worker with one SQLite-backed Durable Object per host, which is the only kind the free plan runs, and the object's alarm is the deadline. `idFromName(host)` is how a host gets its own, so the Mac that checks in is the Mac that is reported missing; hachiko sends the Mac's name on the tailnet, the first label of `tailscale status --json`'s `Self.DNSName`, rather than its hostname, which the router can change under a running Mac and which shibuya would read as this Mac going offline. The last name the tailnet gave is kept in `~/Library/Caches/hachiko/host` for a sweep while tailscale is not answering, a Mac never on a tailnet falls back to its hostname, and `HACHIKO_HOST` overrides all three. The name is reduced to that shape — the first label, lowercased, anything else a hyphen — and a name is validated as `^[a-z0-9-]{1,32}$` before it reaches a storage key. The cost is about three hundred requests a day against a hundred thousand, and nothing runs between them.

Five routes. `GET /` answers `shibuya` with no token and no data, because something has to answer a browser. `POST /ping` carries the reading — free space, open incidents, busy processes, the commit the running binary was built from, and what the Mac is called — and `POST /fail` carries a reason instead; both count as a check-in, since a sweep that ran and went wrong is a sweep that ran. `GET /status` is for Tim: where a host stands, with ISO timestamps, and `DELETE /host` is for Tim too, forgetting one. The four that are not the root take `Authorization: Bearer <ping token>`, compared with `crypto.subtle.timingSafeEqual` against a secret and answered with `401` and nothing else; the method is part of the route, so anything else on one of them is a `404`, and a body over four kilobytes is refused unread. A call the Durable Object does not answer is a `503` and `try again` rather than Cloudflare's own 1101 page — which is what a deploy that has reached this Worker and not yet the object it calls looks like, for the minutes in between — and hachiko reads that as a check-in that did not land and retries on its next sweep.

The alarm is the switch. A check-in arms it a grace ahead of itself — `GRACE_MINUTES`, fifteen — so the alarm that fires is the one no check-in replaced. When it does fire, a forum post is opened titled `🔴 Mac mini offline · <day and time in Europe/London>`, carrying the last check-in's time and its reading, and the host is marked down. One alert per outage: nothing re-arms while it is down, beyond a single reminder six hours later in the same post — and the forum, not the object's memory, is what says the outage already has one, so an alarm retried after a write that did not land finds the post it opened and goes into that. The check-in that comes back posts the recovery into that post — `🟢 Mac mini is back — it checked in after 42 minutes of silence`, and what it came back to — and clears it. The forum's two tags work as they do on hachiko's own posts: an outage post or a failing streak's is opened tagged `Open`, and the message that ends it — the recovery, or the run that came back clean — is followed by `Open` off, `Resolved` on and the post archived, so what is left open in the forum is what is still wrong.

What the Mac is called is the check-in's to say: hachiko sends `display`, cut to forty characters and stripped of anything a terminal would act on, and shibuya uses it in every post title and every lead line. Without one it falls back to the host slug, which is a storage key spelled by whatever the router called the Mac rather than anything a person would write. The slug is still in the one line of each message nobody acts on, beside the build, and `GET /status` answers with both. The shape of a message here is `shibuya/src/message.ts` and it is the shape `hachiko/internal/wording` writes, because the two post into one channel; the six of them render in full in `npm test`.

A failing streak is the other half, and it is a streak rather than an incident per sweep. The first `/fail` opens a post of its own, `⚠️ Mac mini: hachiko's checks are failing · <time>`, with the reason; the ones after it post nothing, since a sweep that fails every five minutes for an hour is one thing wrong, with one reminder at the hour. A clean sweep says so in that post and closes it. What hachiko reports as a failure is the honest set — a walk that ran out of its seconds and saw only part of the disk, a check with no process sample, a state file it could not read — and all three are faults of the watch rather than of the Mac.

Discord is reached through shibuya's own bot, `shibuya`, rather than hachiko's: the name on a message is what tells what the watch says from what the thing watching the watch says, and a token kept on Cloudflare reaches nothing but this forum rather than the bot that takes Tim's replies to an on-call agent. It posts the way hachiko's sender does. The first message of an incident is one `POST /channels/<forum>/threads` carrying the post's name, the `Open` tag and the message; every message after it is a `POST` into the post; a post Tim deleted answers `404` with code `10003` and the message that found it gone opens another under the incident's own name. The forum is `DISCORD_FORUM` in `wrangler.jsonc`, a channel id and no secret, and its tags are found by name on the forum Discord describes, a tag it lacks skipped. Posts are opened to auto-archive after a week rather than hachiko's day, because Discord stops listing a post as active once it has archived, and an active post is how shibuya finds one again.

The forum's open posts are the answer to whether an incident already has a post. Before a message opens one, shibuya lists the server's active threads and looks for a post in this forum that the bot itself opened, still tagged `Open`, whose name starts with this Mac's name and this kind — `🔴 Mac mini offline · ` or `⚠️ Mac mini: hachiko's checks are failing · `, the same words whichever message opened it — and posts into the newest of those instead. The message that ends an incident closes every such post rather than only the one it went into, `Open` off, `Resolved` on and archived, after the message and never before it, since Discord unarchives a post anything is posted into. So a retried alarm whose write was lost, a thread id that went with a forgotten host, and a duplicate that got out anyway all end in one closed post. A Discord that cannot be listed is today's behaviour rather than no alert: the stored post if there is one, a new post if there is not. A check-in that changes nothing asks Discord nothing, and a label that would not go on is a log line and nothing else — the message is already in the post, and sending it again would be a second recovery. Every message carries `allowed_mentions` with nothing in it, since a reason quotes whatever filled the disk. The bot token is in no log and in no error: `console.log` only ever sees text it has been taken out of.

A Discord that will not answer is the one failure that may not be swallowed, since the alert is the whole point of the alarm. So a message that failed is kept and retried on an alarm of its own, backing off from a minute to half an hour, and the object stays armed until it lands.

`DELETE /host?host=<name>` is how an object stops existing, because one outlives its reason to exist: a hostname typed wrong once has a Durable Object of its own for ever, and a retired Mac's deadline is still armed the quarter of an hour after it is unplugged. It deletes the object's alarm and then everything the object holds, so no outage post, no reminder and no queued retry can follow, and answers `forgot <name>` — or `404` and `unknown host` when there was nothing stored under that name, which makes a second run harmless. Nothing goes to Discord, and a forum post the host is still down in is left exactly as it is: an outage that happened is worth a record whatever became of the Mac. A host that checks in afterwards is simply a new one.

A forget that lands while an alert is still in flight stands, which takes saying because the object's input gate opens while it waits on Discord: the alert resumes into a storage this forget emptied, and the record in its hand would otherwise go back and the deadline with it. So the object counts how many times it has been forgotten, every entry point takes that number before it loads, and the one place that writes drops the write when the number has moved. The count is in memory, which is what makes it right rather than a shortcut — the only write that can be undone is one from a handler already running on this instance, and an eviction that loses the count loses that handler too. Storage could not answer for it either way, since a host just forgotten and a host checking in for the first time are the same empty store.

```sh
# The header goes down a pipe for the same reason it does below: `ps` shows one process's
# arguments to every other on this Mac.
printf 'header = "Authorization: Bearer %s"\n' "$(cat ~/.config/hachiko/shibuya-token)" |
  curl -s -K - -X DELETE 'https://shibuya.timche.dev/host?host=probe-test'
```

One entrance: `shibuya.timche.dev`, a Custom Domain in `wrangler.jsonc` with `workers_dev` and `preview_urls` both off, because a workers.dev subdomain and a version preview URL are each a second hostname serving the same Worker with the same one token in front of it. Cloudflare creates the DNS record and the certificate for a Custom Domain itself, which is why there is no record to manage here and why the hostname must not already have a CNAME on it.

### shibuya's secrets

Three, and they are reached in opposite ways.

`DISCORD_BOT_TOKEN` is the `shibuya` bot's, the `bot token` field of the `shibuya-discord` item in the `dev` vault. `CLOUDFLARE_API_TOKEN` is `op://dev/shibuya/api token`, made from Cloudflare's **Edit Cloudflare Workers** template, which carries both permissions a Custom Domain deploy needs — *Workers Scripts: Edit* on the account and *Workers Routes: Edit* on the zone — and no DNS permission, since Cloudflare makes that record itself. All three are `op://` references in `shibuya/.env.op` beside the code, resolved by `op run --env-file` at the moment they are needed and never written anywhere.

The bot is a Discord application of its own named `shibuya`, with **Public Bot** off — which Discord refuses to save until the application's Install Link is set to None — and no privileged intent, since it reads which posts are open and never what is in them. It is invited to the private server and given, on the alerts forum, View Channel, Send Messages, Send Messages in Threads, Create Public Threads, Manage Threads and Read Message History, and nothing server-wide beyond that: a token that leaks from Cloudflare can then post and tag in that one forum. Manage Threads is the one that tags and closes a post.

`PING_TOKEN` is deliberately neither. hachiko reads it twice an hour for ever, which as a 1Password reference would be two hundred and eighty-eight `op run` calls a day against a service account with a daily limit; and writing a resolved `op://` value into a file is the one thing this machine never does. So it is generated on the Mac instead — `shibuya/secrets.sh`, 32 random bytes of hex at `~/.config/hachiko/shibuya-token`, mode 0600, in no repository and in no vault. What it can do if it leaks is fake a check-in, which is worth the asymmetry; hachiko refuses a token file anything but the account can read, because a loose one is a token every session on this Mac has and the fix is one `chmod` rather than a rotation.

If the token is lost or leaked, delete `~/.config/hachiko/shibuya-token` and run `shibuya/secrets.sh` again: it generates a new one and puts it on the Worker as `PING_TOKEN`, and the old one stops working the moment that lands. Between deleting the file and rerunning the script, hachiko has no token to send and says so once rather than every five minutes, and shibuya posts the Mac offline a quarter of an hour later — which is the honest signal, since nothing is checking in. The check-in that works again posts the recovery into that same post.

The URL is not a secret and is in the checkout, `home/.config/hachiko/shibuya`, one `https` line linked to `~/.config/hachiko/shibuya`. A Mac with no file there is one with the switch off rather than one with a broken switch: hachiko says so once and goes on watching.

### Deploying it

Two steps, in this order, because `wrangler secret put` wants a Worker to put a secret on:

```sh
~/.mac-mini/shibuya/deploy.sh      # creates the Worker and its Custom Domain
~/.mac-mini/shibuya/secrets.sh     # makes the ping token if there is none, then sets the secrets
```

`claude.sh` takes both of them on a fresh Mac, which is why neither has to be run by hand there; the second only when there is no token file, since it makes one and replaces the Worker's `PING_TOKEN` with it, and there is one Mac checking in. Between the two the Worker answers `401` to everything, which costs nothing: no check-in has ever arrived, so no alarm is armed and there is no outage to report.

`shibuya/secrets.sh` is the step nothing re-runs — a token generated on the Mac has nowhere for a later run to read it back from, so `claude.sh` takes it only where there is no token file yet. It makes the token if there is none, then pipes both values into `wrangler secret put` on stdin — never an argument, where `ps` shows every process on this Mac the command line of every other — and prints the names it set. It prompts for nothing, so a provision with nobody watching takes it.

`shibuya/deploy.sh` is everything after that: it installs from the lockfile, runs `npm test`, and deploys under `op run`. `claude.sh` is the one thing that calls it, once, after the signing key has stored the service-account token the `op run` needs — a Mac being provisioned has to come out with a switch, since there is nothing else to notice that it never did. Every deploy after that is run by hand, and no install runs one: an `op run` counts against the service account's day, and the Worker is the live switch rather than something to upload on a timer. It refuses to deploy with no token to resolve the Cloudflare one with, and a deploy that lands with no ping token file beside it says so.

Wrangler rather than Cloudflare's own `cf` CLI, which is in beta and short three things this needs: it cannot set one secret without rewriting the rest, a deploy through it wipes the secrets already set, and there is no vitest pool for a Worker bound to its own Durable Object.

`npm test` in `shibuya/` is its behaviour, and it runs in workerd through `@cloudflare/vitest-pool-workers` against the same `wrangler.jsonc` the deploy reads: the auth, the body limit, every field validated, the alarm a check-in arms, the one post an outage opens and the second alarm that opens nothing, the recovery into that post, a failing streak and the clean run that closes it, the open post found in the forum and posted into rather than a second, every open post closed with the incident, a forum that cannot be listed, Discord answering 404 and 500, and that the bot token reaches no log. `tsc --noEmit` is in it as well as vitest, because a Durable Object's whole interface is a type. The compatibility date is the newest the workerd that pool bundles will start on, so what the tests run against is what the deploy asks for.

To see where it is:

```sh
curl -s https://shibuya.timche.dev            # shibuya, and nothing else

# up or down, the last check-in and its reading. The header goes down a pipe as a curl
# config rather than in -H, because `ps` shows one process's arguments to every other on
# this Mac; printf is a shell builtin, so the token is in no command line either.

cd ~/.mac-mini/shibuya && npx wrangler tail   # what the Worker is saying, live
```

## mochi

`mochi` is Tim's own Claude Tag for Discord. He replies to a message in a server mochi is in and mentions it with an instruction; on this Mac a Claude Code session starts in that server's herdr workspace with `/lead`, his instruction and the conversation around it, and he carries on in herdr. It is a tool of its own rather than a hachiko command, because hachiko is scoped to looking after this Mac: a Go module in `mochi/` with its own wrapper in `~/.local/bin/mochi`, built the way [Layout](#layout) describes, its own LaunchAgent `io.github.timche.mochi` and its own log `~/Library/Logs/mochi.log`. The one link between the two is the heartbeat below.

Unlike hachiko it uses modules: discordgo for everything Discord — the gateway, REST, rate limits and attachments — and `BurntSushi/toml` for its config, both pinned in `go.mod` and `go.sum` and bumped only by a commit that means to; `hachiko update` never moves them. The wrapper hashes `go.mod` and `go.sum` with the sources and builds with `GOTOOLCHAIN=local`, so no Go toolchain is downloaded from inside the LaunchAgent. The modules come out of Go's own cache, which `install.sh` fills with `go mod download`; one missing there is fetched by the build itself and checked against `go.sum`, inside the build's two minutes. `test/assert.sh` builds a copy with only what launchd hands the agent and the network refused (`GOPROXY=off`), which is what proves the cache is enough.

Who and where is `home/.config/mochi/config.toml`, linked to `~/.config/mochi/config.toml`: the one Discord user whose mention does anything, and a `[[server]]` per Discord server mapping its guild id to a herdr workspace label and the repository a tab starts in. Repeek is `1220378778665095291` → `repeek` → `~/projects/repeek`. A mention is of mochi itself or of mochi's own managed role, the one Discord's autocomplete offers beside it, whose tags name mochi's user; no other role counts. The role is read from each guild's roles when the gateway delivers them, kept current from its role events, and fetched once when a message needs it first. A message from Tim that names mochi without either mention is ignored with one line in the log. A mention in a server with no entry is ignored, and so is every author but that user, bots included: what anybody else wrote reaches a session only as fenced data. The file is read strictly — an unknown key, or an id that is not a snowflake, stops mochi rather than leaving it obeying nobody.

What a mention gathers depends on where it is, because the discussion a moderator's suggestion gets is mostly plain messages rather than replies, and no fixed window of the latest messages holds it. A reply in a channel gets the replied-to message, its reply chain upward, about fifty messages either side of it (one `around` call, which Discord caps at a hundred), and any later message in the channel that replies to it, deduplicated and in time order. A mention inside a thread or forum post mochi did not open gets the thread from its starter, up to a hundred messages, with the starter added and the gap said when the thread is longer. A mention that replies to nothing, outside a thread, gets the last fifty messages of the channel. Every message carries its author's display name, its time and its link, and the replied-to one is marked. Tim's own mention is the instruction and is not repeated in the context, except inside a thread, where it is part of what the thread is about. Nothing gathered is dropped, but the context comes in two labelled sections, each in time order, and the orders say the first is what Tim's instruction is about: FOCUS — the replied-to message, its reply chain and the later replies to it; in a thread, its starter and Tim's mention with what it replies to; for a mention that replies to nothing, the last five messages before it — and then SURROUNDING CHANNEL, marked as possibly unrelated, with everything else. A split session's TASK line stays above both. A prompt over 200 KB loses the oldest surrounding messages first and never the focus, and says so. A follow-up and `mochi history` have no sections.

Every attachment in what was gathered is downloaded into `~/Library/Caches/mochi/sessions/<thread>/`, outside any repository, and listed by path beside its message, because Claude reads an image from a path and Discord's attachment URLs expire. 25 MB a file and 100 MB a session, and a file skipped for either is listed as skipped and why. The folder goes when the session's record does.

The session is a new tab in the mapped workspace — found by its label in `herdr workspace list`, made in the repository when there is none — with `--cwd` set to the repository, `--no-focus`, and `MOCHI_THREAD=<thread id>` in its environment; then `herdr agent start mochi-<thread> --kind claude` with no model or effort, which leaves both at Tim's defaults, and `herdr agent prompt` with one short line: `/lead`, and the path of the session's brief, `~/Library/Caches/mochi/sessions/<thread>/brief.md` at 0600, to read before anything else. One line because Claude Code turns a long paste into a "[Pasted text]" placeholder, and a `/lead` inside one never runs, so the lead skill would not load; a follow-up is pasted the same way, pointing at `relay-<message>.md` beside it. The brief holds what is that session's alone: a first line, "Invoke the mochi skill before anything else.", where the session posts, then Tim's words and everybody else's in two blocks fenced the way hachiko's on-call brief is — a nonce only that prompt knows, backticks and marker look-alikes taken out — and a split session's TASK line inside the fence; a follow-up's file opens by pointing back at the skill. The standing orders every session shares are the `mochi` skill in `home/.claude/skills/mochi`, which sessions can also load by themselves: how to read the fenced blocks, `mochi history` and `mochi post` with their flags, who reads what, the post shapes, and keeping the tab's name. No on-call standing orders: this is ordinary work in a project, under the lead workflow.

On Discord: a thread opened on Tim's message whose first post mentions Tim — "Session started for <@Tim>'s message: <link>", the link a raw one Discord shows as a pill and a forum on its card, then the replied-to message and Tim's words as block quotes under their authors' names, line breaks kept, attachments as a count like "(2 images)", anything that would ping a crowd or a role made inert, then "**Summary:**" and the classifier's one or two plain sentences on what the messages ask for, for that session's task, escaped like any title and left out when the classifier gave none or when it holds a link or a path, by the same check `mochi post` makes, and the replied-to message shortened with "…", then the summary, to keep the post under Discord's 2,000 characters — since he keeps Discord's notifications to mentions and this is what subscribes him to the thread; he is also made a member of it, so he follows it even if the mention is missed, and neither happens in a thread he is already in. No word mochi posts names a tool behind the work, since moderators read it; the tab and the workspace are in the log for Tim — and 👀 on his message, a mention or a follow-up, for as long as mochi is handling it, taken back once the reply, the question, the ❌ with its reason, or the session's prompt is out; nothing else of mochi's is ever on a message. The state is in the name of the thread or post mochi made, in front of its title: `⏳ <title>` a session working, `❓ <title>` waiting on Tim (a question to answer, or a result to review), `✅ <title>` done with nothing left for him, `❌ <title>` failed. Discord allows a thread two renames in ten minutes, so the name wanted is kept and only the latest is sent: a rename over the limit, or one Discord answers with 429, is made once when the window has passed, never the states in between; a thread mochi did not create, such as a forum post Tim mentioned it in, is never renamed and keeps its author's title. The session moves the state itself with `mochi post --review` (❓) and `--done` (✅), and a follow-up of Tim's puts it back to ⏳ until the session's next such post. Each session's state and its name are kept in `~/Library/Caches/mochi/marks.json`, under a lock since a session's `mochi post` writes it too, so a restart renames from the right state. A session that has stopped on Tim says so itself: the global settings run `mochi session-event` from a `Stop` hook and from a `PreToolUse` hook on `AskUserQuestion`, and say when Tim has answered in the session itself from a `PostToolUse` hook on `AskUserQuestion` and a `UserPromptSubmit` hook; each in a session with `MOCHI_THREAD` set writes one small file into `~/Library/Caches/mochi/events/` — thread, kind, and how much work was still running — and outside one does nothing; it runs the cached binary, reads no config, needs no token, prints nothing and always exits 0, so the turn and the tool go on exactly as without it. The listener reads that folder every second. A question, or a turn that ended, waits three seconds first, so a follow-up queued behind the turn that starts the moment it ends cancels it, and then shows ❓ and gets one post in its thread — "The session is waiting on <@Tim>." — the one place mochi pings anybody, allowed to ping him alone; not for a session that said it is done, nor for a turn that ended with subagents or shells still running, and not again until his next word reaches the session, from Discord or typed in the session itself. That word puts ⏳ back unless the session has set a state of its own since the ping, and anything the session reported from before it, or from before a follow-up last started it, is out of date and pings nobody. A ping that fails is retried after 30 seconds, doubling to an hour, and a thread Discord no longer has is left alone. Whether he has been pinged is kept in `waits.json`, so a restart neither pings twice nor forgets, and a restart clears any half-written event a hook was killed in the middle of. A session that is done and has cleaned up, with nothing left open, posts `--done --close`, which leaves a `close` event of its own; mochi closes its tab a minute later, but only when Tim's last word to it came from Discord. A prompt submitted in the session counts as his own typing unless it is one of the prompts mochi pastes, which the hook recognises by how they begin, and any word from him inside the minute keeps the tab open. The tab is closed only while nobody can be using it: it still carries the label mochi gave it, holds the one pane, is not the tab in front, and its agent is neither working nor on a question; otherwise the log says why and the request is dropped rather than tried again. The record stays, so a later follow-up starts a new session. The skill gives a session two audiences: the thread is the team's, for progress about the product as users see it — findings, options and trade-offs in product terms, questions the team can weigh in on, results with screenshots — and the session is Tim's, for anything internal: code, APIs, rate limits, infrastructure, tools, plans. A decision with both sides is framed for the product in the thread and kept technical in the session; a post with no flag is an update about the product that needs no answer. The thread and the tab are named for what the session is about: the classifier's title for the task, or when it gave none the start of the message Tim replied to, then his own words — a name for him to find it by, which a session sees only inside the fence. A mention inside a thread somebody else opened makes that thread the session's, since a thread cannot hold a thread. Anything that fails is ❌ and one line saying why, in the thread, or as a reply to his message when there is no thread yet. Every line mochi writes itself is a sentence, a capital first and a stop at the end, and names Tim only by a mention where it means to ping him. Every post mochi makes has `allowed_mentions` empty, so nothing it quotes pings anybody.

One mention can start several sessions: "research a, b and c separately" is three. Claude decides that, rather than a rule about the wording. Before a new session, mochi runs one headless `claude -p` with `--output-format json --json-schema` and `--tools "" --strict-mcp-config --setting-sources "" --no-session-persistence`, in an empty temporary folder, with the prompt on stdin, the same scrubbed environment as herdr's, and a minute to answer. It sees Tim's instruction and the message he replied to, fenced, for resolving "a, b and c", and answers with a decision — one session, one per item, or ask — a title for the work as a whole, and every item it sees, each a title and a self-contained instruction. "many" is for items he asks to be done separately and for plainly unrelated pieces of work; "one" for a single item or one piece of work about several, such as comparing them or one plan; "ask" when his words cover several items without saying which, such as "take a look at the three suggestions". The model and effort are `[split]` in the config file, sonnet at medium by default; `mochi split-eval --model <m> --effort <e> < cases.jsonl` runs JSON-lined cases (`{"instruction":…,"replied":…,"want":N}`, with `"decision":"ask"` for a case that should be asked about) through the same prompt, schema and flags and prints each case's decision, count, titles, time and pass, then a summary, which is how the model is chosen. One task, or any failure — a timeout, JSON that does not parse, an empty list, no `claude` — is one session with Tim's own words, as if nothing had been asked. More than five for "many" is a ❌ and nothing started. On "ask", mochi replies to his mention "Separate sessions or one?" with two buttons, one naming the items and one for a single session — only the second when there are more than five — and he can also reply to the question with the number, "all", "separately", "one" or "1". Only his press counts; anybody else's gets "Only the person who asked can choose", visible to them alone. The press is acknowledged at once, the question is edited to show the answer with its buttons disabled, and the sessions start as if he had asked for that from the start. A question waits in `~/Library/Caches/mochi/pending.json`, so a restart still takes the answer, for a day; then it is edited to say it expired and he mentions mochi again. Buttons arrive over the gateway like messages, needing no intent and no permission beyond posting the question. Several tasks each get a public thread of their own in the channel, named from the title, and their own tab and session with the shared context and their own instruction; mochi replies to his message with a link to each, and reacts ⏳ while any of them works, ❓ when none does and one waits on him, ✅ once all are done, or ❌ when any did not start; each new thread's first post carries its own session's state. A mention inside a thread splits into the thread's parent channel; inside a forum post, which has no channel to open threads in, it is one session, and the thread says so. A follow-up is never classified.

A mention inside a session's thread is a follow-up, relayed to the same agent as a new prompt with everything posted in the thread since his previous mention, fenced: the moderators' answers, his own messages, and the session's own posts, marked "mochi (this session)" so it can tell what it said from what was said back. Nothing in the thread reaches the session unless he mentions mochi. When the agent is gone — a session he closed — a new one starts with the whole thread as context, and the thread says so. Tim answers wherever he is, so a follow-up to a session waiting on a question, which herdr will not prompt, is his answer to it: mochi cancels the question with an esc, reads `herdr agent get` until herdr stops calling the agent blocked, as hachiko's on-call does, and then prompts it with a brief that opens by saying he answered in Discord instead of the question; a question still up after five seconds of that is a ❌ and nothing prompted. `~/Library/Caches/mochi/state.json` maps each thread to its agent, its source and his last mention; a record untouched for a week whose agent is gone is dropped with its attachments.

A session has two commands of its own. `mochi post [--review | --done] [--pr <url>] [--file <path>]... <text>` posts into its thread, split between lines past Discord's 2,000 characters, with up to ten files of at most 10 MB each, Discord's limits for one message on a server without boosts. `--review` is for a post that needs an answer from Tim or the team — a result ready for review, or a question about the product — and sets ❓; `--done` is for a task complete with nothing left for him, such as after he said to merge and it merged, and sets ✅; a post with neither changes no state. The thread's readers are moderators, often not technical and without GitHub access, so a post stands on its own in Discord: plain language about what they will see as users, proof as images or video. Text carrying a link, a Discord invite or a file path is refused with the reason; the one link a post may carry is a pull request through `--pr`, which takes only `https://github.com/<owner>/<repo>/pull/<number>` for the session's own repository, read from the mapped checkout's origin remote, and adds `#<number> (<url>)` as a line of its own, with link previews suppressed. The skill tells the session to post with `--review` when it hands Tim a result and `--done` when it is finished, `--pr` on those whenever there is a pull request, and nothing else unprompted. Such a post has a fixed shape — a bold one-line summary, then **What changed** in at most three plain bullets, **Screenshots** numbered in the order the files are attached, **Still to check** only when something is left, and **Questions** as a numbered list so people can answer by number — with headings and list styles fixed, and stays brief, since Tim reads the details in the session and the pull request. With no text argument, `mochi post` reads the text from stdin, so a post of several lines needs no shell quoting; the outer process reads it before `op run` and passes it on as an argument. `mochi history [--before <id> | --after <id> | --around <id>] [--limit N]` prints up to a hundred more messages of the channel or thread it started from, in the same fenced form, with their attachments downloaded, and says how to page further; the prompt tells the session to page back whenever the start of the topic is not in view. Both read the thread from `MOCHI_THREAD` and refuse one mochi has no record of, and history reads only the source in that record, never one passed to it, so a session cannot browse the rest of the server.

The token is the `bot token` field of the `mochi-discord` item in the `dev` vault, referenced from `home/.local/bin/mochi.env.op` beside the wrapper. Every command that needs it re-enters the binary under `op run --env-file`, so it is in one process's environment and never in an argument, a file or the log, and it is taken out of any error text before that is logged. The listener resolves it once per start, and `post` and `history` once per run. A start that never got a token leaves a marker in the cache, and the next start waits out half an hour from it before asking 1Password again, as does a start Discord refused: `ThrottleInterval` alone would be an `op run` every five minutes for as long as the item does not resolve. A gateway that will not connect is tried again in five seconds, doubling to five minutes with a fifth of jitter either way and never sooner than five seconds after the last identify of any mochi process, which is Discord's limit; a close with 1000 straight after an identify is tried again at once. Ten failed attempts, or half an hour of them, and the listener exits, as it does when a connection that dropped stays down for half an hour: only a fresh start under `op run` picks up a token rotated in 1Password, and nothing beats while it is down, so the watch below has already said so. A token Discord turns away, close 4004, is not tried again at all.

While the gateway is connected — Discord acknowledging its heartbeats — mochi writes `~/Library/Caches/mochi/heartbeat` every half minute, and hachiko's watch reads its age the way it reads sync's, from the plist where there is no heartbeat yet: ten minutes without one is a ⚠️ naming `launchctl kickstart -k gui/<uid>/io.github.timche.mochi` and the log. When the wrapper has built a new binary behind it, mochi closes its Discord connection and becomes the new binary in the same process, between mentions and never inside one: `exec` with the arguments and environment it already has, so the token it was started with carries over and no second `op run` is spent. Only when that fails does it exit, for `KeepAlive` to start it again behind the plist's five-minute throttle, which also stands between a binary that crashes on start and a loop of `op run`s. Nothing else runs mochi's wrapper on a timer, so the listener runs `~/.local/bin/mochi version` itself every five minutes, with no secret in its environment, which is what builds an edit. A message sent while it is reconnecting or restarting is not replayed to it, a fresh gateway session not receiving what it missed, so a mention that got no 👀 is one to send again.

A server with a `forum` in the config gets a post in that forum for each session started from a channel, rather than a thread on Tim's message, since new messages bury a thread. The post is named as a thread would be, `⏳ <title>`, the emoji its state and nothing else, and tagged with the classifier's kind of work, `Feature`, `Bug`, `Improvement` or `Research`, found on the forum by name and skipped when the forum lacks it. A state change renames the post; a change of type edits name and tag together, which counts against the same two-in-ten-minutes limit as a rename, and a forum that refuses the tag leaves the name following the state alone. A post that still carries a state tag from before loses it with its next change. Its first message is the announcement with its quotes, Tim is made a member, and his mention gets one reply, "Moved to [<title>](<post>)."; a split is a post per task and one reply listing them, and the question of how to split stays a reply in the channel. A follow-up inside the post relays as one in a thread does, and `mochi history --post` reads the post where plain `mochi history` reads the channel the session came from. A session refiles its post with `mochi post --type <kind>`, when Tim says it is another kind of work or the work shows it. A post three days in `Done` is archived, never deleted, and comes back to the list when somebody writes in it. A mention inside a thread or a post mochi did not make, a forum post of somebody else's included, stays as it was: that thread is the session's, with no post. Sessions in threads opened before a server had a forum go on as threads.

Setting it up: a Discord application of its own called mochi, separate from the hachiko-discord admin bot, with Public Bot off and the Message Content intent on, invited to each server with View Channels, Read Message History, Send Messages, Create Public Threads, Send Messages in Threads, Add Reactions, Embed Links and Attach Files, which in a forum also covers making posts and editing the name, tags and archiving of mochi's own; no Manage Channels or Manage Threads; its token in the `bot token` field of the `mochi-discord` item in the `dev` vault; and an entry in the config file for the server. `install.sh` links the rest and loads the agent.

## Preferences

Tim's own preferences, split by what mise's declarative `[bootstrap.macos.defaults]` can say: a plain user default is declared in `mise.toml` and written by the same `mise bootstrap` that applies the links, and everything else is in `install.sh`.

| Preference | Applied by | |
| --- | --- | --- |
| Tap to click | `mise.toml` | `[bootstrap.macos.trackpad]`'s `tap_to_click`, one friendly key for both `Clicking` domains, plus the per-machine `com.apple.mouse.tapBehavior` as an explicit `host = "current"` entry |
| Finder: hidden files, every extension, status bar, path bar, no extension-change warning | `mise.toml` | `[bootstrap.macos.finder]` covers four of the five; `AppleShowAllExtensions` is global rather than Finder's own and has no friendly key, so it is a raw entry |
| Screenshots in `~/Pictures` | `install.sh` | The value has to be an absolute path — neither mise nor the screenshot service expands a `~`, and mise does not template a defaults value — so declaring it would mean spelling the account name out, which nothing here does |
| `~/Library` visible in Finder | `install.sh` | A flag on the folder, and a Finder info xattr beside it, rather than a preference at all |
| A Dock with none of the icons macOS ships with | `install.sh` | Once, recorded under `~/.local/state/mac-mini` |

Every one of them reads before it writes, and nothing restarts an application that had no reason to notice. That last part is why the restarts are `install.sh`'s rather than a `post-defaults` hook: mise deliberately kills no application, and a hook there would relaunch Finder on every install whether a preference changed or not. So `install.sh` takes the whole `com.apple.finder` domain aside before the bootstrap — the domain rather than the four keys, which is one fewer list to keep in step with `mise.toml` — and relaunches Finder only if the bootstrap or the `~/Library` flag moved something. The screenshot location relaunches `SystemUIServer` and `screencaptureui` both: every guide still names the first, and the process actually found holding the stale copy is the second.

The Dock is emptied once and then left alone. mise could own `persistent-apps` with `apps = []`, but from then on every install would wipe whatever Tim had pinned since the last one, and what he asked for was the factory set gone rather than a Dock that refuses to hold anything. A marker file is what says it has been done, and nothing reads `persistent-apps` again afterwards.

One of them is believed rather than proven. Tap to click's two `Clicking` domains look to be a mirror System Settings keeps rather than what the input stack reads — forcing them to 0 and the per-machine key to 1 still taps to click — so the `host = "current"` entry is the one doing the work and the other two are there because System Settings shows them.

CI reads every one of these back on the `macos-latest` runner and asserts that a second pass finds nothing to write, which is what `mise bootstrap macos defaults status --missing` answers.

## Testing

`.github/workflows/test.yml`, on a `macos-latest` runner and nowhere else: there is no macOS container to put any of this in, and the suite changes the machine it runs on. Hosted runners are free to a public repository, which is the reason this one is public.

The job runs `bootstrap.sh` first, against a clone of the branch under test rather than of main, which is the only path that clones anything. Then each phase by hand, with the asserts after each: `machine.sh` twice, `xcode.sh` twice, then `claude.sh` and after it the `install.sh` that is its own first step, which is the second pass over the account half. The repeat is what keeps the whole of it honest about being safe to re-run, which is the only way a change ever reaches a Mac that is already built. The runner's account is called `runner`, which is what proves nothing here assumes an account name. Then the [root helper](#the-root-helper) under sudo, which only a machine with passwordless sudo can exercise and a runner is exactly that: `--list` and three refusals. None of the actions themselves — a runner has SIP disabled, so a `restart-daemon` kickstart succeeds there where a real Mac may refuse it, which is the opposite of the case the fallback exists for; a `flush-dns` would leave the job's own resolver cold for no information; and a `reinstall-portless` would install a daemon on a machine that is about to be thrown away. Then the two tests that need more than a file read: `signing-key.sh` and `sync-agent.sh`. Then `harden-ssh.sh` with a key seeded the way a real Mac has one, last, because a runner has nothing after it that needs to log in.

There are three assert scripts, one per phase: `test/assert-machine.sh` for what `machine.sh` left, `test/assert.sh` for what `install.sh` left, and `test/assert-claude.sh` for the logins and the signing key.

[shibuya](#shibuya)'s tests are in that job too, although nothing about them needs a Mac: they run in workerd, and this is the job that has mise's node, which is the node every project on this Mac uses. A second job would mean a second way to install node and a second place naming the version it installs. `deploy.sh` runs the same tests before it deploys, and nothing in a run calls it, so without a step of its own a broken Worker would land green. The `--dry-run` beside it is what proves the bundle builds and the bindings resolve without deploying anything.

The compiled tools are the one part the assert scripts deliberately do not test. `go vet` and `go test ./...` run for each of them in the same job, on the go `install.sh` has just installed, and that is where every rule a tool decides by is checked — against injected seams rather than against the Mac, so nothing has to fill a disk or wait an hour. What `test/assert.sh` adds is the wiring Go cannot see: that the wrapper is linked and runs, that the agents are valid plists and loaded, and that the wrapper's own gate works — a tree whose tests fail leaves the last binary that passed in place. That one runs against a copy of the checkout rather than the checkout, since it has to break a test on purpose and the wrapper builds from the working tree it would be broken in; the copy is trusted to mise through `MISE_TRUSTED_CONFIG_PATHS` rather than `mise trust`, which would leave a temp folder in the machine's trust store on every run.

`test/assert-markdown.sh` is the fourth, and the only one that is about the repository rather than the Mac: the word budget on the always-loaded `home/.claude/CLAUDE.md`, and prose that is never hard-wrapped. `test/assert.sh` runs it and adds the number it failed on to its own, and `.github/workflows/markdown.yml` runs it alone on `ubuntu-latest` in a few seconds. That second job is the point of it being a script of its own: `test.yml`'s paths filter deliberately keeps a markdown-only push off a macOS runner, so a rule that lived only in `assert.sh` would be checked by nothing on exactly the commits it is about. Which is also why nothing in it may reach for a command only macOS has.

`test/signing-key.sh` is the one worth reading. It generates a key, puts a stub `op` in front of the real one on PATH, and runs the real `claude/signing-key.sh` against a throwaway `HOME` — then asserts that the private half landed at 600 in a directory at 700, that the public half beside it is the same key, that no staging file was left behind, that a commit signs from the file with no agent anywhere and verifies, and that moving the private half away leaves nothing able to sign. It runs the script twice, since it is documented as safe to re-run, and the stub counts its own reads so that a second run spending another `op read` on the private field is a failure. It refuses to run outside CI unless `MAC_MINI_TEST_ANYWAY=1`, because it would register its throwaway key on whatever GitHub account `gh` is logged in to. `test/sync-agent.sh` is the other one: it loads the sync agent's plist under a label of its own, with a stand-in for the hachiko wrapper, and asserts what only a real `bootstrap` can — that a symlinked plist loads, that the `HOME` launchd hands a gui-domain job is what the shell expands, and that the status reaching `KeepAlive` is the program's.

A local run is `./install.sh && test/assert.sh` on the Mac itself, which is the quick check after each change; `npm test` in `shibuya/` is the Worker's, and `npx wrangler deploy --dry-run` beside it proves the bundle without deploying. What it cannot answer is the promise the suite actually makes, since it runs against a Mac that is already built: only CI does that, where `bootstrap.sh` runs against a runner on every push. Not from nothing, though — a hosted runner arrives with Homebrew and the command line tools already, so the install that a fresh Mac starts with is the one step skipped there, and what is exercised is the clone and both phases against a machine that has never had them. So a change to the fresh-Mac path is tried by pushing the branch and reading that job.

What CI cannot reach: anything that needs a click. Screen Sharing needs the Sharing pane to register the sharing agent's screen recording rights, so `assert-machine.sh` reports where it stands instead of asserting it. The screen lock is worse than unreachable, for the reason above, so nothing checks it at all. Nor a service account and a vault — which takes the shibuya deploy with it, since `op run` is what resolves the Cloudflare token, so what CI exercises there is the tests and the dry run and never the upload, and `claude.sh`'s own shibuya step sees no token file and says so rather than trying — a tailnet to log in to — the runner installs tailscaled and configures its prefs, which works logged out, but nothing authenticates and the asserts say so — a machine that loses power, and TCC, since the runners have SIP disabled and anything gated on Full Disk Access behaves more permissively there than on a real Mac. That last one is why `remote-login.sh` goes through launchd rather than `systemsetup`, which is gated. A runner's sudoers also grants the account every command, which is what lets the helper install there at all and also means the half of it that matters most — that sudo refuses everything outside the helper — is the one thing only a real Mac can assert; `assert-machine.sh` asks whether some other command runs first and says which of the two it is checking. Nor a hypervisor: a runner is a VM itself and Virtualization.framework inside one refuses outright, and OrbStack's first run is a welcome screen on the Mac's own display besides. So everything docker itself answers — the context, `docker info`, a container, the plugins, the two-service compose file — is skipped on a runner, and only a Mac with OrbStack actually running asserts any of it. The docs clone fails too, the runner's token not reaching `timche/docs`, so `hachiko sync` stays unloaded and the asserts check its wiring rather than a running daemon.
